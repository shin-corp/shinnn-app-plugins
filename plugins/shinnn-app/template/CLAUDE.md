# CLAUDE.md

Claude Code がこのリポジトリで作業するときの全体方針です。**このファイルはルーター**で、詳細は各ファイルに置きます。ここに本文を書き戻さないでください。**優先順位: `docs/仕様書.md` > CLAUDE.md > `.claude/rules/`。** 食い違ったら下位を直します。

## 1. 進め方

1. **open な Issue と PR を見る**（次に着手する Issue と open な PR はセッション開始時に表示されます。出ないときは `gh issue list` / `gh pr list` か GitHub の画面で見ます）。作業項目の正本は GitHub Issues、引き継ぎの注意とシン株式会社への要望は pin した「引き継ぎメモ」Issue です。
2. **頼まれた変更は、文言 1 つの直しでも Issue → ブランチ → PR で進めます（`main` で直接編集しない）。** 対象の Issue を決め（無ければ `/shinnn-app:feature` で作る）、`feature/<Issue 番号>-<slug>`（不具合の修正は `fix/`）ブランチを切ります。1 Issue = 1 ブランチ = 1 PR。
3. `shared`（API 定義）→ `server` → `client` → テストの順に実装します。
4. `/shinnn-app:pr` で PR を作ります（出す前に `/shinnn-app:check` を 1 回通し、出した後に `/shinnn-app:retro` で振り返りを残す）。本文に `Closes #<番号>` を書きます。`feature` が続けて行うので、利用者に打たせません。

## 2. リポジトリ構成

| 場所       | 中身                                                                                    |
| :--------- | :-------------------------------------------------------------------------------------- |
| `shared/`  | 画面とサーバーが共有する **API 定義**（zod スキーマ）。業務ロジックと DB 依存は置かない |
| `server/`  | Express 5 のサーバー。`api/` → `service/` → `db/` の一方向                              |
| `client/`  | Angular の画面。API 呼び出しは `api-client.ts` の `call()` のみ                         |
| `docs/`    | 仕様書・環境変数・設計判断の記録・自動テストで確かめられないものの確認結果              |
| `scripts/` | CI と `/shinnn-app:check` が使う確認のスクリプト                                        |
| `.claude/` | Claude Code の設定とルール                                                              |
| `.shinnn/` | セットアップの記録とプロファイル                                                        |

用語: **API 定義** = 画面とサーバーがやり取りするデータの形（URL・入力・出力）を `shared` に 1 か所だけ書いたもの。両側が同じ定義を参照するので、片方を変えるともう片方がビルドエラーになります。`client` と `server` は互いのソースを import しません。共有するのはこの zod スキーマだけです。

## 3. 技術スタック

| 用途         | 採用                                                                                |
| :----------- | :---------------------------------------------------------------------------------- |
| サーバー     | Express 5 / Node.js 24 / TypeScript ESM                                             |
| DB           | PostgreSQL 16 + Drizzle ORM（テストは PGlite）                                      |
| API 定義     | `shared` の zod 4 + `defineRoute()`                                                 |
| 画面         | Angular（standalone / signals / zoneless）+ Angular Material + CDK + Tailwind CSS 4 |
| テスト       | Vitest（`.test.ts`）。サーバーは `app.listen(0)` + fetch                            |
| パッケージ   | npm workspaces（client / server / shared）                                          |
| 使わないもの | NestJS / NgRx / GraphQL / ORM の抽象化層の追加 / 独自 CSS                           |

**車輪の再発明をしない。** 広く使われ、保守が続いているライブラリは入れてよい（`npm install <名前> -w <パッケージ>`）。条件は、ライセンスが OSS（CI が許可リストで検査）、直近 1 年以内に更新がある、持ち込む依存が少ない、既存の採用と重複しないこと。PR 本文に「何を / なぜ / 代替案」を 1 行ずつ書く。

**費用が発生するものは入れない。** 有償・商用ライセンスのライブラリと、利用料が発生する外部サービスの SDK は、必要だと判断した時点で実装を止め、「引き継ぎメモ」Issue の「シン株式会社への要望」に理由と代替案を書いて判断を待つ。

## 4. コマンドとスキル

`npm install` → `npm run dev`。確認は `npm run check` と `npm test`。ルートのこの 4 つは `shared` のビルドを先に済ませるので、クローン直後でもそのまま動きます。`npm run dev` の最中は `shared` を保存すると自動でビルドし直し、server と画面に反映します。終了コードを出すときは `npm test; echo "exit=$?"` のように文字と一緒に出します（`echo "$?"` や `echo "$exit"` のように変数だけを出すと、毎回確認が出ます）。

| スキル                               | 用途                                                              |
| :----------------------------------- | :---------------------------------------------------------------- |
| `/shinnn-app:setup`                  | 初回セットアップ（1 回だけ。再実行で設定を変えられる）            |
| `/shinnn-app:feature <作りたいこと>` | 要望を PR 1 本ずつの Issue に分け、受入条件を起こして順に実装する |
| `/shinnn-app:check`                  | 型検査・lint・テスト・受入条件カバレッジ・API 定義カバレッジ      |
| `/shinnn-app:pr`                     | コミット → push → ドラフト PR → レビュー → `retro`                |
| `/shinnn-app:why <話題 or ファイル>` | 規約の理由を平易な日本語と before / after で説明する              |
| `/shinnn-app:retro`                  | 学びを Issue に残し、引き継ぎに関わることを「引き継ぎメモ」に足す |

## 5. 共通方針

- **言語**: 利用者への返答・コメント・コミットメッセージ・PR 本文・ドキュメントは日本語。識別子は英語。UI 文言は日本語
- **改行**: LF に統一（`.gitattributes`）。改行だけが変わった差分を作らない
- **コメント**: 仕様・制約・非自明な理由だけ残す。レビュー対応の経緯は書かない。実装を変えたら周辺のコメントと JSDoc も直す
- **既存との整合**: 新規ファイルを作る前に、同じディレクトリの同種ファイルを読み、同じ書き方に揃える
- **削る**: ファイルが長くなったら、分割の前に削れないかを検討する
- **知見の追加**: まず既存の該当箇所を直す。新規作成は最後の手段。1 つの事実は 1 か所にだけ書く
