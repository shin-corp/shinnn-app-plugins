# git の進め方

Issue から PR までの手順です。**paths を持たないので常に読み込まれます。**

「（検査: …）」には、その決まりを機械で確かめる仕組みを書いています。付いていない決まりは、レビューだけで確かめます。

## 1 Issue = 1 ブランチ = 1 PR

作業項目は GitHub Issues で管理します。手で更新する進捗ファイルは持ちません。

| 段階     | やること                                                                                                                          |
| :------- | :-------------------------------------------------------------------------------------------------------------------------------- |
| 着手前   | `gh issue list` で open な Issue を見る。担当する Issue を決める                                                                  |
| ブランチ | `git switch -c feature/<Issue 番号>-<slug>`（例: `feature/12-item-filter`）                                                       |
| 実装     | `shared` → `server` → `client` → テストの順。同じ PR に入れる                                                                     |
| PR       | 本文の「対応 Issue」に `Closes #<Issue 番号>` を書く（検査: CI。本文のどこかにあるかだけを見る）。マージで Issue が自動的に閉じる |

- ブランチ名は `feature/<Issue 番号>-<slug>` にする。不具合の修正は `fix/<Issue 番号>-<slug>` にする。ほかの接頭辞を使わない
- ベースブランチは `main` にする

同じリポジトリで別のセッションが並行して作業しているときなど、別の作業フォルダが要るときは、Claude Code の worktree
（作業ツリー。同じリポジトリを別のフォルダに取り出したもの）を使います。`claude --worktree <名前>` で起動するか、
デスクトップアプリでセッションを worktree で始めます。worktree は `.claude/worktrees/<名前>` に作られ、セッションも
そこで動きます。そのため、許可の設定がそのまま適用されます。

`git worktree add` で隣のフォルダに worktree を作り、元のセッションから `cd` して作業する使い方はしないでください。
この使い方では、リポジトリの外を触ります。そのため、操作のたびに確認が出ます。

作った worktree には、依存と git のフックが入っていません。そのため、最初に `npm install` を実行します。

PR を誰がマージするかは、`.shinnn/setup.json` の `mergePolicy` で決まります（`/shinnn-app:setup` で選びます）。`setupCompletedAt` が `null` の記録（setup が済んでいない）は、`mergePolicy` の値にかかわらず `human` として扱います。`human` のリポジトリでは、人が PR を ready にしてマージします。`auto-merge` のリポジトリでは、`/shinnn-app:pr` が、セルフレビューの収束と CI の通過を確かめます。確かめたら、PR を ready にしてマージします。ただし、CI が始まらないときは「CI が始まらないとき」に従います。どちらの場合も `main` へ直接コミットしません（「やらないこと」）。`auto-merge` での進め方は「`auto-merge` のとき」にあります。

Dependabot（依存更新の bot）が作る PR に対応する Issue（`[依存] …`、ラベル `type:deps`）は、ワークフロー `dependabot-issue.yaml` が自動で作ります。ワークフローは、PR の本文に `Closes #n` を足します。PR が閉じると、Issue も閉じます。CI は、ワークフローが本文を書き換える前に走ります。そのため、CI の `Closes #n` の確認は、bot の PR では免除しています。人と Claude の PR は、Issue を先に作ってから出します。

## コミットメッセージ

```
[<対象>]<体言止めの要約>

- 変更点を箇条書きで
- 「〜した」ではなく「〜の追加」「〜の修正」
```

- 1 行目は `[<対象>]<要約>` の形にする（検査: git のフック。`<対象>` が `shared`・`server`・`client`・`docs`・`ci`・`deps`・最上位のフォルダの名前のどれかであることも見る）
- 要約は体言止めにする（検査: git のフック。語尾の「した」「する」「です」「ます」だけを見る）
- ただし、空のリポジトリでのコミット（リポジトリの最初のコミットと、直前のコミットのファイルが GitHub の作成画面で付けた `README.md`・`LICENSE`・`.gitignore` だけのときのコミット）と、`git merge`・`git revert` が作るメッセージ（`Merge `・`Revert ` で始まるもの）は、1 行目の形・要約の語尾・1 行目の長さ・本文の言語の決まりに従わなくてよい（git のフックは、これらのメッセージを丸ごと見ない）
- `<対象>` は、変更したパッケージ（`shared` / `server` / `client`）にする。文書だけの変更は `docs`、CI の設定の変更は `ci` にする
- ただし、依存の変更（`package.json` の依存の欄と `overrides`（依存の依存の版を差し替える指定）、`package-lock.json`）は、どのパッケージでも `deps` にする
- パッケージにも文書にも CI の設定にも当たらない、案件で足したフォルダ（例: サーバーに置く設定やスクリプトの `deploy/`）の変更は、最上位のフォルダの名前（例: `deploy`）にする
- 受入条件に対応するコミットは、要約に識別子を入れる（例: `[server]AC-2 在庫チェックの追加`）
- **AI の帰属行（`Co-Authored-By` など）を書かない**（検査: git のフック。Claude か Anthropic の名前を含む `Co-Authored-By:` の行と、`Generated with` の後に Claude と書いた行だけを見る）
- 本文は日本語で書く
- 1 行目は 50 文字以内にする（検査: git のフック）
- `Test plan` のような定型の節を付けない（検査: git のフック。`Test plan` だけを見る）
- 複数行のメッセージは、本文をファイルに書いて `git commit -F <ファイル>` で渡す
  （PowerShell の here-string `@'...'@` をそのまま Bash に渡すと、先頭に `@` が付く）

## コミットの分け方

- **定義が先、参照が後。** `shared` の API 定義を先にコミットし、それを使う `server` / `client` を後に置く。
  途中のコミットで型エラーが出ない順序にする
- **実装とテストは別のコミットにする。** 順番は問わない
- パッケージをまたぐ変更は、パッケージごとにコミットを分ける
- ただし、依存の変更は、パッケージをまたいでも 1 つの `deps` のコミットにする
- 依存の変更は、ほかの変更と別のコミットにする
- ただし、依存の変更の理由を `docs/decisions/` の設計判断の記録（ADR）に書く場合は、その ADR の変更を依存の変更と同じ `deps` のコミットに入れる
- 依存を足して使うときは、`deps` のコミットを先に置き、使うコードのコミットを後に置く
- 挙動を変えない整形・リネームを、機能の変更と同じコミットに混ぜない
- ただし、**参照側を同時に直さないと型エラーになる変更**は、`shared` と参照側（`server` / `client`）を
  1 コミットにまとめてよい。例: 型を狭める（省略可 → 必須、値の範囲を狭める）、列挙に値を足す（網羅的な `switch` が型エラーになる）、
  API 定義の名前を変える。まとめた理由をコミットの本文に 1 行書く

## やらないこと

- `git push --force` / `git reset --hard` / `git rebase` / `git clean` を使わない（検査: 権限の設定）
- husky のフックを飛ばさない（`git commit --no-verify` / `git push --no-verify` / `HUSKY=0`）（検査: 権限の設定。
  `git push` の `--no-verify`、`HUSKY=0` で始まるコマンド、`git commit` の直後に書いた `--no-verify` / `-n` だけを止める）
- コミットが lint-staged の `Failed to back up original state!` で止まったときに、lint-staged が案内する `git apply --index <git-hash>` で戻さない
  （戻し方は `/shinnn-app:pr` の手順 2）
- `main` へ直接コミットも push もしない。`main` へは、作業ブランチからの PR でだけ入れる（検査: git のフック。
  GitHub に既にある `main` への push だけを止める。`main` のファイルが作成画面の 3 つだけのときに、テンプレートを取り込むコミット
  （`.claude/rules/.standards-version` を含むもの）を送る push は通す。通すのは、送り先の `main` のコミットを手元に取ってあるときだけ）
- ただし、GitHub の `main` が無いときと、`main` のファイルが GitHub の作成画面で付けた `README.md`・`LICENSE`・`.gitignore` だけのときは、
  テンプレートを取り込むコミットを `main` に作って push してよい（`/shinnn-app:setup` の手順 0）
- `gh pr merge` に `--admin` を付けない（検査: 権限の設定）
- `server` と `shared` の `.ts` に `prettier --write` を掛けない
- prettier で整えるのは、画面（`client`）の `.ts` と json・md・yaml だけにする
- `client` の `.ts` には、手で prettier を掛けなくてよい（保存時の hook とコミット時の lint-staged が整え、CI が確かめる）
- 既存のアプリを一度にそろえる整形は、`/shinnn-app:update-rules` の手順で、整形だけの PR にする
- 生成物（`package-lock.json` / `server/drizzle/` / メッセージキーの生成物 / `client/src/theme.css`）を手で編集しない（検査: 権限の設定。
  `package-lock.json` と `server/drizzle/` だけを止める）

## `auto-merge` のとき

`.shinnn/setup.json` の `mergePolicy` が `auto-merge` のリポジトリでは、利用者は、Issue の作成から PR のマージまでを Claude に任せています。
Claude が作りきった後に、利用者が動く画面を見て調整します。

`/shinnn-app:setup` の実行の間（「進め方」・手順 0〜6・「失敗したとき」）の質問と確認には、この節を当てません。setup の手順に従います。
setup が手順 6 の最後に呼んだ `/shinnn-app:feature` からは、この節に従います。

- 計画・Issue の作成・コミット・push・PR の作成・マージの前に、進めてよいかを利用者に聞かない
- 決まっていないことは、仮置きして進める
- 仮置きした点は、Issue の「未決」に書く
- 見た目の案は、利用者に確かめずに決める
- レビューの指摘で判断が分かれるものは、Claude が決めて直す
- 判断が分かれた指摘で決めた内容は、PR 本文の「規約で迷った点」に書く
- 範囲外で気づいた点は、利用者に聞かずに Issue にする
- 次のどれかに当たったら、その Issue を `status:blocked` にする
  - 費用が発生するものが要る（ルートの `CLAUDE.md` の「費用が発生するものは入れない」）
  - 人が入れたデータを消す変更が要る（`DROP TABLE` / `DROP COLUMN`）
  - 人にしかできない操作が要る（認証情報の入力、ブランチ保護を外す、権限の設定で止まるファイルの変更）
  - 同じレビューの指摘か同じ CI の失敗を、2 巡続けて直せない
- ただし、同じ計画の中で足したテーブルと列を消す変更では、`status:blocked` にしなくてよい
- ただし、コミットが lint-staged の `Failed to back up original state!` で止まったことだけでは、`status:blocked` にしない（その場で戻す。戻し方は `/shinnn-app:pr` の手順 2）
- `status:blocked` にした理由は、その Issue に書く
- `status:blocked` にした後は、進められる別の Issue に移る
- 利用者への報告は、進められる Issue が無くなったときに 1 回にまとめる
- ただし、コミットが lint-staged の退避で止まったときの、利用者にアプリを閉じてもらう依頼は、その場で出す
- 報告には、仮置きした点の一覧と、`status:blocked` にした Issue とその理由を入れる

## CI が始まらないとき

Actions（GitHub の上で CI を動かす仕組み）には、月に使える時間（分）の上限があります。上限を超えるか障害が起きると、CI が動きません。
CI は job（CI の検査のまとまり。「型検査と lint」「テスト」「規約チェック」）に分かれています。
job は step（1 つ 1 つの手順）に分かれています。
「CI が始まらない」とは、落ちた実行の job がすべて、step が 1 つも動かずに落ちていることです。

- CI が始まらないときは、手元の確かめで代えてマージに進んでよい（確かめる中身と手順は `/shinnn-app:pr` の「8. CI が始まらないとき」）
- ただし、step が 1 つでも動いて落ちた job がある CI は、手元の確かめで代えない
- 手元の確かめで進めた PR は、番号を「引き継ぎメモ」Issue の「CI で確かめていないマージ」に足す
- 必須のチェックを課すブランチ保護（またはルールセット。新しい方式のブランチ保護）があるときは、人に外してもらってからマージする
- Claude は、ブランチ保護を自分で外さない
- ブランチ保護を外してもらうときは、その旨を「CI で確かめていないマージ」に書く
- ブランチ保護を外している間の PR は、頼み直さずにマージしてよい
- Actions が動くようになったら、`main` の最新のコミットで CI を走らせる（手順は `/shinnn-app:pr` の「9. CI で確かめていないマージを確かめる」）
- 外したブランチ保護は、`main` の CI が緑になってから、人の了承を得て戻す
- 「CI で確かめていないマージ」の行は、確かめた CI が緑になるまで消さない

## なぜ

Issue 番号を軸にするのは、半年後でも「なぜこのコードがあるのか」を辿れるようにするためです。ブランチ名・PR 本文の
`Closes #n`・テスト名の受入条件の識別子から、元の Issue にたどり着けます。また、状態を人が書き写す場所がありません。
そのため、更新漏れで実態と食い違うこともありません。

コミットを層ごとに分けるのは、レビューする人が 1 コミットずつ読めば理解できるようにするためです。
API 定義と実装が同じコミットに混ざっていると、差分のどこが「決めたこと」でどこが「決めたことへの追従」か
分からなくなります。

参照側を同時に直さないと型エラーになる変更をまとめてよいのは、どのコミットでも型検査を通すためです。`shared` だけを
先に出すと、そのコミットで参照側が型エラーになります。

依存の変更を `deps` の別のコミットにするのは、レビューする人が依存の変更を 1 か所で確かめられるようにするためです。
依存の変更では、ライセンスと、何が入るか（依存の依存を含む）を確かめます。Dependabot（依存更新の bot）のコミットも `[deps]` を使います。
どのパッケージの依存でも `deps` にし、パッケージをまたいでも 1 つのコミットにするのは、ルートの `package-lock.json` をどのパッケージに数えるかで迷わないためです。
`package-lock.json` は、ワークスペース全体で 1 つです。
依存の変更の理由を書いた ADR を同じコミットに入れるのは、依存の変更と、その理由と外す条件を一緒に戻せるようにするためです。
片方だけを戻すと、ADR と `package.json` が食い違います。
依存を足して使うときに `deps` のコミットを先に置くのは、途中のコミットでもビルドと lint を通すためです。
lint は、`package.json` に書いていない依存の import を止めます。

案件で足したフォルダの変更の `<対象>` をフォルダの名前にするのは、テンプレートに無いフォルダでも `<対象>` を迷わずに決めるためです。
最上位のフォルダの名前にするのは、`deploy/staging/` のような下のフォルダごとに `<対象>` が増えないようにするためです。

コミットメッセージを git のフックで確かめるのは、形の崩れを履歴に残さないためです。
形と長さと帰属行は文字列で判定できるので、フックから AI のモデルを呼びません。
モデルを呼ぶと、オフラインや未ログインの環境でコミットできなくなります。

`server` と `shared` に prettier を掛けないのは、変更と関係ない行の改行を変えないためです。この 2 つは、prettier の
書き方にそろえていません。prettier の書き方では改行が増え、かえって読みにくくなることがあります。`eslint --fix` は、
改行や字下げを整えません。

force push と `--no-verify` を禁じるのは、非エンジニアが復旧できない状態になるのを防ぐためです。履歴や検査が
いったんおかしくなると、非エンジニアには元に戻せません。履歴を書き換えずに前へ進む（打ち消しコミットを積む）方が、常に安全です。

lint-staged が案内する `git apply --index <git-hash>` で戻さないのは、この案内では退避（stash）を戻せないためです。
`git apply` はパッチのファイルを読むので、退避のコミットの値を渡すと失敗します。
また、この止まり方では、作業ツリーと index（ステージした中身）が半端な状態で残ります。index を HEAD に戻してから退避を当てないと、衝突します。

作業ブランチへの push を確認なしで実行するのは、確認を求めても、コードを読まない人には判断できないためです。push の
中身の良し悪しは、コードを読まないと分かりません。代わりに、困ることを仕組みで止めます。

GitHub に `main` がまだ無いときは、PR の送り先がありません。そのため、テンプレートを取り込むコミットと push だけは `main` に直接行います。
GitHub の作成画面で付けた `README.md` などだけの `main` に直接 push してよいのは、守る中身がまだ無いためです。
作成画面で付けた `README.md` には、リポジトリの名前と、入れたときは説明の文だけが書かれます。
空のリポジトリでのコミットのメッセージをフックが見ないのは、そのコミット（テンプレートの取り込み）には `<対象>` に当たるパッケージが無いためです。
フックが空のリポジトリかをファイルの顔ぶれで見て、テンプレートの目印で見ないのは、目印が消えたリポジトリで検査が止まり続けないようにするためです。

`main` への push を確実に止めるのは、GitHub のブランチ保護です。使えるプランなら、setup が設定します（推奨）。
`.husky/pre-push` は、誤って push したときに止める安全網です。ただし、フックを飛ばす書き方があるので、これだけには
頼りません。秘密情報は、`.env` の読み取りの禁止と、`.gitignore` と、CI で止めます。

`gh pr merge` の `--admin` を禁じるのは、ブランチ保護が課す条件（必須のチェックなど）を満たさない PR を `main` に入れないためです。
`--admin` は、リポジトリの管理者の権限で、その条件を飛ばしてマージします。
setup が設定するブランチ保護は管理者にも当たるので、GitHub の側でも断ります。
ただし、人が設定したブランチ保護とルールセットでは、管理者が条件の対象から外れていることがあります。

`auto-merge` で確認を挟まないのは、作りきるまでの時間を短くするためです。
確認のたびに作業が止まると、利用者は画面の前を離れられません。
利用者にとっては、案の説明を読むより、動く画面を見るほうが判断しやすいです。

仮置きした点を報告に入れるのは、利用者が後からまとめて直せるようにするためです。

Issue を 1 つだけ止めて別の Issue に移るのは、1 つの人待ちで残りの作業まで止めないためです。

確認を挟まずにマージしてよいのは、セルフレビューの収束と CI が歯止めになるからです。
使えるプランでは、ブランチ保護も歯止めになります。

setup が済んでいない記録を `human` として扱うのは、利用者が選ぶ前に、テンプレートの値（`auto-merge`）で確認なしのマージに進まないためです。

setup の実行の間にこの節を当てないのは、マージの方針などを利用者に聞く質問を、「`auto-merge` のとき」の決まりで飛ばさないためです。

setup が呼んだ `feature` からこの節に従うのは、setup の後の実装を、確認を挟まずに作りきるためです。

同じ計画の中で足したテーブルと列を消すときに止めないのは、人が入れたデータがまだ無いからです。

コミットが lint-staged の退避で止まったことだけで `status:blocked` にしないのは、半端な変更を別の Issue のブランチに持ち込まないためです。
Issue を止めると、PR が無ければ、まずここまでの変更をコミットします（`/shinnn-app:feature` の「Issue を止める」）。
ほかのアプリがファイルを開いている間は、このコミットも同じところで止まります。
止まるたびに、半端な状態の退避がもう 1 つ積まれます。
積まれると、`/shinnn-app:pr` の戻し方が選ぶいちばん上の退避は、止まる前の状態ではなくなります。
続けて `main` に切り替えると、手元に残った半端な変更は、切り替えた先のブランチに移ります。
`/shinnn-app:pr` の戻し方は、今のブランチの名前で退避を探します。そのため、切り替えた後は、退避が見つかりません。
引き換えに、利用者がアプリを閉じるまで、ほかの Issue の作業も止まります。

アプリを閉じてもらう依頼をその場で出すのは、閉じてもらうまで戻せないためです。
ほかのアプリが開いているファイルは、`git restore` でも書き戻せません。

CI が始まらないときにマージを止めないのは、コードと関係ない理由で作業を止めないためです。始まらない原因は Actions の上限や障害です。コードを直しても、CI は始まりません。

手元の確かめで代えてよいのは、CI の検査のうち認証情報の混入（gitleaks）以外を手元で見られるからです。認証情報の混入は、後で `main` の CI の gitleaks が履歴をすべて走査して確かめます。PR のブランチは push の時点で GitHub にあるので、マージしても漏れる範囲は変わりません。

step が動いて落ちた CI を代えないのは、コードの不具合を見逃さないためです。

ブランチ保護を人が外すのは、保護が必須のチェックの報告を待ち続けて、マージを止めるからです。Claude が自分で外さないのは、保護を外す判断を人に残すためです。

外したブランチ保護は、緑になる前に戻すと、その間に出した PR がマージできなくなります。CI が始まらないままでは、必須のチェックが報告されないからです。

番号を残すのは、後で確かめる PR を忘れないためです。
