# 画面を 1 つ追加する

このスキルは順番だけを示す。守る決まりは `client/CLAUDE.md` と `.claude/rules/` の client の規約
（`client-architecture.md`・`client-coding-conventions.md`・`client-styling.md`）にある。**層を新しく作らない。**

最初に手本のサンプル `client/src/app/features/items/` を読む（サンプルの `items` を消した後は、既存の機能を手本にする）。
読むと、`client/CLAUDE.md` と client の規約も読み込まれる。

**画面のコードを書く前に、手順 0 で見た目の方針を確かめ、手順 3 で Skill ツールで `frontend-design:frontend-design` を
呼んで、デザインの指導を受ける。書き終えたら、手順 9 で作った画面を見直す。どれも飛ばさない。**
ただし、手順 9 を飛ばしてよいときと、いつ受けるかの決まりは、`.claude/rules/client-styling.md` の「デザインの指導」にある。

## デザインの指導を受ける

受け方は、どの場面でも次のとおり。

1. 材料を集める。

   | 材料 | 取る場所 |
   |:--|:--|
   | アプリの目的とやること | `docs/仕様書.md` の「目的」「スコープ」 |
   | 使う人と場面（どんな人か、業務と IT の慣れ、どこで・どの機器で・どのくらいの頻度で使うか） | `docs/仕様書.md` の「見た目の方針」の「使う人と場面」。空か分からないところがあれば、依頼の言葉と今ある文書から推測して書く（書き方は規約の「デザインの指導」） |
   | 見た目の方針（配色・書体・骨組み・大事にすること） | `docs/仕様書.md` の「見た目の方針」。空なら「空」と書く |
   | 今回の対象 | 対象の画面、その受入条件、増える項目と操作、利用者の依頼の言葉 |
   | 今の画面 | 手順 9 の 1 のとおりに撮った画像の場所。画面がまだ無ければ省く |

2. Skill ツールで `frontend-design:frontend-design` を呼び、`args` に材料と次の条件を渡す。
   - 業務の画面なので、目新しさより、使う人が迷わず・間違えずに速く進められることを優先する
   - 部品は Angular Material、見た目は Tailwind のユーティリティで作る。守る決まりは `.claude/rules/client-styling.md`
     （「テーマと書体」を含む）。案が規約とぶつかるときは規約に従う
   - `mergePolicy` が `auto-merge` なら、確かめる相手はいない。案を 1 つに決めて進める
3. 指導の結果から、配置・情報の優先度・文言・読み込み中と 0 件のときの案内を決める。
   方針を変える案になったら、`docs/仕様書.md` の「見た目の方針」を先に直す。

## `frontend-design` が無いとき

スキルの一覧に `frontend-design` が無いときは、`claude plugin install frontend-design@claude-plugins-official --scope local`
を実行する。配布元に無いと出て失敗したら、`claude plugin marketplace add anthropics/claude-plugins-official` を実行してから
入れ直す。入れたものは、次に起動したときから使える。

- 「見た目の方針」が空なら、ここで止めて、利用者に起動し直してもらう。起動し直した後に手順 0 から始める
- ただし、`mergePolicy` が `auto-merge` なら止まらない。使わずに進め、同梱のテーマのままにする。起動し直すと指導を受けられることを、最後の報告に書く
- 方針が埋まっていれば、今回は使わずに進め、手順 3 の案は方針と規約に沿って立てる
- 入れられなかったときは、そのことを利用者に伝えて使わずに進める。方針は決めずに空のまま残し、同梱のテーマのままにする

## 0. 見た目の方針を確かめる

`docs/仕様書.md` の「見た目の方針」を読む。埋まっていれば、その方針に沿って 1 へ進む。
空か節が無ければ、先に方針を決める。アプリ全体の見た目を変えたいと頼まれたときも、ここから始める。
すでに画面があるアプリで方針が空のときは、今の見た目のまま方針に書く案も示す（テーマを変えると、今ある画面の見た目も変わるため）。

1. 「デザインの指導を受ける」のとおり指導を受け、使う人と場面・配色（主色と、4〜6 色の役割）・書体・
   画面の骨組み・大事にすることの案を立てる。材料には、仕様書の「画面」も足す
2. 案を利用者に見せて確かめる（色の値と、画面のどこに使うか。書体の名前）。渡した色から Material が濃淡を作るので、
   出来上がる値は少し変わることも伝える。ただし、`mergePolicy` が `auto-merge` なら、確かめずに 3 に進む
3. 決めた内容を仕様書の「見た目の方針」に書く（節が無ければ「画面」の章の終わりに足す）。配色は、生成に渡した色を書く
4. テーマと書体を入れる（決まりは `client-styling.md` の「テーマと書体」）。案で主色のほかの色も決めたなら
   `--secondary-color` / `--tertiary-color` でも渡す。作り直すときも同じコマンドで、`--force` が上書きする。
   どちらもリポジトリのルートで実行する（`-w client` が `client` を指す）

   ```
   npm exec -w client -- ng generate @angular/material:theme-color --primary-color=<主色> --is-scss=false --directory=src/ --interactive=false --force
   npm install <書体のパッケージ> -w client
   ```

   生成した `client/src/theme.css` を `styles.css` の同梱のテーマの代わりに読み込む。書体のパッケージも読み込み、
   書体の名前を `styles.css` の決まった場所に入れる。画面の骨組みのうちアプリ全体に関わるもの（ツールバーなど）は、
   `app.component.ts` のシェルに入れる

5. `npm run dev` で起動し、利用者に画面を開いて見た目を確かめてもらう（開発用の通行証の入れ方は `README.md` の
   「画面から API を呼ぶための通行証（開発中）」）。ただし、`mergePolicy` が `auto-merge` なら、手順 9 で Claude が見直す

## 1. 受入条件と API 定義を確かめる

Issue の受入条件を読み、作る画面と要るデータを確かめる。`shared/src/api/<機能>.ts` に API 定義が無ければ、
先に `/shinnn-app:add-api` で shared と server を用意する（同じ PR）。

## 2. 置き場所とルート

`features/<機能>/` を作り、`<機能>.routes.ts` を `app.routes.ts` から `loadChildren` で繋ぐ。
置き場所の決まりは `.claude/rules/client-architecture.md` の「新規ファイルの配置判断」。

## 3. 画面の案

「デザインの指導を受ける」のとおり指導を受け、この画面の配置・情報の優先度・読み込み中と 0 件のときの案内を決める。
失敗のときの文言は `describeError()` が出すので、出し方だけを決める（`client/CLAUDE.md` の「画面の決まり」）。
依頼には、方針の配色と書体を使うと書く。
この画面だけで使う色や書体が要る案になったら、利用者に確かめてから（`auto-merge` なら確かめずに）、役割の名前で `styles.css` の `@theme` に足す。
その色や書体は「見た目の方針」の「画面だけの追加」にも書く（`client-styling.md` の「テーマと書体」）。

## 4. ページのコンポーネント

`client/CLAUDE.md` の「Angular 規約」に従って作る。

## 5. 取得と表示

`client/CLAUDE.md` の「画面の決まり」（取得と 3 状態、一覧）と「API 呼び出し」に従う。

## 6. 入力

`client/CLAUDE.md` の「画面の決まり」（入力）に従う。

## 7. スタイル

手順 3 の案に沿って、`.claude/rules/client-styling.md` に従って作る。

## 8. テスト

`.claude/rules/testing.md` の「画面のテスト」に従う。画面に現れる受入条件（表示・操作）は、ここで `AC-n` のテストにする。

## 9. 作った画面を見直す

1. 開発用のサーバーを起動し（`/shinnn-app:dev-stack-start`）、画面を撮る。
   画面を操作する道具（ブラウザのツール）が使えれば、それで撮る。無ければ、scratchpad に `playwright-core` を入れ、
   入っているブラウザ（`channel: 'msedge'` か `'chrome'`）を画面なしで動かして撮る。
   認証が要る画面では、`npm run token -w server` で発行した値を `addInitScript` で `localStorage` の `token` に入れる
2. 撮った画像を Read で開く。画像の場所を材料に足して、「デザインの指導を受ける」をもう一度行う。
   頼むことは、この画面の批評と、直す箇所を優先の順に挙げること。
   前に受けた指導が会話に残っていても、Skill ツールで呼び直す。画像を自分で見て直すだけで済ませない
   （手順 3 の指導は作る前の案に向けたもので、出来上がりの批評ではないから）
3. 直して、撮り直す。指導と直しは 2 巡までにする
4. PR 本文の「確認した結果」に、見直した画面と直した点を 1 行で書く
5. 撮れないときと、`frontend-design` が使えないとき（「`frontend-design` が無いとき」で入れて、まだ起動し直していないときを含む）は、
   飛ばして先に進む（規約の「デザインの指導」のただし書き）。PR 本文の「確認した結果」に、見直していない理由を書く。
   `frontend-design` が使えなかったことは、最後の報告にも書く

## 確認

```
npm run check -w client
```

画面のパッケージの型検査と lint だけを通す。まとめての `/shinnn-app:check` は、`/shinnn-app:pr` が PR を出す前に 1 回通すので、ここでは走らせない。
