# テスト規約

Vitest を使います。「（検査: …）」には、その決まりを機械で確かめる仕組みを書いています。付いていない決まりは、
レビューだけで確かめます。

- テストファイルの名前は `.test.ts` で終える。`.spec.ts` などの `.spec.*` にしない（検査: CI。`.spec.ts`・`.spec.tsx`・
  `.spec.js`・`.spec.mjs` で終わる名前だけを止める）

## 何をテストするか

- テストは、実装の振る舞いを固定するために書く
- テストが落ちたときに直すものは、次の表で決める。正しさの順位は、仕様書の受入条件、実装、テストの順とする

| 状況                                                 | 直すもの                                                       |
| :--------------------------------------------------- | :------------------------------------------------------------- |
| 仕様書の受入条件と実装が食い違う                     | 実装                                                           |
| 仕様書に書いていない挙動を、テストが決め打ちしている | テスト                                                         |
| テストが、受入条件どおりの挙動を確かめていない       | テスト                                                         |
| 実装を意図して変え、仕様書も更新した                 | テスト                                                         |
| どちらが正しいか分からない                           | **どちらも直さずに手を止め、人に聞く。テストを消して通さない** |

- テストを `skip` しない。ただし、実装に想定外の挙動を見つけ、その場で直さない場合は、`skip` してよい。そのときは、
  Issue を立て、その番号を `skip` の行にコメントで書く
- 不具合を直すときは、直った後の正しい振る舞いを受入条件にする。その受入条件のテストは、直す前の実装で落ちるものにする
- テストそのものの不具合（まれに落ちる、特定の環境でだけ落ちる）を直すときは、受入条件を足さない。直す前と後を
  同じ条件で繰り返して実行する。それぞれの落ちた回数を、PR 本文に書く（確かめ方は `/shinnn-app:pr` の手順 1）
- 振る舞いが変わらない変更（文言・見た目の調整）には、受入条件を足さない
- 受入条件の `AC-n` には、リポジトリ全体の通し番号を振る（検査: CI。仕様書の `| AC-n |` で始まる表の行に、
  同じ番号が 2 つ以上あるかだけを見る）

## テスト名

- `test` の名前は日本語で、条件と結果を書く。`should` や `test1` のような名前にしない
- **受入条件を確かめるテストは、名前の先頭に受入条件の識別子を書く**（例: `AC-3 存在しない id は 404 を返す`）
  （検査: CI。仕様書の各 `AC-n` が、いずれかのテストファイルに書かれているかだけを見る）
- `test` は、`正常系` / `異常系` / `エッジケース` のどれかの `describe` に入れる。その外側を、対象の名前の
  `describe` で囲んでよい。3 つのどれにも当たらないテスト（型の検査など）は、中身を表す名前の `describe` に
  入れてよい

## 観点

1 つの対象を、次の 3 つの観点で確かめます。

| 観点         | 例                                                            |
| :----------- | :------------------------------------------------------------ |
| 正常系       | 期待どおりの入力で、期待どおりの結果と状態の変化になる        |
| 異常系       | 不正な入力、存在しない id、権限なし、他人のデータ             |
| エッジケース | 空配列、0 件、上限ちょうど、上限 +1、最大長の文字列、同時実行 |

- API のルートごとに、正常系と異常系のテストをそれぞれ 1 本以上書く
  （検査: CI。ルートごとに、そのルートを参照するテストが 1 本以上あるかだけを見る）
- エッジケースのテストは、表の例に当たる入力を対象が受け付ける場合に書く
- **正常系は、status だけを確かめて終えない。** レスポンスの本文を検証する。書き込むルートでは、DB の状態の変化も
  検証する
- **異常系は、status と `messageKey` の両方を検証する。** 文言（`message`）は検証しない

## サーバーのテスト

- **サーバーは、`app.ts` を import して `app.listen(0, '127.0.0.1')` で起動する。** リクエストは native fetch で
  HTTP として送る
- handler（`route()` に渡す関数）を直接呼ばない
- 待ち受けるアドレスは、リクエストを送る先（`127.0.0.1`）と同じにする（同梱の `startServer()` がそうしている）
- API 定義にあるルートの URL は、API 定義から組み立てる（`server.url(itemsApi.getItem, { id })`）。URL を文字列で
  手書きしない。ただし、API 定義に無いルート（`/health`）とクエリ文字列は、文字列で足してよい
- API の振る舞い（データ・権限・入力の検証）に関わる受入条件は、このテスト（HTTP 経由）で確かめる
- ヘルパーは `server/tests/helpers/` に置く。同梱のヘルパーは次の 3 つ
  - `startServer()`（`helpers/server.ts`）: テストサーバーを起動する。戻り値の `reset()` はデータを空にする。
    `close()` はサーバーを止める。`url()` は URL を組み立てる
  - `createTestDb()`（`helpers/db.ts`）: PGlite の DB を作り、マイグレーションを流す
  - `createAuthHeaders()`（`helpers/auth.ts`）: 認証済みのリクエストヘッダを作る
- 同じデータの用意を 2 つ以上のテストが書いたら、`seed<対象>()` のようなヘルパーに寄せる
- サーバーと DB は、テストファイルごとに 1 回だけ作る（`beforeAll` で `startServer()`、`afterAll` で `close()`）
- テストの DB は **PGlite**（Postgres の WASM 版）を使う。追加のインストールは要らない
- ただし、PGlite で再現できない機能（一部の拡張、ロール）を使うテストは、実 PostgreSQL に向けてよい。そのときは、
  次の 3 つを行う
  - 接続先を渡す環境変数を足す
  - `docs/env.md` に、その環境変数の名前を書く
  - PGlite では足りない理由を、テストのコメントに書く
- AI の SDK を呼ぶルートのテストは、[ai-integration.md](ai-integration.md) の「テスト」に従う
- 各テストの前に、`beforeEach` で `reset()` を呼んでデータを空にする。前のテストが残したデータに依存しない
- **利用者ごとのデータを扱うルートには、別の利用者で確かめるテストを書く。**
  `createAuthHeaders({ subject: '<別の id>' })` で、別の利用者のトークンを作る。そのトークンで、次の 2 つを確かめる
  - 他人のデータの取得・更新・削除が 404 になる
  - 一覧と件数に他人のデータが入らない

## 単体テストの例外

- **副作用が無く、DB にも HTTP にも触れないモジュール**（計算・整形など）は、直接 import して単体テストしてよい。
  入力と戻り値だけを検証する
- 単体テストを、受入条件のテストの代わりにしない
- 速さを測るテストは `*.bench.test.ts`、その場限りの確認用のテストは `*.tmp.test.ts` という名前にする
- この 2 つには、通り続けることを求めない。応答を終えるときの自動チェックは、この 2 つだけを変えたときには
  実行しない（server と shared では、ほかのソースを変えると、そのソースを読み込むこの 2 つも実行される。client では、
  どのソースを変えても全部が実行される）

## 画面のテスト

- 対象ファイルの隣に `<対象>.test.ts` を置く
- 表示される結果（DOM のテキスト、要素の有無）を検証する。内部の signal を直接読まない
- **サーバーの呼び出しは、`fetch` を差し替えて再現する。** `api-client.ts` の `call()` を差し替えない
  （手本は同梱の `items-page.component.test.ts`。サンプルの `items` を消した後は、既存の機能を手本にする）
- サーバーからデータを読み込む画面は、empty / loading / error の 3 状態をそれぞれ確かめる
- 画面に現れる受入条件（表示・操作）は、画面のテストで確かめる

## やらないこと

- テストのためだけに、実装へ分岐や公開メソッドを足さない
- 1 つの `test` で複数の機能を確かめない
- 乱数・現在の時刻・テストの実行順で結果が変わるテストを書かない。現在の時刻を使う処理は、`vi.setSystemTime()` で
  時刻を固定して確かめる
- 処理にかかる時間で結果が変わるテスト（「N ミリ秒以内に終わる」など）を書かない。時間のかかる処理は、待ち時間を
  引数で渡せる形にするか、`vi.useFakeTimers()` の偽のタイマーで確かめる
- テストが起動したサーバー（`127.0.0.1`）以外のネットワークと外部サービスに、実際にアクセスしない

## なぜ

実際に HTTP を叩くのは、middleware・検証・error middleware を含めた**本番と同じ経路**を通すためです。
handler を直接呼ぶテストは、認証を外した状態や検証を飛ばした状態でも緑になります。

待ち受けるアドレスをリクエストの送り先と同じ `127.0.0.1` にするのは、別のアプリと番号がぶつかるのを防ぐためです。
アドレスを省くと、サーバーはすべてのアドレス（`::`）で待ち受けます。このとき、別のアプリが `127.0.0.1` だけで使って
いる番号が、割り当てられることがあります（macOS で起きます）。そうなると、リクエストがそのアプリに届きます。その
結果、テストがまれにタイムアウトや 404 で落ちます。

URL を API 定義から組み立てるのは、パスを変えたときにテストも一緒に変わるようにするためです。CI の API 定義の
検査も、テストが API 定義を参照しているかを数えます。

副作用の無いモジュールを直接 import してよいのは、境界値や丸めの結果を戻り値で 1 つずつ固定できるためです。
同じ確認を HTTP 経由で書くと、リクエストを組み立てる手間が増えます。また、落ちたときに、計算と経路のどちらが原因かが
分かりません。

API の振る舞いの受入条件を HTTP 経由で確かめるのは、本番と同じ経路で確かめるためです。受入条件は、使う人から見た
振る舞いです。使う人のリクエストは、本番の経路を通ります。

画面に現れる受入条件（表示・操作）を画面のテストで確かめるのは、画面を描かないと確かめられないためです。API の
テストでは、表示や操作は確かめられません。

不具合の受入条件のテストを直す前の実装で落ちるものにするのは、不具合が戻ったときに気づけるようにするためです。
直す前の実装で落ちないテストは、不具合が戻っても落ちません。

まれに落ちるテストや、特定の環境でだけ落ちるテストの直しで、繰り返した結果を比べるのは、直ったことを示すためです。
このような直しには、直す前の実装で落ちる受入条件のテストがありません。また、1 回通っただけでは、直ったとは言えません。

文言や見た目だけの変更に受入条件を足さないのは、守るものが増えない受入条件を足さないためです。文言や見た目は、
振る舞いの約束ではありません。これを約束として数えても、受入条件の数が増えるだけです。

受入条件の番号を通し番号にするのは、1 つの番号が 1 つの条件だけを指すようにするためです。CI の検査は、番号ごとに
テストがあるかを見ます。番号が重なると、片方の条件のテストだけで、もう片方も確かめたことになります。

処理にかかる時間で結果が変わるテストを書かないのは、原因の無い失敗を混ぜないためです。処理にかかる時間は、走らせる
機械の速さや、同時に動いている処理で変わります。

DB をテストファイルごとに作り、テストの間はデータだけを空にするのは、確認を遅くしないためです。DB を作るたびに、
マイグレーションを流す時間がかかります。テストごとに作り直すと、テスト 1 件ごとにその時間がかかります。テストが
増えるほど、確認が遅くなります。データを空にすれば、DB を作り直すときと同じように、前のテストの結果に
左右されない状態を保てます。

1 つの `test` で 1 つの機能だけを確かめるのは、落ちたときに原因を絞れるようにするためです。

`messageKey` まで検証するのは、エラーの種類が変わったことに気づくためです。status だけだと、
「見つからない」が「権限がない」に変わっても 404 のままで通ってしまうことがあります。

画面のテストで `fetch` を差し替えるのは、`call()` の URL の組み立て・ヘッダ・エラー変換まで含めて
画面の振る舞いを検証するためです。`call()` ごと差し替えると、その部分が抜けたまま緑になります。
`api-client.test.ts` は、`call()` 自体の検証です。そのため、そこでも `fetch` を差し替えます。

受入条件の識別子をテスト名に入れるのは、引き継ぎのときに「この条件は確認済みか」を機械で判定できる
ようにするためです。人が一覧を作り直す作業が要らなくなります。
