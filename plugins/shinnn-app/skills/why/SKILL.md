# なぜそうなっているかを説明する

引数（`$ARGUMENTS`）に話題かファイルパスを受け取り、その決まりの理由を説明する。
**憶測で答えない。** 必ず下の根拠を読んでから答える。

## 根拠の探し方（この順に見る）

| 順 | 場所 | 何が書いてあるか |
|:--|:--|:--|
| 1 | `docs/仕様書.md` | このアプリが何をするか。**最も強い正本** |
| 2 | `docs/decisions/` | なぜその設計にしたか。設計判断の記録 |
| 3 | `.claude/rules/*.md` の `## なぜ` 節 | 規約そのものの意図 |
| 4 | `CLAUDE.md`（root / client / server） | 構成と共通方針 |
| 5 | Issue と PR（`gh issue view` / `gh pr view`） | いつ・誰が・どう決めたか |

優先順位は **仕様書 > CLAUDE.md > rules**。食い違っていたら、その食い違い自体を報告する。
どこにも根拠が無い場合は、**「根拠が見つからない」と正直に言う**。もっともらしい理由を作らない。

## 答え方

非エンジニアが読む前提で、次の 4 つを順に書く。専門用語は初出で 1 行説明を添える。

1. **一言で**: 「〜だからです」を 1 行
2. **困ること**: この決まりが無いと何が起きるか。具体例で
3. **before / after**: 実際のコードで、規約に反した書き方と沿った書き方を並べる。**このリポジトリの実物から引く**
4. **根拠**: 読んだファイルのパスと該当箇所

長さは画面 1 つに収まる程度。読み切れない説明は説明になっていない。

## 例

パスの例はサンプルの `items`（サンプルを消した後は、既存の機能のパスに読み替える）。

```
/shinnn-app:why shared に zod を置く理由
/shinnn-app:why client/src/app/features/items/items-page.component.ts
/shinnn-app:why なぜ package-lock.json を編集できないのか
```

## 規約に納得できないと言われたら

議論を打ち切らない。次のどれかに振り分けて、人に返す。

- **理由が古い**（前提が変わっている）→ `docs/decisions/` に新しい記録を足す提案として PR にする
- **この案件だけの事情**→ `CLAUDE.local.md`（git に入らない）に書く案を示す
- **標準そのものを直すべき**→ 当社に上げる項目として「引き継ぎメモ」Issue に書く
