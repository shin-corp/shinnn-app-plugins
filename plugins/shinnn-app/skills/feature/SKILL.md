# 作りたいことを形にする

作りたいことを受け取り、1 本ずつ Issue・仕様・実装・テストまで通す。
**1 Issue = 1 ブランチ = 1 PR** を崩さない。**要望を分けるのは Claude の仕事**で、利用者に分けさせない。

題が `[確認]` の open な Issue があれば、引数があってもなくても、利用者の今の依頼を返事として「10. 最初の画面を確かめてもらう」の 4 を行う
（「続きをお願い」は、このままでよいという返事に当たる。引数に直したいことが書かれていれば、10 の 4 の 1 で Issue に足す）。
open な `[確認]` は、セッションの最初の「確認待ち」に出る。出ていなければ `gh issue list --state open --label status:doing` で見る。

引数（`$ARGUMENTS`）に作りたいことが書かれていれば、それを出発点にする。
無いとき、または「続き」と言われたときは「続きから始める」に進む。続きも無ければ、作りたいことを最初に聞く。
「画面を見ながら調整したい」と頼まれたときは「9. 画面を見ながら調整する」に進む。
「後回しにした点も進めて」と頼まれたときは、open なすべての `[後回し]` の Issue（`/shinnn-app:pr` の手順 6 が作る）に `status:next` を付けて、「続きから始める」の 2 から進める。

`.shinnn/setup.json` の `mergePolicy` が `auto-merge` のときは（`setupCompletedAt` が `null` のときを除く）、規約 `git-workflow.md` の「`auto-merge` のとき」に従い、
利用者に聞かずに、進められる Issue が無くなるまで作りきる（計画で決めた、最初の画面が仕上がる位置で 1 回だけ止まる。「10. 最初の画面を確かめてもらう」）。
計画の最後には、デザインの改善案を 1 件ずつ、入れるかを聞く（「8. デザインを見直す」。作り直しでは聞かない）。
動く画面を見ながらの調整は、その後に行う。
`self-review` は、規約 `git-workflow.md` に「`auto-merge` のとき」の節があれば、`auto-merge` と同じに扱う。
このスキルから呼ぶスキル（`plan.md`・`add-screen`・`check` など）の `auto-merge` の分かれ目でも同じ。
節が無い（標準を取り込む前の）リポジトリでは、マージにかかわる分かれ目だけを `auto-merge` と同じに行う。
これに当たるのは、`pr` の手順 6 の「すべて緑」と「CI が始まっていない」の分かれ目、手順 7、手順 8 の 4 のマージと、
このスキルの手順 7 の表の「`pr` がマージまで済ませたら」の動きだけ。ほかの分かれ目（`pr` がマージせずに人に渡したときを含む）は `human` と同じに進める。

## 準備. 道具とルールの版を確かめる

このスキルを読み込んだときに確かめた結果:

!`node "${CLAUDE_PLUGIN_ROOT}/scripts/check-plugin-version.mjs"`

上に結果が出ていなければ、同じコマンドを自分で実行する。結果に応じて、作業を始める前に次を行う。

| 結果 | すること |
|:--|:--|
| プラグイン: 古い | 「更新:」の 2 つのコマンドを順に実行する。終わったら利用者に「道具を新しくしました。`/reload-plugins` と入力してから、もう一度『続きをお願いします』と伝えてください」と頼み、**ここで止まる**（新しい手順は、読み込み直すまで使われない。`/reload-plugins` は利用者にしか打てない） |
| ルール: 古い | 利用者に「ルール（決まりごと）の新しい版が届いています。`/shinnn-app:update-rules` で取り込めます」と伝えてから、頼まれた作業を進める |
| 最新、または確かめられない | そのまま進める（オフラインなどで確かめられなくても止めない） |

## 0. 大きさを見る

PR 1 本の目安は、**使う人から見て 1 つできるようになること**。変更するファイルが 10 個くらいで、レビューする人が 15 分で読める量。

| 要望 | 進め方 |
|:--|:--|
| 1 本に収まる | 1 から順に進める |
| 収まらない（できるようになることが 2 つ以上ある、など） | 同じフォルダの `plan.md` で計画を作る（`human` では利用者の確認を取る）。先頭の Issue を 2 から進める |

**文言 1 つの直しや不具合の修正も、同じ流れ（Issue → ブランチ → PR）で進める。** `main` で直接編集しない。違うのは次だけ。

- 不具合の Issue は `gh issue create --template bug.yml` で作り、ブランチは `fix/<Issue 番号>-<slug>` にする
- 受入条件の立て方（不具合の修正と、振る舞いが変わらない変更）は `.claude/rules/testing.md` の「何をテストするか」に従う。
  受入条件を足さないときは、Issue の受入条件の欄と PR 本文の「対応した受入条件」に「無し（文言だけの変更）」のように書く
- まれに落ちるテストなど、テストそのものの不具合は、直す前に `pr` の手順 1 の条件で落ちる回数を測っておく

**依存の脆弱性の勧告を直す依頼は、不具合の流れ（`bug.yml`・`fix/`）にしない。** CI の「依存の脆弱性」の失敗や注記を貼り付けた依頼も、
`npm audit` の勧告を直す依頼も、`/shinnn-app:check` の「`npm audit` で勧告が出たとき」で進める
（`main` の上で頼まれたときは、その節の「元の PR が無いとき」の順）。直しの Issue とブランチは、その節が決める。

**この道具を使わずに作ったアプリ（以下「元のアプリ」）を作り直すときも、計画から始める（`plan.md`）。** 違うのは次だけ。

- このフォルダに `.claude/rules/.standards-version` が無いときは、テンプレートから作ったフォルダではない。作り直しを始めず、
  `/shinnn-app:setup` の手順 0 の 1 の案内を伝えて止まる
- 依頼に元のアプリのフォルダの場所が無ければ聞く（「1. Issue を作る」の確認の質問の数には入れない）。
  そのフォルダはこのフォルダの外に置いたままにし、このフォルダにコピーしない。コピーすると、git・lint・CI の対象になる
- 元のアプリのフォルダを `--add-dir` で足さずに起動していると、読むときに確認が出る。そのときは `/exit` で終了し、
  `claude --add-dir <元のアプリのフォルダ>` で起動し直すよう頼む。起動し直した後は、計画を作る前なら同じ依頼を、
  作った後なら「続きをお願い」を入力してもらう
- 止まるときの報告（7）に、次も `claude --add-dir <元のアプリのフォルダ>` で起動することを添える
- 計画を作る前に、元の画面の用意のしかたを利用者に聞き、答えを待つ（「作り直しの元の画面・見た目・移植対応表」の 1）。
  元のアプリのフォルダの場所と同じく、確認の質問の数には入れない。`auto-merge` でも聞く
- 元のアプリは読むだけで、書き換えない。`--add-dir` で足したフォルダへの書き換えは、確認なしで通る。
  Edit・Write で開くのは、このフォルダの中のファイルだけにする
- 元のアプリのコードを写さない。書き方は規約と手本に従う。CLAUDE.md と規約の「既存の処理」「既存の機能」は、このフォルダの中だけを指す
- 元のアプリの `.env` で始まるファイルは、`.env.example` のほかは読まない。権限の設定が止めるのは `.env`・`.env.local`・
  `.env.production` などの決まった名前だけで、`.env.prod` のような名前は止まらない
- 元のアプリを検索するときは Grep ツールを使い、`glob` に `!**/.env*` を付けて `.env` で始まるファイルを外す。
  Bash の `grep -r` は使わない（`.env` の中身も結果に出る）
- 設定の項目の名前が要るときは、`.env.example` を Read ツールで読む（`cat` は権限の設定で止まる）。
  `.env.example` が無ければ、コードの `process.env.` の参照から拾う
- 計画は、元のアプリの画面・API・保存しているデータの形（テーブルと項目）を読んで、`plan.md` の「1. 分ける」の単位に分ける。
  データそのもの（DB のファイルや書き出したファイル）は読まない
- 計画を作るときに、元のアプリから見た目の値を取り出し、仕様書に「再現の度合い」と一緒に書く（「作り直しの元の画面・見た目・移植対応表」の 2）
- 計画の Issue を作ったら、`docs/移植対応表.md` を作る（同じ節の 3）。作り直しの完成は、この表の「まだ」が 0 件になったとき
- 受入条件は、元のアプリの今の振る舞いから立てる。規約に従うと振る舞いが変わる点（認可が無かった操作など）は、
  規約に従う側で仮置きし、元のアプリとの違いを移植対応表のその行の「違い」に書く（Issue の「未決」には書かない）
- `docs/仕様書.md` の「目的」と「使う人と場面」は、計画を作るときに、元のアプリの画面・文言・文書から推測して書く
  （分からないところの書き方は規約 `client-styling.md` の「デザインの指導」）。この変更は、`plan.md` の 3 の 5 と同じく先頭の Issue の PR に入れる
- 本番のデータの移し替えと、新しいアプリへの切り替え（公開先・URL・利用者への周知）は、計画の「今回やらないこと」に書く。
  この 2 つは「あとで足せます」とは伝えず、シン株式会社の担当者に相談するよう、利用者に伝える

## 1. Issue を作る

- **確認の質問は 3 つまで。** 分からないことは仮置きし、Issue の「未決」に書く（質問を重ねて止めない）。`auto-merge` では質問しない
- 聞くなら、この 3 つから選ぶ: 何のためか / 誰が使うか / 保存するデータは何か
- `gh issue create --template feature.yml` で作る。本文には次を必ず入れる

| 見出し | 内容 |
|:--|:--|
| 目的 | 何が嬉しいのかを 1〜2 行 |
| 画面 | 追加・変更する画面と、そこでできること |
| データ | 保存する項目と、その意味。**誰が見られて誰が変えられるか**（利用者ごと / 全員で共有 / 管理者だけが変える、など） |
| 受入条件 | `AC-n` の番号を振る。**1 行 = 1 つの確認できる事実**として書く。利用者ごとのデータなら「他の利用者のデータは見えず、変えられない」を 1 つ入れる |
| 未決 | 仮置きした点。人に確認してから決めること |

受入条件の番号は、`docs/仕様書.md` と open な Issue で**使われている最大の番号の続き**から振る（決まりは `.claude/rules/testing.md` の「何をテストするか」）。
受入条件ごとに「この AC に対応するテストがあるか」を、あとで CI が機械的に確かめる。
**測れない書き方（「使いやすいこと」など）をしない。**

計画から進めるときは、Issue は `plan.md` で作ってあるので 2 に進む。

## 2. 仕様書に反映する

Issue の `AC-n` が、仕様書やほかの open な Issue で使っている番号と重なることがある（人がフォームで立てた Issue は `AC-1` から振ってある）。そのときは、仕様書に追記する前に、使われている最大の番号の続きに振り直す。Issue の本文も同じ番号に直す。
`docs/仕様書.md` の該当章に、Issue と同じ内容を追記する。追記した後は、仕様書を正とする（ルートの `CLAUDE.md` の優先順位。CI の受入条件の検査も仕様書を見る）。Issue は作業の単位として扱う。
**着手する Issue の分だけ**入れる。計画にある他の Issue の受入条件を先に入れると、テストがまだ無いので CI（`check-ac-coverage`）が落ちる。
依頼に、どんな人がどのように使うかが書いてあれば、「見た目の方針」の「使う人と場面」にも書く。
既存の記述と食い違う場合は、**書き換えずに人へ報告する**（仕様書の版は人が管理する）。
`auto-merge` では止まらず、仕様書のとおりに作る。食い違いは Issue の「未決」に書く。

## 3. ブランチを作る

```
git fetch origin main
git switch -c feature/<Issue 番号>-<英小文字の短い slug> origin/main   # 不具合の修正は fix/<Issue 番号>-<slug>
gh issue edit <Issue 番号> --remove-label status:next --add-label status:doing
```

例: `feature/12-item-archive`

**ブランチは必ず `origin/main` から切る。** マージされていない別の PR のブランチから切らない。
前の PR が要る Issue は、そのマージを待つ。

## 4. 実装する（この順を守る）

| 順 | 場所 | やること |
|:--|:--|:--|
| 1 | `shared/src/api/` | API 定義。**データの形の唯一の正** |
| 2 | `server/src/db/schema/` | テーブルを足すなら先にスキーマ（`/shinnn-app:db-migrate`） |
| 3 | `server/src/service/` | 業務処理 |
| 4 | `server/src/api/<機能>/` | router と controller |
| 5 | `client/src/app/features/<機能>/` | 画面 |
| 6 | `server/tests/` と画面の `.test.ts` | 受入条件 `AC-n` ごとにテスト。API の振る舞いはサーバー、画面に現れることは画面のテスト（`.claude/rules/testing.md`） |

**参照される側を先に書く。** shared を変えずに server や client だけ直したくなったら、それは API 定義の考え漏れなので shared に戻る。

応答を終えるたびに、触ったファイルの lint と関連テストを hook が走らせる。各段階では、その結果を直してから次へ進む
（全部書いてからまとめて直さない）。段階ごとに `/shinnn-app:check` をまとめて走らせない（`pr` が出す前に 1 回通す）。
1〜4 とサーバーのテストは `/shinnn-app:add-api`、5 と画面のテストは `/shinnn-app:add-screen` の手順で進める。
アプリ全体の見た目（配色・書体・画面の骨組み）を変えるときは `add-screen` の「0. 見た目の方針を確かめる」から、
今ある画面の見た目だけを変えるときは `add-screen` の「3. 画面の案」と「7. スタイル」で進め、書いた後に「9. 作った画面を見直す」を行う。
機能を足して今ある画面の項目・操作・状態が増えるときも、コードを書く前に `add-screen` の「3. 画面の案」を、書いた後に「9. 作った画面を見直す」を行う。
題が `[デザイン]` の Issue（`/shinnn-app:design-review` で利用者が入れると決めた改善案）は、本文の「変えること」のとおりに作る。
「変えること」が見た目の方針を変えるものなら `add-screen` の「0. 見た目の方針を確かめる」から、ほかは今ある画面の見た目だけを変えるときと同じに進める。
受入条件があれば（振る舞いが変わる改善案）、ほかの Issue と同じに 2 で仕様書に足し、テストにする。
受入条件が「無し（見た目の調整）」なら、PR 本文の「対応した受入条件」にも「無し（見た目の調整）」と書く。
守る決まりは、それぞれが名指しする規約にある。

### ライブラリを探す

汎用の処理（規約 `libraries.md` の「探して使う」）を書く前に、次の順で探す。
使ってよいものの条件と、使わないときに理由を残す形は、同じ規約の「入れる条件」と「使わないとき」にある。

1. 標準の機能（規約の「探して使う」）がその処理を備えているかを確かめる。備えていれば、それで書いて終える
2. 既に入っている依存がその処理を備えているかを確かめる。ルートと各パッケージの `package.json` の `dependencies` と `devDependencies` を読む。備えていれば、それで書いて終える。ただし、ほかのパッケージにだけ入っているときは、規約の「入れる条件」のとおり、同じ版を使うパッケージに入れてから書く
3. npm で探す。処理を表す英語の語で `npm search <語> <語>` を実行し（例: CSV を読むなら `npm search csv parse`）、説明が処理に合う候補を選ぶ
4. 候補ごとに `npm view <名前> license version deprecated` を実行する。続けて `npm view <名前> "time[<version の値>]"` を実行し、最後の版を出した日を見る。
   それぞれを規約の「入れる条件」に照らして、合わない候補を外す（`deprecated` は、値が出れば非推奨。`license` が `(MIT OR Apache-2.0)` のような式なら、`OR` はどれか 1 つ、`AND` はすべてが許可リストにあるかを見る）。要る機能を備えていない候補も外す
5. 残った候補の週ごとのダウンロード数を、WebFetch で `https://api.npmjs.org/downloads/point/last-week/<名前>` から読む（`@` で始まらない名前は、カンマでつないで 1 回で読める）
6. 規約の「入れる条件」のとおりに 1 つ選んで入れる
7. `node scripts/check-licenses.mjs` を実行する（入れたものが持ち込んだ依存のライセンスも見る）。落ちたら `npm uninstall <名前> -w <パッケージ>` で外し、6 に戻って残った候補から選ぶ。通れば、入れたものを使って書く
8. 残った候補が無ければ自前で書き、JSDoc に理由の行を書く（形は規約の「使わないとき」）

## 5. コミットする

`.claude/rules/git-workflow.md` の「コミットメッセージ」「コミットの分け方」を読み直してから、それに従ってコミットする。

## 6. 仕上げ

```
/shinnn-app:pr
```

`pr` が手順 1 で `check` を通し、最後に `retro` で振り返りまで残す。どれも利用者に打たせず、ここで続けて行う。
計画の Issue か、題が `[デザイン]` の Issue か、利用者に頼まれて `status:next` を付けた `[後回し]` の Issue なら、続けて 7 に進む。ほかの計画の無い 1 本なら、`/shinnn-app:session-retro` を 1 回行ってから、7 の形で報告して終える。
ただし、`check` の「`npm audit` で勧告が出たとき」で直しの Issue（題が `[依存] 依存の脆弱性の修正`）を作ったか見つけ、
それが `status:next` のときは、終える前にその Issue を、`check` の同じ節の 2 の 5 で進める（計画の Issue でも、7 で次の Issue より先に進める）。
進めてよいかを利用者に聞かない。直しは、頼まれた作業の続きとして行う。依頼の範囲を広げることには当たらない。
利用者への報告は、直しの PR まで出してから 1 回にまとめる。

## 7. 次の Issue へ進む（計画があるとき）

題が `[デザイン]` の Issue（`/shinnn-app:design-review` で利用者が入れると決めた改善案）と、利用者に頼まれて `status:next` を付けた `[後回し]` の Issue も、6 から 7 に進むことと、次の Issue の選び方は、計画の Issue と同じに扱う。

PR を出したあとの動きは `.shinnn/setup.json` の `mergePolicy` で決まる（キーが無いとき、または `setupCompletedAt` が `null` のときは `human` として扱う）。

| `mergePolicy` | PR を出したあと |
|:--|:--|
| `human` | PR はドラフトのまま人に渡す。**今の PR を待たずに作れる** `status:next` の Issue があれば、それを 2 から進める |
| `auto-merge` | `pr` がマージまで済ませたら、`git switch main` を実行し、成功したら `git pull --ff-only` を実行する。失敗したら、次に進まずに報告する。成功したら、「10. 最初の画面を確かめてもらう」に当たるかを見る。当たれば 10 を行う（10 の 3 で止まる）。当たらなければ `plan.md` の「依存が解けた Issue を進める」を行い、`status:next` の先頭を 2 から進める。`pr` がマージせずに人に渡したときは、下の「Issue を止める」を行う |

どちらでも、次の Issue を選ぶ前に「続きから始める」の 1 の後半（待っている PR への `main` の取り込み）を行う。
次の Issue は「続きから始める」の 4 の順で選ぶ（題が `[依存] 依存の脆弱性の修正` の Issue を先に取る）。

### Issue を止める（`auto-merge`）

規約 `git-workflow.md` の「`auto-merge` のとき」の `status:blocked` にする条件に当たったら、実装の途中でも次を順に行う。

1. PR がまだ無ければ、ここまでの変更を手順 5 の決まりでコミットし、push する。
   続けて、`pr` の手順 3 の形でドラフト PR を作る。本文の「規約で迷った点」には、止めた理由と、人に決めてほしいことを書く
2. Issue を `status:blocked` にする（`gh issue edit <番号> --remove-label status:doing --add-label status:blocked`）
3. Issue に、止めた理由と、人に決めてほしいことをコメントする
4. `git switch main` を実行し、成功したら `git pull --ff-only` を実行する。失敗したら、次に進まずに報告する。
   成功したら、止めた Issue に印（`plan.md` の「1. 分ける」の「確かめてもらう位置」）が付いていれば、「10. 最初の画面を確かめてもらう」を行う（10 の 3 で止まる）。
   付いていなければ、進められる別の Issue に移る

ドラフト PR にするのは、止めた作業を人が見つけられるようにするため。
コミットして push しておくと、止めた変更が次の Issue のブランチに混ざらない。

### 止まるとき

次のときは止まる。

- 進められる `status:next` の Issue が無い（計画が終わった、または残りが PR のマージ待ち）
- 実装の途中で仕様の穴が見つかり、人に返した
- `pr` のレビューが収束しない（`pr` の手順 2 で直しきれず、PR を作って人に渡した）、または CI が直らない

ただし、`auto-merge` で止まるのは 1 つ目だけ（コミットが lint-staged の退避で止まったときに、利用者にアプリを閉じてもらうのを待つことを除く。規約 `git-workflow.md` の「`auto-merge` のとき」）。同じ節が止まる・止まってよいとしているとき（利用者が止めるよう伝えたとき、10 で最初の画面を確かめてもらうときなど）も止まる。仕様の穴は仮置きして進める。レビューと CI で進めない Issue は、「Issue を止める」を行って別の Issue に移る。

1 つ目の理由（進められる Issue が無い）で止まるときは、報告の前に次を順に行う。

1. 「8. デザインを見直す」でいう「この計画」（「作る順番」の Issue がすべて閉じた計画）があれば、8 を行う
2. `/shinnn-app:session-retro` を 1 回行い、このセッションで出した PR の振り返りを、次から役立つ形に置き直す（PR ごとには行わない）
3. `auto-merge` で画面があれば、`/shinnn-app:dev-stack-start` で起動する

止まるときは、次を**利用者の言葉で**報告する。

- できたこと（PR の番号と、使う人から見て何ができるようになるか）
- 待っていること（誰が何をすれば続きを作れるか。例: 「PR #14 を取り込んでもらえれば、在庫の一覧を作れます」）
- 次に「続きをお願い」と言われたら着手する Issue
- `auto-merge` では、仮に決めたことの一覧と、`status:blocked` にした Issue とその理由。
  止めた Issue は、人が決めた内容を伝えてもらえれば、続きから進められること
- `auto-merge` では、レビューで見送った指摘と、後回しにした点をまとめた `[後回し]` の Issue の番号と件数（`pr` の手順 6 の報告の中身）。
  `[後回し]` の Issue には、利用者に頼まれるまで着手しないこと。「後回しにした点も進めて」と伝えれば作ること（冒頭の振り分け）
- 作り直しでは、移植対応表の「まだ」の件数と全体の件数（例: 「まだ 0 件 / 全 12 件」）と、「違う」にした行があること（表の場所を添える）
- 作り直しでは、元の画像が無かった画面の一覧（移植対応表の「元の画像」が `無` の画面の行のうち、状態が `済み` か `違う` のもの）。その画面は元のアプリのコードから作ったので、最後の調整（「9. 画面を見ながら調整する」）で確かめてほしいこと
- 8 でデザインを見直したときは、入れた改善案と入れなかった改善案の数と、記録の Issue（`[調整] デザインの見直し`）の番号。`design-review` が `.gitignore` に `/screenshots/` の行を足してコミットせずに残したときは、そのこと
- 作り直しで、8 ですべての画面を元と並べて撮ったときは、並べた画像の置き場所（`screenshots/compare/`）と、最後の調整（「9. 画面を見ながら調整する」）で元と見比べてほしいこと
- `frontend-design` が無くて、方針を決める指導か 8 のデザインの見直しを行えなかったときは、そのことと、入れて起動し直せば `/shinnn-app:design-review` で見直せること（`add-screen` の「`frontend-design` が無いとき」）
- `auto-merge` で起動したときは、画面の開き方（通行証の入れ方は `README.md` の「画面から API を呼ぶための通行証（開発中）」）と、画面を見ながら直したいところを伝えてほしいこと

## 8. デザインを見直す

この節と「止まるとき」の 1 でいう「この計画」は、題が `[計画]` の Issue のうち、「作る順番」の Issue がすべて閉じているもの（親が open でも closed でも）で、
子 Issue が最後に閉じたのがいちばん新しいものを指す。この計画について、1 回だけ行う。

次のときは行わない。

- 画面が無いアプリ
- この計画が無い（計画の無い 1 本だけを作ってきたときを含む）
- この計画の `[調整] デザインの見直し`（本文の先頭が `計画: #<親の番号>` の Issue）が閉じている
- この計画の `[調整] すべての画面の見直し` がある（この計画のすべての画面は見直し済み）

仕様書の「見た目の方針」の「再現の度合い」が「元に寄せる」のアプリでは、下の「作り直しのとき」を行い、`design-review` を呼ばない（規約 `client-styling.md` の「デザインの指導」）。

ほかのアプリでは、Skill ツールで `shinnn-app:design-review` を呼ぶ。`args` には、この計画の親 Issue の番号を `計画: #<親の番号>` の形で渡す。
この計画の `[調整] デザインの見直し` が open なら、入れるかを聞き終えていない改善案がある。同じく `design-review` を呼び、続きから聞いてもらう。

`design-review` を終えたら、入れた Issue（`status:next` を付けた `[デザイン]` の Issue）があれば、「続きから始める」の 2 から作る。
無ければ、7 の「止まるとき」の、報告の前に行う 2 に進む。

### 作り直しのとき

すべての画面を元と並べて撮る。撮った画像を見て直すことはしない（画面ごとの見直しは `add-screen` の「作り直しのとき」で済んでいる）。
並べた画像は、最後の調整（「9. 画面を見ながら調整する」）で利用者が見比べる。

1. この計画の親 Issue のコメントに `すべての画面を元と並べて撮った（screenshots/compare/）` があれば、この計画では撮ってある。撮らずに 5 に進む
2. `/shinnn-app:dev-stack-start` で起動する。移植対応表の画面の行から、画面の一覧を JSON で、Write ツールで scratchpad に書く。
   name は `add-screen` の 9 で使った画面の名前にする。元の画像がある画面は、`original` に `screenshots/original/<元の画面の画像>` を書く
3. まとめて撮る。`--token` とブラウザの扱いは、`add-screen` の「9. 作った画面を見直す」の 1 と同じ

   ```
   node ${CLAUDE_PLUGIN_ROOT}/scripts/capture-screens.mjs batch --list <一覧のファイル> --out-dir screenshots --token
   ```

   一覧の形: `[{ "name": "items", "url": "<画面の URL>", "original": "screenshots/original/<元の画面の画像>" }]`。
   撮った画像は `screenshots/<name>.png` に、元と並べた画像は `screenshots/compare/<name>.png` に書かれる（元の画像が無い画面は、並べた画像を作らない）
4. この計画の親 Issue に、計画ごとに 1 回の印としてコメントする

   ```
   gh issue comment <親の番号> --body "すべての画面を元と並べて撮った（screenshots/compare/）"
   ```

5. 7 の「止まるとき」の、報告の前に行う 2 に進む。報告には、並べた画像の置き場所を添える

撮れない（ブラウザが無い、サーバーを起動できない）ときは、4 の印を付けずに 5 に進む。報告には、撮れなかったことを書く。

## 9. 画面を見ながら調整する

作りきった後や、利用者が画面を見ながら直したいと頼んだときに行う。

1. 題が `[調整] 画面の調整` の open な Issue があれば、それを使う。無ければ作る（ラベルは `type:feature` と `status:doing`）。
   ブランチは `feature/<Issue 番号>-ui-adjust`（`origin/main` から切る）
2. `/shinnn-app:dev-stack-start` で起動し、画面の開き方を伝える
3. 依頼を受けるたびに直して、コミットする。見た目の方針を変えたいという依頼なら、先に `add-screen` の「0. 見た目の方針を確かめる」で指導を受ける（規約 `client-styling.md` の「デザインの指導」）。
   作った画面の見直し（`add-screen` の 9）は行わない（同じ規約のただし書きで、しなくてよいとしている）。PR 本文の「確認した結果」には、利用者が画面で確かめたことを書く
4. 直したら、画面を読み込み直して見てもらう
5. 依頼ごとに PR にしない。利用者が「ここまで」と伝えたら、`/shinnn-app:pr` に進む（`auto-merge` ならマージまで進む）
6. 受入条件を変える依頼と、新しい機能の依頼は、「途中で要望が増えたとき」に従う

## 10. 最初の画面を確かめてもらう（`auto-merge`）

規約 `git-workflow.md` の「`auto-merge` のとき」の、計画の最初の画面で 1 回だけ止まる決まりの手順。
`human` では行わない（計画のときに確かめ、PR ごとに人がマージする）。

次のときに行う。

- 親 Issue の「作る順番」で、印 `（ここまで作ったら、利用者に確かめてもらう）` を付けた Issue の PR がマージ済みである（印の位置は `plan.md` の「1. 分ける」で決める）
- この計画の `[確認] 最初の画面の確認` が、まだ無い（open でも closed でも、あれば行わない）

印の無い `auto-merge` の計画（印を付ける前に作った計画、`human` で作って後から `auto-merge` にした計画）では、10 に当たるかを見る前に、`plan.md` の「1. 分ける」の決め方で、親 Issue の「作る順番」に印を付ける。
印を付けた Issue が既にマージ済みなら、そのまま 10 に当たる。

印を付けた Issue を `status:blocked` にした（「Issue を止める」）ときは、その時点で 10 を行う。
作れたところまでを見てもらい、3 の報告に止めた理由も入れる。

当たるかは、手順 7 の `auto-merge` の行（マージの後）と、「続きから始める」の 3 の後と、「Issue を止める」の 4 で見る。

1. 画面を撮る。`/shinnn-app:dev-stack-start` で起動し、`add-screen` の「9. 作った画面を見直す」の 1 の形で、作った画面を `screenshots/` に撮る。
   作り直しでは、元の画像がある画面だけ、元と新を並べた画像も作る（`add-screen` の「作り直しのとき」）。画面が無いときは撮らない。
   撮れない（ブラウザが無い、スクリプトが止まる）ときは、撮らずに 2 に進み、3 では画面の開き方だけを伝える
2. Issue を作る。題は `[確認] 最初の画面の確認`、ラベルは `type:feature` と `status:doing`、本文の先頭に `計画: #<親の番号>` を書く。本文には次を書く
   - 計画の一覧（親 Issue の「作る順番」と「今回やらないこと」）。作り直しでは、移植対応表の場所と、「まだ」の件数と全体の件数
   - 撮った画像の置き場所。リポジトリからの相対パスで書く（絶対パスには利用者の名前が入りうる）。
     例: 並べた画像は `screenshots/compare/<画面の名前>.png`、元の画像が無い画面は `screenshots/<画面の名前>.png`。
     画面が無いときは、代わりに、できたこと（使う人から見て何ができるようになったか）と、その確かめ方を書く
   - 確かめてほしいこと（配置・色・項目・言葉）。作り直しでは、移植対応表の「違う」の行と「違い」の列も見てほしいこと（表の場所を添える）
   - 作り直しで、見せる画面に元の画像が無ければ、そのことと、元のアプリのコードから作ったこと
3. 利用者に、2 の中身を利用者の言葉で報告して止まる。報告には、画面の開き方と、次の 2 つを添える（画面が無いときは、画面の開き方は添えない）
   - 直したいところがあれば伝えてほしいこと
   - このままでよければ「続きをお願いします」と伝えてほしいこと
4. 返事を受けたら、次を順に行う
   1. 直したいことがあれば、計画の中の Issue に足すか、`plan.md` の「計画に足す」で Issue にする。作り直しでは、移植対応表の行も直す
   2. 返事の要点を `[確認]` の Issue にコメントして閉じる（`gh issue close <番号> --comment "<要点>"`）
   3. 「続きから始める」の 1 の後半（待っている PR への `main` の取り込み）から続け、進められる Issue が無くなるまで作りきる

## 作り直しの元の画面・見た目・移植対応表

元のアプリを作り直すとき（0 の作り直しの節）に行う。

### 1. 元の画面を用意する

計画を作る前に、次を順に行う。

1. 元のアプリのコード（ルート・画面の部品・テンプレートなど）を読み、画面の一覧を作る。この一覧は、「3. 移植対応表を作る」の画面の行の元にもなる
2. 画面の一覧と、画面ごとに付けてほしいファイルの名前（例: `商品一覧.png`）を示して、用意のしかたを聞き、答えを待つ。選んでもらうのは下の表の 2 つ。
   聞くときは、撮れない画面は飛ばしてよいことと、飛ばした画面は元のアプリのコードから作って最後に確かめてもらうことも伝える
3. (a) を選ばれたら、利用者に一覧の画面を撮って置いてもらい、置き終えたら伝えてもらう。撮れない画面（管理者だけの画面など）は飛ばしてよい。
   伝えられたら、置かれたファイルを一覧と照らす。名前が合わないファイルと、無い画面は、計画の知らせ（`plan.md` の 2）で示す（待たない）。そのうえで計画に進む
4. (b) を選ばれたら、下の形で撮る。撮った画像を Read で開いて確かめる（スクリプトは、ログインの画面に飛ばされても撮れたことにする）。
   ログインの画面か、頼んだのと別の画面が写っていれば、撮れなかった画面に入れる。
   撮れなかった画面は、同じ待ちの中で一覧にして示し、(a) で補うか、飛ばすかを選んでもらう。(a) で補うときは、3 と同じく置き終えるまで待つ

| 選択肢 | 用意のしかた |
|:--|:--|
| (a) 利用者が撮って置く | 利用者が元のアプリの画面を撮り、このフォルダの `screenshots/original/` に、示したファイルの名前で置く。PNG と JPEG を受け付ける |
| (b) Claude が URL から撮る | ログインの要らない画面か、テスト用のデータで動いている元のアプリの URL を受け取り、下の形で撮る |

- 聞くときは、撮った画面には本物のデータが写りうるので、`screenshots/` は git に入れないことを添える
- `.gitignore` に `/screenshots/` の行が無ければ、聞く前に足す（足した変更は、計画の先頭の Issue の PR に入れる）
- Claude はログインのパスワードを入れない。(b) でログインが要る画面は、4 のとおり (a) で補うか飛ばしてもらう
- 元のアプリを手元で起動して撮らない（元のアプリは読むだけにする）
- 元の画像が無い画面（飛ばした画面）も、止めずに作る（作り方は `add-screen` の「作り直しのとき」）。
  その画面は、移植対応表の「元の画像」を `無` にし、最後の報告（手順 7 の「止まるとき」）で確かめてもらう

(b) の撮り方: 一覧のファイル（JSON）を scratchpad に書き、まとめて撮る。`--token` は付けない（通行証はこのアプリのもの）。

```
node ${CLAUDE_PLUGIN_ROOT}/scripts/capture-screens.mjs batch --list <一覧のファイル> --out-dir screenshots/original
```

一覧の形: `[{ "name": "商品一覧", "url": "<元の画面の URL>" }]`。name には、2 で示したファイルの名前（拡張子を除く）を使う。撮れなかった画面は、4 のとおり示す。

### 2. 元のアプリから見た目を取り出す

計画を作るときに、元のアプリの CSS・テンプレート（HTML など）と元の画面の画像から、次を取り出す。
読み方は、0 の作り直しの節の決まり（Grep ツールで `.env` を外すなど）に従う。

- 主な色（見出しの帯・ボタン・リンク・背景・文字・強調）
- 書体（`font-family` の並び）
- 余白・角丸・文字の大きさ

取り出した値は、`docs/仕様書.md` の「見た目の方針」に書く。この変更は、計画の先頭の Issue の PR に入れる。

- 「再現の度合い」に「元に寄せる」と書く（振る舞いは元と同じにし、見た目は元に寄せる、という意味）。行が無ければ、「使う人と場面」の次に足す
- 「配色」に、テーマの生成に渡す色と、元のどこの色かを書く（例: 主色 `#1565c0`（元の見出しの帯））
- 「書体」に、元の書体の並びを書く
- 「画面の骨組み」に、元の余白・角丸・文字の大きさと、画面の並べ方（上の帯・左のメニューなど）を書く

この値でテーマを作るのは、最初の画面の `add-screen` の「作り直しのとき」の 0 の行。

### 3. 移植対応表を作る

`plan.md` の 3 で Issue を作ったら、`docs/移植対応表.md` を作る。この変更は、計画の先頭の Issue の PR に入れる。
仕様書とは別のファイルにする（受入条件の検査は仕様書の中の `AC-n` を数えるので、表を仕様書に入れない）。

```markdown
# 移植対応表

元のアプリの画面と機能を 1 行ずつ書き、作り直しの進み具合を数える表です。完成は、「状態」の「まだ」が 0 件になったときです。

| 元の画面・機能 | 元の場所 | 元の画像 | 状態 | Issue | 違い |
| :-- | :-- | :-- | :-- | :-- | :-- |
| 備品の一覧 | `public/index.html`（`/`） | 有 | まだ | #12 | |
| 備品の登録 | `public/new.html`（`/new`） | 無 | まだ | #13 | |
```

| 列 | 書くこと |
|:--|:--|
| 元の画面・機能 | 元のアプリの画面と、画面の中の機能（登録・検索・印刷・書き出しなど）。1 行に 1 つ |
| 元の場所 | 元のアプリのフォルダの中のファイルのパスと、画面のパス（URL のホストより後ろ）。元のアプリのフォルダそのものの場所（ドライブや利用者の名前を含むパス）は書かない |
| 元の画像 | `screenshots/original/` に元の画面の画像があれば `有`、無ければ `無`。画面の中の機能の行は、その画面と同じにする |
| 状態 | `済み`（元と同じに作った）・`違う`（違う形で作った）・`まだ`・`やらない` のどれか。表を作るときは、`plan.md` の 2 の確認で利用者が外したものを `やらない`、ほかを `まだ` にする |
| Issue | その行を作る Issue の番号。受入条件の番号（`AC-n`）は書かない（受入条件は仕様書の 6 にある） |
| 違い | `違う` と `やらない` の理由。`まだ` の行でも、違いになると分かった点は書いておく |

- 元のアプリの画面と機能は、すべて行にする。どの行も、計画のどれかの Issue に結ぶ（`やらない` の行を除く）
- 各 Issue の PR で、その Issue の行の状態を `済み` か `違う` に直す
- 規約に従うと振る舞いが変わる点（認可が無かった操作など）と、元の作りがこのテンプレートで作れない点は、`違う` にする
- `/shinnn-app:design-review` で利用者が入れると決めた改善案（`[デザイン]` の Issue）で変えた点も、`違う` にする
- `やらない` は、利用者が決めたときだけにする（`[確認]` への返事や、作業の途中で利用者が伝えたときを含む）。Claude は `やらない` を決めない
- 元のアプリとの違いは、この表にだけ書く。Issue の「未決」・PR 本文の「規約で迷った点」・引き継ぎメモには書かない
- 作り直しの完成は、「まだ」が 0 件になったとき。セッションの最初に、`session-start` が件数を出す

## 途中で要望が増えたとき

作業中に別の要望を言われたら、**今のブランチに混ぜない。** `plan.md` の「計画に足す」で Issue にし、今の Issue を最後まで進める。
今の Issue の受入条件を変える話なら、勝手に変えず利用者に確認し、決まったら Issue と仕様書を直す。

## 続きから始める

0. **Issue に紐づかない変更**が手元にあれば、先にそれを流れに乗せる。`main` の上に未コミットの変更か `origin/main` より先のコミットがある、
   または今のブランチの名前が `feature/<番号>-`・`fix/<番号>-` で始まらないときがこれに当たる。
   ただし、`main` の上の未コミットの変更が `.gitignore` に足した `/screenshots/` の行だけで、`status:next` の `[デザイン]` の Issue があるか、
   open な記録の Issue `[調整] デザインの見直し` があるときは、0 を行わない（その行は、最初に作る `[デザイン]` の Issue のブランチに持ち越す。
   `design-review` の「1. 材料をそろえる」の 4）
   1. その変更の Issue を手順 1 で作る。振る舞いが変わる変更なら、手順 2 で受入条件を仕様書に足す
   2. `git switch -c feature/<Issue 番号>-<slug>`（不具合の修正は `fix/`）で作業ブランチを作る（未コミットの変更もコミットも、そのまま移る）。
      未コミットの変更があれば、ここで手順 5 の決まりでコミットする（3 の切り替えで衝突しないように）
   3. `main` にコミットがあったときは、`git switch -C main origin/main` で手元の `main` を `origin/main` に戻し、
      作業ブランチに `git switch` で戻る。コミットは作業ブランチに残るので、`git reset --hard` と違って何も失わない
   4. 手順 4 以降（残りの実装とテスト、コミット、`pr`）を進める
1. 作業途中のブランチ（`git status` に変更がある、または PR の無い `feature/`・`fix/` ブランチ）があれば、その Issue を先に仕上げる。
   ただし、Issue が `status:blocked` のブランチは除く（人の判断を待っている）。
   ただし、その Issue の題が `[設定] 初回セットアップの適用` なら、このスキルでは進めず、`/shinnn-app:setup` を実行する。
   open な PR の本文に `依存の脆弱性: NG（… #<番号> で直す）` の行があり、#<番号> の Issue が閉じていれば、その PR に `main` を取り込む
   （`check` の「`npm audit` で勧告が出たとき」の 2 の 4）
2. `git switch main` を実行し、成功したら `git pull --ff-only` を実行する。失敗したら、次に進まずに報告する
3. `plan.md` の「依存が解けた Issue を進める」を行う。`auto-merge` で「10. 最初の画面を確かめてもらう」に当たれば、ここで 10 を行う（10 の 3 で止まる）
4. 題が `[依存] 依存の脆弱性の修正` の `status:next` の Issue があれば、計画や番号の順より先に取る（`check` の「`npm audit` で勧告が出たとき」の 2 の 5 で進める）。
   無ければ、open な計画（タイトルが `[計画]` の Issue）の「作る順番」で `status:next` の先頭を取る。計画の「作る順番」に `status:next` が無ければ（計画が無いときを含む）、`status:next` の Issue を番号の小さい順に取る
5. 取った Issue を 2 から進める（直しの Issue は 4 のとおり）。取れる Issue が無ければ、7 の「止まるとき」のとおりに進めて報告する

### 止めた Issue を再開する

利用者が、止めた Issue（`status:blocked`）について決めた内容を伝えたら、次を順に行う。

1. 決まった内容を Issue にコメントする
2. ラベルを替える（`gh issue edit <番号> --remove-label status:blocked --add-label status:doing`）
3. その Issue のブランチに `git switch` で戻る
4. PR 本文の「規約で迷った点」から、決まった項目を消す（`gh pr edit <PR 番号> --body-file <本文のパス>`）
5. このスキルの「4. 実装する」から続ける。PR は既にあるので、`pr` の手順 3 では push だけを行う

## 迷ったとき

- 規約の理由が分からない: `/shinnn-app:why <話題>`
- 実装の途中で大きすぎると分かった: 残りを Issue に切り出して計画に足す（`plan.md`）
- 片方だけでは動かず分けられない変更: 実装の前に、決めたことと理由を Issue に書き、PR 本文にも載せる。あとの判断に役立つものは `docs/decisions/` に残す
- 実装の途中で仕様の穴が見つかった: **勝手に決めず**、Issue にコメントして人に返す。ただし、`auto-merge` では仮置きして進め、Issue の「未決」に書く
