# ライブラリの規約（規約 `libraries.md`）の理由

探さずに自前で書いてよいものを、このアプリに固有の処理に限るのは、線引きを判断しやすくするためです。
固有の処理は、どのライブラリにもありません。

組み込みの機能を組み合わせて書いた処理を自前で書いたものとするのは、探す手順と理由の行を飛ばす抜け道を作らないためです。
CSV の分割も、`split` と正規表現だけで書けてしまいます。

汎用の処理をライブラリで済ませる（決まりはルートの `CLAUDE.md` の「車輪の再発明をしない」）理由は 2 つあります。
1 つ目は、細かい場合の扱いを誤らないためです。
汎用の処理には、見落としやすい場合が多くあります（CSV の引用符の中の改行、日付の月末とうるう年など）。
広く使われているライブラリは、多くのアプリでそうした場合に当たり、直されてきています。
2 つ目は、自分たちで直すコードを減らすためです。
自前のコードの不具合と脆弱性は、自分たちで見つけて直すほかありません。
ライブラリの脆弱性は、Dependabot と `npm audit` が知らせます。

標準の機能と既に入っている依存を先に使うのは、依存を増やさないためです。
依存が増えるほど、更新と脆弱性の確かめの手間が増えます。

ライブラリを import するパッケージに入れるのは、パッケージを単体で配布したときに落ちないようにするためです。
ワークスペースでは、ほかのパッケージのライブラリも同じ `node_modules` に並びます。
そのため、`package.json` に書き忘れても、手元では動いてしまいます。
`devDependencies` を読んでよいファイルだけで使うものを `devDependencies` に入れてよいのは、本番で使わないものを、本番の環境に入れないためです。
import せずに読み込まれるものをルートに入れる理由は、`docs/decisions/0002-package-manager.md` の「テストの画面の環境（jsdom）はルートで宣言する」にあります。
リポジトリ全体で使う道具をルートに入れるのは、どのパッケージにも属さないからです。
ほかのパッケージと同じ版を入れるのは、同じ書き方が片方のパッケージでだけ通る状態を避けるためです。

入れる条件を決めておくのは、誰にも聞かずに入れても困らないようにするためです。
利用者はエンジニアではないので、ライブラリの良し悪しを判断できません。
ライセンスを許可リストに限るのは、費用や義務が生じるライセンスを、聞かずに入れないためです。
許可リストに無いライセンスは、シン株式会社が判断します。
1 年以内に新しい版が出ているものに限るのは、更新が止まって直せなくなったライブラリを避けるためです。
非推奨のものを入れないのも、同じ理由です。
同じ役割のものを 2 つ入れないのは、同じことをするコードの書き方を 1 つにそろえるためです。
PR の本文に「何を / なぜ / 代替案」を書くのは、選んだ理由と比べた候補を、レビューする人が確かめられるようにするためです。

候補からダウンロード数のいちばん多いものを選ぶのは、広く使われているもの（デファクトスタンダード）を使うためです。
使われている数が多いライブラリほど、不具合と脆弱性が早く見つかって直ります。
使い方の情報も多いので、Claude が書き方を誤りにくくなります。
ダウンロード数を基準にするのは、選び方を、誰が確かめても同じ答えになる数にするためです。

「使わないもの」と、ほかの規約が入れないと決めているものをダウンロード数で選ばないのは、理由があって外したものだからです。
NestJS と NgRx を外した理由は、`docs/decisions/0001-template-stack.md` の「採らなかったもの」にあります。
ほかの規約が入れないと決めているものの理由は、このフォルダの、その規約と同じ名前のファイルにあります。

使わない理由を JSDoc に書くのは、そのコードを後で直す人が、理由を読んで判断できるようにするためです。
理由が無くなったら（ライブラリが、要る機能を備えたときなど）、ライブラリに置き換えられます。
PR の本文に書いた理由は、コードを直すときには読まれません。
行の書き出しを `ライブラリを使わない理由:` にそろえるのは、自前で書いた汎用の処理を `git grep` で一覧にするためです。

守りが要ることだけを理由にしないのは、守りはライブラリを使っても書けるからです。
上限は、ライブラリの設定（1 つのセルの長さの上限など）か、ライブラリが返す行やファイルを数えながら確かめられます。
守りのために処理の全体を自前で書くと、守りと関係ない部分（引用符や改行の扱い）の誤りまで、自分たちで負うことになります。

API 定義のヘルパーを汎用の処理に含めないのは、自前で書く理由が [api-contract.md](api-contract.md)（規約 `api-contract.md` の理由）にあるからです。
