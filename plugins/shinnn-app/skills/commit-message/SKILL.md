# コミットメッセージの規約

## 件名（1 行目）

形式は `[<対象>]<要約>`。

- `<対象>`: `client` / `server` / `shared`。リポジトリ全体なら `common`、文書と設定だけなら `docs`
- `<要約>`: **体言止め**（「〜の追加」「〜の修正」。「〜した」「〜する」は使わない）
- 受入条件に対応する変更なら、要約に `AC-n` を入れる。履歴からどの条件の変更か追える
- 日本語で書く

```
[shared]AC-3 項目一覧 API の定義追加
[server]AC-3 項目一覧エンドポイントの追加
[client]AC-3 項目一覧画面の追加
[common]import 制約 lint の追加
```

## 本文（変更点が複数なら書く）

- 箇条書き（`- ` 始まり）・体言止め
- 変更点と理由を簡潔に
- `Test plan` のような定型の節は不要
- **AI 生成を示す文言（`Co-Authored-By` 等）は付けない**

```
[server]AC-3 項目一覧エンドポイントの追加

- GET /api/items を追加
- limit / offset のページングに対応
- 件数超過は 400（APP_VALIDATION_FAILED）
```

## コミットの分け方

- **層ごとに分ける**: `shared`（API 定義）→ `server`（DB → API → 業務処理）→ `client`（画面）
- **参照される側を先に**積む。順序を逆にすると途中のコミットで型が通らない
- **実装とテストは別のコミット**にする。文書と設定もさらに分ける
- **挙動が変わらないリファクタと、挙動が変わる修正は別のコミット**にする（レビューしやすさを優先）
- レビュー指摘への対応は **1 コメント = 1 コミット**

## 改行コード

- LF に統一する（`.gitattributes` の `* text=auto eol=lf` が前提）
- **改行コードだけが変わった差分を作らない。** 検出方法は `pr` スキルの「PR を出す前に確認する」を読む

## 複数行のメッセージを渡すとき

- Bash では件名と本文で `-m` を分ける（`git commit -m "件名" -m "- 箇条 1"`）か、本文をファイルにして `-F` で渡す
- PowerShell では here-string（`@'...'@`、閉じの `'@` は行頭）を使う。これを Bash に渡すと先頭に `@` が混ざる

## その他

- コード内のコメントも日本語で書く
- **コミットは人の指示があるときだけ行う。** 勝手にコミットしない
