## 背景

このテンプレートは、開発に慣れていない担当者の PC で動きます。最初の 1 時間でつまずく箇所が
「アプリの作り方」ではなく「パッケージマネージャの都合」になるのを避けるため、次を重く見ました。

1. **入れるものを増やさない** — Node.js を入れれば動くこと
2. **インストールが途中で止まらない** — 依存のビルドスクリプトの許可などで、人の対話が要らないこと
3. **手元と CI で入る依存が同じになる** — lock ファイルどおりに再現できること

## 決めたこと

**npm workspaces を使う。** ルートの `package.json` の `workspaces` に
`["shared", "server", "client"]` をこの順で並べ、`--workspaces` を付けたコマンドはこの順に走ります
（`shared` の API 定義を先に建てないと、`server` と `client` の型検査が通らないため）。

- npm は Node.js に同梱されるので、追加で入れるものはありません（Node.js の版は [0003](./0003-node-version.md)）
- 依存のビルドスクリプト（esbuild など）は、npm 11 系では既定で実行されません。許可は
  **`package.json` の `allowScripts` に書いて配る**ので、担当者の手元で対話も追加のコマンドも要りません
- CI は `npm ci` を使います。`package-lock.json` と食い違ったらインストールの時点で落ちます

## 採らなかったもの

| 候補       | 採らなかった理由                                                                                                                                                                                                                                                                                                        |
| :--------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| pnpm       | Node.js に同梱されないため、別途入れてもらう必要がある（Corepack 経由の導入は、Corepack が Node.js 25 で同梱から外れるため当てにできない）。依存のビルドスクリプトを `pnpm approve-builds` で人が許可するまでテストもビルドも動かず、「動かない理由が依存の中にある」状態は、慣れていない担当者には原因の見当がつかない |
| yarn / bun | 同じく別途の導入が要る。AI の学習データでの実例も npm より少ない                                                                                                                                                                                                                                                        |

## npm で気を付けること（幻の依存）

npm は依存を 1 か所にまとめて置くため、`package.json` に書いていないパッケージでも
import が通ってしまいます（幻の依存）。pnpm はこれを構造的に防ぎますが、npm では次の 2 つで補います。

| 起きうること                           | 防ぎ方                                                                                |
| :------------------------------------- | :------------------------------------------------------------------------------------ |
| 宣言していない依存を import してしまう | ESLint の `import-x/no-extraneous-dependencies` を **error** で全パッケージに入れる   |
| lock ファイルと違う依存が入る          | CI は `npm ci` を使う（`package-lock.json` と食い違ったらインストールの時点で落ちる） |

`no-extraneous-dependencies` は、そのファイルが属するパッケージの `package.json` に
書かれていない import を lint エラーにします。`devDependencies` を読んでよいのは、
配布物に入らないファイル（テスト・種データ・設定・スクリプト）だけに絞っています。

## 同じライブラリはワークスペース全体で同じ版にそろえる

npm workspaces では、パッケージごとに違う版を入れること自体はできます。それでも、TypeScript や
テストの土台のようにどのパッケージでも同じ書き方をするものは、ワークスペース全体で 1 つの版に
そろえます。系統が 2 つあると、同じ書き方が片方でだけ通らない状態を持ち込むからです。

TypeScript はワークスペース全体で 6 系です。Vitest はワークスペース全体で 4 系です。`client` は `@angular/build` の peer が `vitest@^4` なので、
4 系から動かせません。

新しいライブラリを足すときは「他のパッケージが同じものを別の版で使っていないか」を先に
見てください。peer 依存で要求される版が食い違う場合は、`npm install` の時点で分かります。

## 依存の中の古い版を overrides で差し替えているもの

依存の依存として入ってくる古い版のうち、**実際には読み込まれないのに脆弱性の警告が出るもの**は、
ルートの `package.json` の `overrides` で新しい版に差し替えています。対応の要らない警告が
出続けると、本当に対応が要る警告が埋もれるためです。

### `@esbuild-kit/core-utils` の下の `esbuild`

- **差し替え**: `~0.18.20` を `^0.25.0` にします
- **経路**: `server` → `drizzle-kit` → `@esbuild-kit/esm-loader` → `@esbuild-kit/core-utils` → `esbuild`
- **理由**: `@esbuild-kit` は tsx に統合されて更新が止まったパッケージです。`drizzle-kit` は
  自分の中に含む tsx で TypeScript を読み込むため、この `esbuild` は読み込まれません。それでも
  esbuild 0.24.2 以下の脆弱性（GHSA-67mh-4wv8-2f99）として、`npm audit` と Dependabot が警告を出します。
  `drizzle-kit` の 0.31 系のうちはこの依存が残るため、`drizzle-kit` の版上げでは消せません
- **外す条件**: `drizzle-kit` が `@esbuild-kit` を依存から外したとき（1.0 の正式版で外れる予定です）。
  外すときは `overrides` からこの項目を消し、`npm ls --all` が通ることを確かめます

### lock ファイルの作り直し方

`overrides` を足したり版を変えたりしたときは、`npm update <差し替えるパッケージ>`
（上の例では `npm update esbuild`）で `package-lock.json` を作り直します。`npm install` だけでは
lock ファイルが変わらず、`npm ls --all` が `invalid` を出して失敗します。lock ファイルを手で
直しても同じです。

`npm update` は、同じ名前のパッケージをほかの場所でも範囲内で上げることがあります。作り直した後は、
lock ファイルの差分が差し替えた対象の下（上の例では `node_modules/@esbuild-kit/core-utils/node_modules/`）
だけに収まっていることと、`npm ls --all` と `npm audit` が通ることを確かめてください。

## 結果

- 手元で必要なのは Node.js だけです。`npm install` / `npm run dev` / `npm test` で動きます
- 依存の書き忘れは `npm run check` の lint で落ちます。CI でも同じルールが走ります
- `package-lock.json` は生成物です。手で編集せず、`npm install` で作り直します

## 見直す時期

- `import-x/no-extraneous-dependencies` が実際に幻の依存を捕まえた件数を、半年後に振り返ります
- パッケージマネージャを Node.js と一緒に配る仕組み（Corepack の後継）が安定したら、再検討します
- `drizzle-kit` が `@esbuild-kit` を依存から外したら（1.0 の正式版の予定）、`esbuild` の `overrides` を外します
