# スタイリング規約（client）

**独自 CSS を書かない。Tailwind のユーティリティクラスと Angular Material のテーマ変数だけで作ります。**

「（検査: …）」には、その決まりを機械で確かめる仕組みを書いています。付いていない決まりは、レビューだけで確かめます。

## 基本

- **`.css` / `.scss` ファイルを新規に作らない。** コンポーネントの `styles` / `styleUrls` を増やさない。
  ただし、生成したテーマ `client/src/theme.css` は例外とする（「テーマと書体」）
- `@apply` を使わない
- グローバルスタイルは、Tailwind のエントリの 1 ファイル（`client/src/styles.css`）にだけ書く。
  機能ごとのクラスやセレクタをここに書き足さない（役割の名前の変数は「テーマと書体」）
- 色・余白・フォントは、Tailwind の設定にある段階値を使う。任意値（`w-[137px]` / `text-[#1a2b3c]`）を書かない。
  段階値に無い値が要るときは、Tailwind の `@theme` に段階値を足す

## Material と Tailwind の共存

- Material のテーマ（`--mat-sys-*` の変数。同梱のテーマか生成した `theme.css`）は、`styles.css` の `material` レイヤに
  読み込む。Material の部品自身の CSS は、レイヤの外に入る。レイヤの外の CSS は、どのレイヤの CSS よりも優先される
- Material と同じ色を Tailwind で使うときは、Material のシステム変数（`--mat-sys-*`）を Tailwind の `@theme` に
  割り当てる。同じ色を 2 か所に別々の値で書かない
- **Material の部品の要素（`mat-dialog-content`・`th mat-header-cell`・`td mat-cell`、`*matNoDataRow` の行の `td`
  （部品が `mat-mdc-cell` を足す）など）に、部品が自分で決めている性質（`display`・余白・文字の揃えなど）の
  ユーティリティを付けない。**
- ただし、部品が決めていない性質（幅・ツールバーの `gap` など）のユーティリティは、部品の要素に付けてよい
- 部品が決めている並べ方・内側の余白・揃えを変えるときは、ユーティリティを部品の中に置いた要素（`div` など）に付ける
  （`flex`・`gap`・`p-*`・`text-right` など）
- 部品の中の間隔は、`margin` ではなく、親の `gap`（中身どうし）か `p-*`（部品の縁と中身の間）で取る
- **Material のスタイルを `::ng-deep` で上書きしない。** コンポーネントが公式に提供する入力
  （`color` / `appearance` など）とテーマ変数だけで調整する。それで調整できない見た目は作らず、
  `docs/仕様書.md` の未決事項に上げる

## テーマと書体

- **配色と書体は、`styles.css` の 1 か所で決める。画面のテンプレートに直値を書かない。** 方針は `docs/仕様書.md` の
  「見た目の方針」に書く。方針を変えるときは、そこを先に直す
- 特定の画面だけで使う色や書体が要るときも、`styles.css` の `@theme` に役割の名前（例: `--color-highlight`、
  `--font-display`）で足す。どの画面のどこに使うかは、「見た目の方針」に書く。名前に画面の名前を付けない。
  色の値は、テーマの変数（`--mat-sys-*`）から取る。主色と別の系統の色が要るときは、`theme-color` の生成に
  第 3 の色（`--tertiary-color`）として加える
- 配色は Material のテーマで決める。使うのは、同梱のテーマ（Angular Material の `azure-blue.css`）か、主色から
  Material の `theme-color` で生成した `client/src/theme.css` のどちらかにする
- 色を変えるときは、`theme.css` を生成し直す（生成物を手で編集しない決まりは、[git-workflow.md](git-workflow.md) の「やらないこと」）
- `theme.css` を読み込むレイヤは、同梱のテーマと同じ `material` にする
- 書体を変えるときと、主色と別の系統の色が要るときは、`theme.css` を生成して使う（同梱のテーマは、下の書体の変数を
  読まない。配色を変えないなら、今の主色で生成する）
- 書体は、npm の `@fontsource` / `@fontsource-variable` のパッケージを入れて、`styles.css` で読み込む。
  外部の配信（Google Fonts の `<link>` など）から読み込まない。書体の名前は `styles.css` の `html` の
  `--mat-sys-plain-font-family` / `--mat-sys-brand-font-family` と、`@theme` の `--font-sans` に入れる
- `frontend-design` スキルの案がこの規約とぶつかるときは、規約に従う（独自の CSS・任意値・外部の書体の配信は、
  案にあっても使わない）

## デザインの指導

- 次のときは、画面のコードを書く前に、`frontend-design` スキルでデザインの指導を受ける（受け方は `/shinnn-app:add-screen` の「デザインの指導を受ける」）
  - 画面を足すとき
  - 機能を足して、今ある画面の項目・操作・状態が増えるとき
  - 見た目を変える依頼を受けたとき
- 画面を作り終えたら、撮った画像を添えて指導を受け、見直す（手順は `/shinnn-app:add-screen` の「9. 作った画面を見直す」）
- ただし、画面を撮れない（ブラウザが無い、サーバーを起動できない）ときは、作り終えた後の見直しをしなくてよい
- ただし、利用者が画面を見ながら調整を頼んでいるときは、作り終えた後の見直しをしなくてよい
- 計画の Issue がすべて閉じたら、すべての画面を通して指導を受け、見直す（手順は `/shinnn-app:feature` の「8. すべての画面を見直す」）
- 前に指導を受けた画面でも、これらに当たるたびに受け直す
- ただし、文言だけの変更では、受けなくてよい
- ただし、利用者が変え方まで指定した変更では、受けなくてよい
- ただし、`frontend-design` が使えないときは、指導を受けずに進めてよい（進め方は `/shinnn-app:add-screen` の「`frontend-design` が無いとき」）
- 指導には、`docs/仕様書.md` の「目的」と「使う人と場面」を渡す
- 「使う人と場面」の分からないところは、推測で埋めて「（仮）」を付ける

## クラスの書き方

- 条件付きのクラスは `[class.xxx]` か `[ngClass]` で切り替える。
  **テンプレート内で文字列を連結してクラス名を組み立てない**
- 同じクラスの組み合わせが 3 か所以上に出たら、コンポーネントに切り出す。クラスの文字列を定数にして使い回さない
- レスポンシブは、Tailwind のブレークポイント接頭辞（`sm:` / `md:` / `lg:`）で書く。メディアクエリを手書きしない

## なぜ

独自 CSS を禁じるのは、ある画面の変更が、別の画面の見た目を壊すのを防ぐためです。CSS では、ある画面のために書いた
セレクタが、別の画面の見た目を変えることがあります。そうなっても、型検査もテストも教えてくれません。
ユーティリティクラスなら、影響範囲がそのタグの中で閉じます。

`@apply` を使わないのは、クラスの実体をテンプレートから見えるようにしておくためです。

クラス名を文字列の連結で組み立てないのは、Tailwind が、使うクラスを見落とさないようにするためです。Tailwind は、
テンプレートにそのまま書かれたクラス名だけを拾います。組み立てたクラス名は拾われず、スタイルが生成されません。

Material のテーマをレイヤに入れるのは、書体の変数をテーマの値より優先させるためです。書体の変数は、`styles.css` の
`html` に、レイヤの外で書いています。レイヤの外の指定は、読み込む順に関係なく、レイヤの中の指定より優先されます。
Tailwind の preflight（ブラウザ既定のスタイルを打ち消す仕組み）も、レイヤの中にあります。そのため、preflight は、
レイヤの外に入る Material の部品の CSS を消しません。

部品の要素に、部品が決めている性質のユーティリティを付けないのは、適用されない指定を書かないためです。
Material の部品の CSS は、Angular が画面を出すときに、レイヤの外に差し込まれます。レイヤの外の指定は、
レイヤの中のユーティリティより優先されます。そのため、部品が決めている性質は、ユーティリティを付けても変わりません。
適用されなくても、型検査にも lint にもエラーは出ません。部品が決めていない性質は、部品の CSS とぶつからないので、
ユーティリティが適用されます。一方、部品の中に置いた要素には、部品の CSS はほとんど適用されません。そのため、
並べ方・内側の余白・揃えのユーティリティは、書いたとおりに適用されます。

部品の中の間隔を `margin` ではなく親の `gap` か `p-*` で取るのは、間隔をそろえるためです。部品は、中に置いた
最初の子の上の `margin` と、最後の子の下の `margin` を 0 にすることがあります（ダイアログの中身など）。子に `margin` を
付けると、その分だけ間隔が消えます。

`::ng-deep` を禁じる理由は 2 つあります。1 つ目は、Angular が非推奨にしていることです。2 つ目は、Material の内部構造が
変わると、`::ng-deep` で書いた上書きが気づかないうちに適用されなくなることです。適用されなくなると、版を上げた日に、
どの画面が崩れるか分からない状態になります。

見た目の方針をアプリで 1 つにするのは、使う人が画面を移るたびに、見方を覚え直さなくて済むようにするためです。

特定の画面だけで使う色や書体も同じ場所に役割の名前で足すのは、どの色と書体がどこで使われているかを、1 か所で見渡せる
ようにするためです。画面のテンプレートに直値が散らばると、方針を変えたときに直し漏れが出ます。

配色を生成に任せるのは、文字と背景を読みにくい組み合わせにしないためです。Material のテーマは、主色 1 つから、
文字と背景の組み合わせを 150 を超える変数に展開します。これを手で書くと、読みにくい組み合わせが混ざります。

書体を npm で同梱するのは、外部の配信に頼らないためです。外部の配信に頼ると、社内のネットワークでは書体を
読み込めないことがあります。また、画面を開いたことが配信元に伝わります。

`frontend-design` スキルは、見た目の案を立てるのに使います。ただし、このスキルは、独自の CSS を書く前提の案も出します。
そのため、案と規約がぶつかるときは、上の理由から規約を優先します。

デザインの指導を最初の 1 回で終わらせないのは、機能が増えるたびに、画面の中の情報の優先度が変わるからです。
最初に決めた方針だけでは、増えた項目や操作の置き場所は決まりません。

計画の Issue がすべて閉じた後にすべての画面を見直すのは、画面をまたぐ食い違いを見つけるためです。
用語・配置・操作の順番の食い違いは、画面を 1 つずつ作っている間には見えません。

文言だけの変更で指導を受けなくてよいのは、配置と情報の優先度が変わらないからです。
変え方まで指定した変更で受けなくてよいのは、利用者が決めたことを指導で覆さないためです。

作った画面の画像を添えて見直すのは、コードからは見えない崩れを見つけるためです。
余白や文字の詰まり方は、型検査にもテストにも出ません。

画面を撮れないときに見直しを飛ばしてよいのは、撮る道具が無いことで作業を止めないためです。
飛ばした画面は、PR 本文に書いておくと、人が後で確かめられます。

画面を見ながらの調整で見直しをしなくてよいのは、利用者が直した画面をその場で見るからです。

`frontend-design` が使えないときに進めてよいのは、道具が入っていないことで作業を止めないためです。
入れたものは、次に起動したときから使えます。

「目的」と「使う人と場面」を毎回渡すのは、同じ機能でも、使う人と場面で良い配置が変わるからです。
毎日大量に入力する人と、月に 1 度だけ確かめる人では、優先する情報が違います。

分からないところを「（仮）」のまま進めるのは、確かめる相手がいなくても指導を受けられるようにするためです。
仮に書いてあれば、利用者が後から見つけて直せます。
