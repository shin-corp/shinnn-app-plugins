# 0002. パッケージマネージャに npm workspaces を使う

## 背景

このテンプレートは、開発に慣れていない担当者の PC で動きます。最初の 1 時間でつまずく箇所が
「アプリの作り方」ではなく「パッケージマネージャの都合」になるのを避けるため、次を重く見ました。

1. **入れるものを増やさない**: Node.js を入れれば動くこと
2. **インストールが途中で止まらない**: 依存のビルドスクリプトの許可などで、人の対話が要らないこと
3. **手元と CI で入る依存が同じになる**: lock ファイルどおりに再現できること

## 決めたこと

**npm workspaces を使う。** ルートの `package.json` の `workspaces` に
`["shared", "server", "client"]` をこの順で並べ、`--workspaces` を付けたコマンドはこの順に走ります
（`shared` の API 定義を先にビルドしないと、`server` と `client` の型検査が通らないため）。

- npm は Node.js に同梱されるので、追加で入れるものはありません（Node.js の版は [0003](./0003-node-version.md)）
- 依存のビルドスクリプト（esbuild など）は、npm 11 系では既定で実行されません。許可は
  **`package.json` の `allowScripts` に書いて配る**ので、担当者の手元で対話も追加のコマンドも要りません
- CI は `npm ci` を使います。`package-lock.json` と食い違ったらインストールの時点で落ちます

## 採らなかったもの

| 候補       | 採らなかった理由                                                                                                                                                                                                                                                                                                            |
| :--------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| pnpm       | Node.js に同梱されないため、別途入れてもらう必要がある（Corepack 経由の導入は、Corepack が Node.js 25 で同梱から外れるため当てにできない）。依存のビルドスクリプトを `pnpm approve-builds` で人が許可するまで、テストもビルドも動かない。「動かない理由が依存の中にある」状態では、慣れていない担当者は原因の見当がつかない |
| yarn / bun | 同じく別途の導入が要る。AI の学習データでの実例も npm より少ない                                                                                                                                                                                                                                                            |

## npm で気を付けること（幻の依存）

npm は依存の多くをルートの `node_modules` にまとめて置くため、`package.json` に書いていないパッケージでも
import が通ってしまいます（幻の依存）。pnpm はこれを構造的に防ぎますが、npm では次の 2 つで補います。

| 起きうること                           | 防ぎ方                                                                                |
| :------------------------------------- | :------------------------------------------------------------------------------------ |
| 宣言していない依存を import してしまう | ESLint の `import-x/no-extraneous-dependencies` を **error** で全パッケージに入れる   |
| lock ファイルと違う依存が入る          | CI は `npm ci` を使う（`package-lock.json` と食い違ったらインストールの時点で落ちる） |

`no-extraneous-dependencies` は、そのファイルが属するパッケージの `package.json` に
書かれていない import を lint エラーにします。`devDependencies` に書いたものを import してよいファイルは、どのパッケージでも
テストと設定ファイルです。server では、さらに種データ・評価（`server/evals/`）・スクリプトと、必要になったときにだけ
PGlite を読み込む `src/db/` の 2 ファイルも import してよいことにしています。

## 同じライブラリはワークスペース全体で同じ版にそろえる

npm workspaces では、パッケージごとに違う版を入れること自体はできます。それでも、TypeScript や
テストを動かすライブラリのようにどのパッケージでも同じ書き方をするものは、ワークスペース全体で 1 つの版に
そろえます。版の系統が 2 つあると、同じ書き方が片方でだけ通らない状態になるからです。

TypeScript はワークスペース全体で 6 系です。Vitest はワークスペース全体で 5 系です。`client` のテストは `@angular/build` が動かすので、
Vitest の版は `@angular/build` の peer の範囲から選びます。Vitest を上げるときは、3 つのパッケージを一緒に上げます。

新しいライブラリを足すときは「他のパッケージが同じものを別の版で使っていないか」を先に
見てください。peer 依存で要求される版が食い違う場合は、`npm install` の時点で分かります。

## テストの画面の環境（jsdom）はルートで宣言する

`client` のテストは、ブラウザの代わりに jsdom を使います。jsdom は、ブラウザの画面の仕組み（DOM）を
Node.js の中で再現するライブラリです。jsdom を使うのは `client` のテストだけです。それでも、宣言は `client` ではなく、
ルートの `package.json` の `devDependencies` に置きます。jsdom の版を上げるときも、ルートの `package.json` を直します。
`client` のテストのコードからは、jsdom を直接 import しません。import すると、lint が `client` の `package.json` への
宣言を求めます。

jsdom を読み込むのは Vitest です。Node.js は、import を書いたファイル（ここでは Vitest の中のファイル）のあるフォルダから
上へたどって `node_modules` を探します。ルートの `node_modules` は、Vitest がどこに置かれていても、上へたどる途中にあります。
`client/node_modules` は、Vitest がルートに置かれていると、上へたどる途中にありません。今の lock ファイルでは、
Vitest はルートに置かれています。

`client` で宣言したパッケージをどこに置くかは、npm と lock ファイルが決めます。Dependabot（依存の版上げの PR を
自動で作る GitHub の機能）が作る lock ファイルでは、jsdom が `client/node_modules` に置かれることがあります。
そうなると、`client` のテストが `Cannot find package 'jsdom'` で落ちます。ルートで宣言したパッケージは、
必ずルートの `node_modules` に置かれます。

## 依存の中の古い版を overrides で差し替えているもの

依存の依存として入ってくる古い版のうち、次のどちらかに当てはまるものは、ルートの `package.json` の `overrides` で
新しい版に差し替えています。

1. **実際には読み込まれないのに脆弱性の警告が出るもの。** 本当に対応が要る警告を見落とさないためです。
   対応の要らない警告が出続けると、対応が要る警告が埋もれます
2. **読み込まれる依存のうち、脆弱性の直った版が出ているのに、それを使うライブラリが古い版に固定しているもの。**
   ライブラリの新しい版を待つ間も、直った版で動かすためです

### `@esbuild-kit/core-utils` の下の `esbuild`

- **差し替え**: `~0.18.20` を `^0.25.0` にします
- **経路**: `server` → `drizzle-kit` → `@esbuild-kit/esm-loader` → `@esbuild-kit/core-utils` → `esbuild`
- **理由**: `@esbuild-kit` は tsx に統合されて更新が止まったパッケージです。`drizzle-kit` は
  自分の中に含む tsx で TypeScript を読み込むため、この `esbuild` は読み込まれません。それでも
  esbuild 0.24.2 以下の脆弱性（GHSA-67mh-4wv8-2f99）として、`npm audit` と Dependabot が警告を出します。
  `drizzle-kit` の 0.31 系のうちはこの依存が残るため、`drizzle-kit` の版上げでは消せません
- **外す条件**: `drizzle-kit` が `@esbuild-kit` を依存から外したとき（1.0 の正式版で外れる予定です）。
  外すときは `overrides` からこの項目を消し、`npm ls --all` が通ることを確かめます

### `@angular/build` の 22.2 系の下の `vite`

- **差し替え**: `8.3.0` を `8.3.4` にします
- **経路**: `client` → `@angular/build` → `vite`
- **理由**: `@angular/build` の 22.2 系（22.2.3 まで）は、`vite` を `8.3.0` に固定しています。`vite` は、
  `npm run dev`（開発用のサーバー）とテストで読み込まれます。`vite` の 8.3.0〜8.3.2 には、中に含む launch-editor
  （画面のエラー表示からエディタを開く処理）と、開発用のサーバーの脆弱性の勧告が出ています。いちばん重いのは
  GHSA-587h-7wmj-h5pm（high）です
- **8.3.4 を選んだ理由**: 8.3 系で勧告が直っているのは 8.3.3 以上です。その中から、Angular の 22.3 の最新の試験版
  （22.3.0-next.2）が固定している版を選びます。Angular 自身が組み合わせて出している版だからです
- **Vitest にも届く**: Vitest は、`@angular/build` が peer として使うパッケージです。そのため、この差し替えは
  Vitest が使う `vite` にも届きます。lock では、ルートに置いた 1 つの `vite`（8.3.4）を、`@angular/build` と
  Vitest（`server`・`shared` のテストを含む）が使います。項目がある間は、Vitest の `vite` も 8.3.4 から上がりません
- **22.2 系だけに効かせる**: `overrides` のキーを `@angular/build@22.2` にします。このキーは、`vite` を差し替える
  だけでなく、`@angular/build` 自身の範囲も 22.2 系に絞ります。そのため、項目がある間は、`npm update` を実行しても
  `@angular/build` は 22.3 系に上がりません。22.3 系に上げるときは、`client/package.json` の `@angular/build` の範囲を
  上げます（例: `npm install @angular/build@^22.3.0 -w client`）。範囲が 22.2 系を含まなくなると、差し替えは
  効かなくなります。そのときは、その版が固定する `vite` が入ります
- **キーに版を付ける理由**: 新しい系統の `@angular/build` に古い `vite` を組み合わせないためです。差し替えた版は
  `npm ls --all` でも範囲の外として扱われないので、項目の消し忘れに気づく仕組みがありません
- **外す条件**: `client/package.json` の `@angular/build` の範囲を 22.3 系以降に上げたとき、または 22.2 系の新しい版が
  `vite` を 8.3.3 以上に固定したとき。外すときは `overrides` からこの項目を消し、`npm update vite` で lock ファイルを
  作り直します。そのうえで、`npm ls --all` と `npm audit --audit-level=high` が通ることを確かめます

### lock ファイルの作り直し方

`overrides` の項目を足したとき、消したとき、版を変えたときは、`npm update <差し替えるパッケージ>`
（`esbuild` なら `npm update esbuild`）で `package-lock.json` を作り直します。`npm install` だけでは
lock ファイルが変わらず、`npm ls --all` が `invalid` を出して失敗します。lock ファイルを手で
直しても同じです。

`npm update` は、同じ名前のパッケージをほかの場所でも範囲内で上げることがあります。作り直した後は、
lock ファイルの差分を見て、版が変わった場所を 1 つずつ確かめてください。差し替えた場所とその依存のほかで版が
変わっていたら、何がそれを使っているかを調べて、上がってよいかを決めます（`vite` では、Vitest が同じ `vite` を
使うことを上の項目に書いています）。あわせて、`npm ls --all` と `npm audit --audit-level=high` が通ることを確かめてください。

## 結果

- 手元で必要なのは Node.js だけです。`npm install` / `npm run dev` / `npm test` で動きます
- 依存の書き忘れは `npm run check` の lint で落ちます。CI でも同じルールが走ります
- `package-lock.json` は生成物です。手で編集せず、`npm install` で作り直します

## 見直す時期

- `import-x/no-extraneous-dependencies` が実際に幻の依存を見つけた件数を、半年後に振り返ります
- パッケージマネージャを Node.js と一緒に配る仕組み（Corepack の後継）が安定したら、再検討します
- `drizzle-kit` が `@esbuild-kit` を依存から外したら（1.0 の正式版の予定）、`esbuild` の `overrides` を外します
- `client/package.json` の `@angular/build` の範囲を 22.3 系以降に上げたら、`vite` の `overrides` を外します
- 22.2 系の新しい `@angular/build` を入れたら、それが固定する `vite` の版を見ます。8.3.3 以上なら、`vite` の
  `overrides` を外します
