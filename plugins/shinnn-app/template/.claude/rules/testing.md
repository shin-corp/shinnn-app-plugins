# テスト規約

Vitest を使います。**ファイル名は `.test.ts`。`.spec.ts` は CI で fail します。**

## 何をテストするか

- **実装が正。** テストは実装の振る舞いを固定するために書く。
  テストが落ちたとき、直すのが実装かテストかは次の表で判断する

| 状況                                               | 直すもの                                       |
| :------------------------------------------------- | :--------------------------------------------- |
| 仕様書の受入条件と実装が食い違う                   | 実装                                           |
| 仕様書に書いていない挙動をテストが決め打ちしている | テスト                                         |
| テストが受入条件どおりの挙動を確かめていない       | テスト                                         |
| 実装を意図して変えた（仕様書も更新済み）           | テスト                                         |
| どちらが正しいか分からない                         | **手を止めて人に聞く。テストを消して通さない** |

- 通らないテストを `skip` して緑にしない。想定外の挙動を見つけたら Issue を立て、
  その番号をコメントに書いてから `skip` する
- **不具合を直すときは、直った後の正しい振る舞いを受入条件にする。** そのテストは、直す前の実装では落ちるものにする
- 振る舞いが変わらない変更（文言・見た目の調整）には、受入条件を足さない

## テスト名

- 日本語で「何が起きるか」を書く。`should` や `test1` のような名前を付けない
- **受入条件に対応するテストは、名前の先頭に識別子を入れる**（例: `AC-3 存在しない id は 404 を返す`）。
  CI の policy job が「仕様書の全受入条件にテストがある」ことを検査する
- `describe` は `正常系` / `異常系` / `エッジケース`、`test` は条件と結果

## 観点

1 つの対象につき、次の 3 つを意識して書きます。API のルートは 1 つにつき、正常系と異常系を最低 1 本ずつ書きます。

| 観点         | 例                                                                                             |
| :----------- | :--------------------------------------------------------------------------------------------- |
| 正常系       | 期待どおりの入力で、期待どおりの結果と状態変化                                                 |
| 異常系       | 不正な入力、存在しない id、権限なし、他人のデータ。**status と `messageKey` の両方を検証する** |
| エッジケース | 空配列、0 件、上限ちょうど、上限 +1、最大長の文字列、同時実行                                  |

- 「200 が返る」だけで終えない。**レスポンスの中身と DB の状態変化まで確認する**
- 異常系は `messageKey` まで見る。文言（`message`）は変わるので突き合わせない

## サーバーのテスト

- `app.ts` を import して `app.listen(0)` で起動し、**native fetch で実際に HTTP を叩く**。
  handler を直接呼ばない（middleware と検証を飛ばしてしまう）
- 要求先の URL は API 定義から組み立てる（`server.url(itemsApi.getItem, { id })`）。
  URL を手で書かない。パスを変えたときにテストが一緒に動き、CI の API 定義カバレッジも数えられる
- ヘルパーは `server/tests/helpers/` に置く。同梱は 3 つ
  - `startServer()`（`helpers/server.ts`）: テストサーバーの起動。戻り値の `reset()` でデータを空にし、`close()` で止め、
    `url()` で URL を組み立てる
  - `createTestDb()`（`helpers/db.ts`）: PGlite の DB を作りマイグレーションを流す
  - `createAuthHeaders()`（`helpers/auth.ts`）: 認証済みの要求ヘッダを作る
  - 同じ用意を 2 つのテストが書いたら `seed<対象>()` のようなヘルパーに寄せる
- サーバーと DB はテストファイルごとに 1 回だけ作る（`beforeAll` で `startServer()`、`afterAll` で `close()`）。
  テストごとに `beforeEach` で `reset()` を呼んでデータを空にし、前のテストが残したデータに依存しない
- **利用者ごとのデータを扱うルートは、別の利用者で確かめるテストを必ず書く。**
  `createAuthHeaders({ subject: '<別の id>' })` で別の利用者のトークンを作り、
  他人のデータの取得・更新・削除が 404 になること、一覧と件数に他人のデータが入らないことを見る。
  自分のデータだけで試すテストは、持ち主で絞り忘れても全部通る
- 時刻に依存するテストは `vi.setSystemTime()` で固定する

## 単体テストの例外

- **副作用が無く、DB にも HTTP にも触れないモジュール**（計算・整形など）は、直接 import して
  単体テストしてよい。入力と戻り値だけを見る
- API の振る舞い（データ・権限・入力の検証）に紐づく受入条件（`AC-n`）は、HTTP 経由のテストで確かめる。
  単体テストはその補助で、受入条件のテストの代わりにはしない
- **時間に依存するテストを書かない。** 「N ミリ秒以内に終わる」のような判定は、走らせる機械の速さで
  結果が変わる。時間のかかる処理は、待ち時間を引数で渡せる形にするか、`vi.useFakeTimers()` で
  偽のタイマーを使う
- **速さを測るテストは `*.bench.test.ts`、その場限りの確認用は `*.tmp.test.ts`** という名前にする。
  この 2 つは常に緑である前提を置かないので、応答を終えるときの自動チェックの対象から外れる

## 画面のテスト

- 対象ファイルの隣に `<対象>.test.ts` を置く
- 検証するのは **表示される結果**（DOM のテキスト、要素の有無）。内部の signal を直接読まない
- サーバー呼び出しは **`fetch` を差し替えて再現する**（同梱の `items-page.component.test.ts` が手本。
  サンプルの `items` を消した後は、既存の機能を手本にする）。`api-client.ts` の `call()` は差し替えない
- empty / loading / error の 3 状態をそれぞれ確認する
- 画面に現れる受入条件（表示・操作）は、画面のテストの名前の先頭に `AC-n` を入れて確かめる。
  API の振る舞い（データ・権限・入力の検証）に関わる受入条件は、サーバーの HTTP 経由のテストで確かめる

## やらないこと

- テストのためだけに実装へ分岐や公開メソッドを足すこと
- 1 つの `test` で複数の機能を確認すること（落ちたときに原因が絞れない）
- ランダム値・現在時刻・実行順に依存すること
- ネットワークと外部サービスへ実際にアクセスすること

## なぜ

実際に HTTP を叩くのは、middleware・検証・error middleware を含めた**本番と同じ経路**を通すためです。
handler を直接呼ぶテストは、認証を外した状態や検証を飛ばした状態でも緑になります。

副作用の無いモジュールを直接 import してよいのは、境界値や丸めの結果を戻り値で 1 つずつ固定できるためです。
同じ確認を HTTP 経由で書くと、要求を組み立てる手間が増え、落ちたときに計算と経路のどちらが原因か分かりません。
API の振る舞いの受入条件を HTTP 経由で確かめるのは、受入条件が使う人から見た振る舞いで、本番と同じ経路を通ってはじめて
確かめられるためです。画面に現れる受入条件（表示・操作）を画面のテストで確かめるのは、画面を描いてはじめて分かることで、
API のテストでは確かめられないためです。不具合の受入条件のテストを直す前の実装で落ちるものにするのは、落ちないテストは
その不具合が戻っても気づけないためです。文言や見た目だけの変更に受入条件を足さないのは、振る舞いの約束ではないものを
約束として数えると、受入条件が増えるだけで守るものが増えないためです。時間に依存するテストを書かないのは、走らせる機械の速さや同時に動いている処理で結果が
変わり、原因の無い失敗が混じるためです。

DB をテストファイルごとに作り、テストの間はデータだけを空にするのは、DB を作るたびにマイグレーションを流すためです。
テストごとに作り直すと 1 件ごとにその時間がかかり、テストが増えるほど確認が遅くなります。データを空にすれば、
前のテストの結果に左右されないことは同じように守れます。

`messageKey` まで検証するのは、エラーの種類が変わったことに気づくためです。status だけだと、
「見つからない」が「権限がない」に変わっても 404 のままで通ってしまうことがあります。

画面のテストで `fetch` を差し替えるのは、`call()` の URL の組み立て・ヘッダ・エラー変換まで含めて
画面の振る舞いを検証するためです。`call()` ごと差し替えると、その部分が抜けたまま緑になります。
`api-client.test.ts` は `call()` 自体の検証なので、そこでも `fetch` を差し替えます。

受入条件の識別子をテスト名に入れるのは、引き継ぎのときに「この条件は確認済みか」を機械で判定できる
ようにするためです。人が一覧を作り直す作業が要らなくなります。
