# データベース規約

PostgreSQL 16 と Drizzle ORM です。層の位置づけは [server-architecture.md](server-architecture.md) を参照。

## 新規ファイルの配置判断

| 書こうとしているもの   | 置き場所                                                           |
| :--------------------- | :----------------------------------------------------------------- |
| テーブル定義           | `server/src/db/schema/<テーブル>.ts`（1 ファイル 1 テーブル）      |
| 接続                   | `server/src/db/client.ts`（新設しない）                            |
| マイグレーションの適用 | `server/src/db/migrate.ts`                                         |
| マイグレーション SQL   | `server/drizzle/`（`drizzle-kit generate` の生成物）               |
| クエリ                 | `server/src/service/<機能>.service.ts`（`db/` にクエリを置かない） |
| 初期データ             | `server/seed/`                                                     |

## スキーマ

- **テーブル定義は `db/schema/*.ts` だけ。** SQL の `CREATE TABLE` を手で書かない
- テーブル名・列名は snake_case、TypeScript 側の識別子は camelCase
- 主キーは `uuid`。作成日時 `created_at` と更新日時 `updated_at` を全テーブルに置く
- **一意性・参照整合・値域は DB の制約（UNIQUE / FK / CHECK）で表す。**
  TypeScript の if 文だけで守らない。並行して実行されると通り抜ける
- **利用者ごとのデータのテーブルには持ち主の列（`owner_id`）を `NOT NULL` で置く。** 認証の方式によって
  利用者の識別子が uuid とは限らないので `varchar` で持つ。持ち主ごとの一意性は `(owner_id, name)` のような
  複合の UNIQUE で表す（この索引が持ち主での絞り込みにも効く）
- 削除は原則として物理削除。論理削除が要る場合は仕様書に理由を書いてから足す

## マイグレーション

1. `db/schema/*.ts` を編集する
2. `npm run db:generate -w server` で `server/drizzle/` に SQL を生成する
3. **生成された SQL を読む。** 意図しない `DROP` や型変更が入っていないか確認する
4. `npm run db:migrate -w server` で適用する

- **生成物を手で編集しない**（`.claude/settings.json` で編集が deny されている）。
  直したいときはスキーマを直して生成し直す
- 生成済みのマイグレーションを後から書き換えない。**打ち消す新しいマイグレーションを足す**
- 列の削除・リネームは、生成 SQL がデータを消す形になっていないか必ず確認する

## クエリとトランザクション

- クエリは Drizzle のクエリビルダで書く。生 SQL（`sql` テンプレート）は、
  ビルダで表現できないときだけ使い、理由をコメントに残す
- **1 つのリクエストで複数の書き込みがあるなら `db.transaction()` で囲む。**
  途中で失敗したときに中途半端な状態を残さない
- **同じトランザクションの中のクエリは 1 つずつ `await` する。**
  `Promise.all` で並べない（同じ接続での並行クエリは非対応になる）
- 整合の取れた読み取りが要る複数クエリも、読み取り専用のトランザクションにまとめる
- 一覧を返すクエリには必ず `limit` を付ける。全件取得を書かない
- ユーザー入力を文字列連結で SQL に埋め込まない。必ずビルダかプレースホルダを使う

## テストでの DB

- テストは既定で **PGlite**（Postgres の WASM 版）を使う。追加のインストールは要らない
- テストファイルごとに新しい in-memory DB を作り、マイグレーションを流す。テスト間で状態を共有しない
- PGlite で再現できない機能（一部の拡張、ロール）を使うテストだけ、実 PostgreSQL に向ける。
  接続先を渡す環境変数を足し、`docs/env.md` に名前を書き、なぜ PGlite では足りないかをテストのコメントに書く

## なぜ

制約を DB 側に置くのは、アプリの経路が増えても必ず通る唯一の場所だからです。管理画面・バッチ・
手作業の SQL のどれから書き込んでも、DB の制約は効きます。TypeScript の検査は、その経路を通ったときだけ
効きます。

マイグレーションの生成物を手編集しないのは、次に `generate` を実行したときに手編集が失われるか、
スキーマ定義との差分が二重に出るためです。「スキーマ定義が正で SQL は生成物」を崩さないでください。

トランザクションで囲むのは、部分的に成功した状態がいちばん直しにくいからです。
どの行まで書けたかを人が調べる作業は、非エンジニアには手に負えません。
