# 外部の AI サービスとの連携（Claude Agent SDK など）

`server/src/provider/` に置く、外部システムの SDK を呼ぶコードと、その評価（`server/evals/`）の規約です。
層の位置づけは [server-architecture.md](server-architecture.md) を参照。ここでは Claude Agent SDK を例に書きますが、
他の AI サービスや外部 API でも同じ考え方で扱います。

## 置き場所と呼び出し

- SDK を入れる前に止まり、シン株式会社の判断を待つ（ルートの `CLAUDE.md` の「費用が発生するものは入れない」）。
  Claude Agent SDK はライセンスが `SEE LICENSE IN README.md`（OSS のライセンスではない）で、`scripts/check-licenses.mjs` が通さない
- SDK を import してよいのは `server/src/provider/<システム>.provider.ts` だけ。ESLint の `no-restricted-imports` で止める
  （`server/eslint.config.js` に SDK のパッケージ名を書く）
- `provider/` は通信だけを担う。プロンプトの組み立てや応答の解釈は `service/` に置き、`provider/` は「渡された文字列を送って結果を返す」に留める
- `api/` から `provider/` を直接呼ばない。必ず `service/` を通す

## Claude Agent SDK を呼ぶときに必ず指定すること

| 指定              | 値                                   | 理由                                                                                                                                                                                                                                                                                                                                                                                                                        |
| :---------------- | :----------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tools`           | `[]`                                 | 組み込みツール（ファイル・Bash・Web）を持たせない。文章を返させるだけなら要らず、持たせると利用者の入力でサーバーのファイルに触れる                                                                                                                                                                                                                                                                                         |
| `strictMcpConfig` | `true`                               | 手元の Claude Code ログインに紐づく claude.ai のコネクタ（Gmail・Notion など）を読み込まない。`tools: []` では外れない                                                                                                                                                                                                                                                                                                      |
| `disallowedTools` | `['mcp__*']`                         | 上の保険。SDK の挙動が変わっても MCP のツールをモデルに見せない                                                                                                                                                                                                                                                                                                                                                             |
| `settingSources`  | `[]`                                 | 設定ファイル（CLAUDE.md や `.claude/`）を読ませない                                                                                                                                                                                                                                                                                                                                                                         |
| `maxTurns`        | `1`（文章を返すだけなら）            | ツールが無いので 1 往復で終わる。終わらない応答（`error_max_turns`）は失敗として扱う                                                                                                                                                                                                                                                                                                                                        |
| `persistSession`  | `false`                              | 会話を SDK 側に残さない                                                                                                                                                                                                                                                                                                                                                                                                     |
| `env`             | `process.env` を土台に組み立てたもの | SDK の `env` は子プロセスの環境を丸ごと置き換えるので `PATH` などを引き継ぐ。**端末の `ANTHROPIC_API_KEY` は渡さない**。このアプリでキーを使うときは専用の環境変数（`<アプリ名>_ANTHROPIC_API_KEY`。例 `MYAPP_ANTHROPIC_API_KEY`）を `config.ts` で読み、それだけを `ANTHROPIC_API_KEY` として入れる。どちらも無ければ手元の Claude Code のログインを使う（開発中の便宜。第三者に提供するサービスでは専用のキーを設定する） |
| `abortController` | 上限時間で `abort()` する            | 上限時間（例 `GENERATION_TIMEOUT_MS`）を環境変数にし、超えたら中断して 502 を返す。生成は数分かかることがある                                                                                                                                                                                                                                                                                                               |

## 運用の必須事項

- **同時実行数に上限を置く**（例 `MAX_CONCURRENT_GENERATIONS`）。超えた要求は 429 で断る。モデルの子プロセスと費用を抑えるため
- **利用者ごとの頻度制限**を掛ける（例 1 分 5 回）
- **利用者の入力（説明文・生成物）をログに出さない**。ログに残すのはモデル名・所要時間・費用・失敗の種類だけ
- **SDK が返した失敗の中身を利用者への応答に載せない**（`details` に理由の種類だけを入れ、本文はログに残す）
- SDK の応答は `service/` で必ず解析・検証してから使う（HTML なら形式の検査、JSON ならスキーマ検証）

## テスト

- SDK の `query()` を `vi.hoisted` + `vi.mock` で差し替え、HTTP 経由で API を呼んで **SDK に渡した `options` を検証する**テストを 1 本以上置く
  （`tools` / `strictMcpConfig` / `disallowedTools` / `settingSources` / `maxTurns` / `persistSession` と、`env` に端末の `ANTHROPIC_API_KEY` が無いこと）
- 専用のキーを設定した場合の `env` は、`config` を差し替える別ファイルのテストで確かめる（config はモジュールの読み込み時に決まるため）
- 差し替えた SDK に形の崩れた応答を返させ、その応答を使わずに失敗（502）として扱うことを確かめるテストを置く
- 実際にモデルを呼ぶ経路は自動テスト（CI）の対象外にし、次の「評価」で確かめる

## 評価（実際にモデルを呼んで確かめる）

AI を呼ぶ機能ごとに、代表的な入力と正しい答えの条件を決めておき、実際のモデルで繰り返し流して判定する。

| 項目       | 決まり                                                                                                                                                                                                                                                |
| :--------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 置き場所   | 入力と条件は `server/evals/<機能>/cases.json`。`server/package.json` に `eval`（例 `tsx --env-file-if-exists=.env evals/run.ts`）を足し、`npm run eval -w server -- <機能>` で流す                                                                    |
| ケース     | 代表的な入力を 3〜5 件。答えが入力に無いもの、または曖昧なものを 1 件は入れる（無い値を作らないかを見る）。利用者の実データは入れない                                                                                                                 |
| 回数       | 各ケース 3 回（例: 5 件 × 3 回 = 15 回呼ぶ）                                                                                                                                                                                                          |
| 呼び方     | プロンプトの組み立て・`provider/` の呼び出し・応答の検証をまとめた `service/` の関数を直接呼ぶ。HTTP・認証・DB への保存は通さない                                                                                                                     |
| 判定       | コードで確かめられる条件を使う（値の一致、語を含む、応答の検証を通る、入力に無い値を作っていない）。読みやすさのように機械で決められない質だけ、別の呼び出しで 1〜5 の採点をさせ、合格とみなす点数の下限を決める。採点の呼び出しも `provider/` を通す |
| 合格の基準 | 例: 不合格は全体で 1 回まで。「作ってはいけない」条件は全回で合格。案件で決めた基準は `docs/decisions/` に残す                                                                                                                                        |
| 回すとき   | AI を呼ぶ機能を足したとき、プロンプト・モデル・応答の扱いを変えたとき。CI では回さない                                                                                                                                                                |
| 記録       | `docs/results/<機能>-eval.md` に、日付・コミット・モデル・ケースごとの合格数・基準と判定を書く。回し直したら同じファイルを書き換える。PR 本文の「確認した結果」に合否と記録のファイルを書く                                                           |

`server/evals/` を初めて置くときは、次を確かめる。

- `server/tsconfig.check.json` の `include` に `evals/**/*.ts` があること。無ければ足す（型検査と、型情報つきの lint の対象にするため。無いと lint が解析の誤りで止まる）
- `server/eslint.config.js` の、SDK の import を止める設定の `files` に `evals/**/*.ts` があること。無ければ足す（評価からも SDK を直接呼ばず、`provider/` を通すため）
- 結果の表示は `process.stdout.write` で行う（`console` は lint が止める）

## 記録

- SDK を採用した理由と、上の指定の根拠を `docs/decisions/` に残す
- 環境変数（専用のキー・上限時間・同時実行数）は `docs/env.md` と環境変数の見本に**名前だけ**書く。値は書かない

## なぜ

例に Claude Agent SDK を使うのは、API キーが無くても、開発者の手元の Claude Code のログインで AI の機能を作って試せるためです。
第三者に提供するサービスでは、専用のキーを設定します（「Claude Agent SDK を呼ぶときに必ず指定すること」の `env` の行）。
AI の SDK は、ライセンスと利用料の両方で費用が絡むので、入れるかどうかはシン株式会社が判断します。
この規約は、入れると決まった後の書き方です。

`tools: []` は組み込みのツールを外すだけで、手元の Claude Code のログインに紐づく claude.ai のコネクタ（MCP）は外れません。
開発者の手元で動かすと、利用者の入力を処理するモデルに開発者の Gmail や Notion のツールが見え、モデルがそれを呼ぼうとして
生成が失敗します。`strictMcpConfig` と `disallowedTools` の両方を指定するのは、SDK の版が変わっても同じ事故を起こさないためです。

`env` を明示するのは、端末に別の案件向けの `ANTHROPIC_API_KEY` があると、そのキーで課金されるためです。
「このアプリ専用の変数だけを渡す」形にしておけば、開発者の環境に何が設定されていても影響を受けません。

上限時間と同時実行数を必須にするのは、生成 1 回が数分・数十円かかるためです。上限が無いと、利用者の操作 1 つで
サーバーの子プロセスと費用が積み上がります。

評価を置くのは、AI の応答が同じ入力でも毎回揺れるためです。1 回動かして期待どおりでも次も同じとは限らず、
プロンプトを直したときに別の入力で崩れても気づけません。入力と条件を決めて繰り返し流せば、
変更の前後を同じ物差しで比べられます。条件をコードで判定するのは、AI に採点させると採点そのものも揺れるためです。
件数と回数を小さく決めておくのは、1 回ごとに時間と費用がかかるためです。
CI で回さないのは、キーと費用が要り、応答の揺れで CI が不安定になるためです。
