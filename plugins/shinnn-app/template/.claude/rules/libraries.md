# ライブラリの規約

汎用の処理を、自前で書かずにライブラリで済ませるための決まりです。入れてよいライブラリの条件と選び方、使わないときに理由を残す場所も、ここに書きます。

「（検査: …）」には、その決まりを機械で確かめる仕組みを書いています。付いていない決まりは、レビューだけで確かめます。

## 探して使う

**汎用の処理**とは、このアプリに固有でない処理です。
このアプリに固有の処理は、業務の計算と判定と、このアプリの画面と API の組み立てです。
汎用の処理の例は、ファイルの形式（CSV・ZIP・Excel・PDF）の読み書き、日付と時刻の計算（営業日・時差）、文字コードの変換、画面の部品（グラフ・リッチテキストの入力）、外部との連携（メールの送信）です。
規約が自前で書くと決めているもの（API 定義のヘルパー。[api-contract.md](api-contract.md)）は、汎用の処理に含めません。
**標準の機能**とは、Node.js とブラウザに組み込みの機能です（圧縮の `node:zlib`、日付の表示の `Intl`、文字コードの変換の `TextDecoder` など）。
**既に入っている依存**とは、ルートと各パッケージの `package.json` に書いてあるライブラリです。
**自前で書く**とは、その処理を備えた標準の機能もライブラリも使わずに、処理そのものを書くことです。
文字列の分割（`split`）や正規表現のような組み込みの機能を組み合わせて書いた処理も、自前で書いたものに当たります。

- 汎用の処理は、書く前に、使えるものを探す（探し方は `/shinnn-app:feature` の「ライブラリを探す」）
- 標準の機能か既に入っている依存がその処理を備えているときは、それを使う
- 標準の機能と既に入っている依存がその処理を備えていないときは、「入れる条件」を満たすライブラリを入れて使う

## 入れる条件

- ライブラリは、import するパッケージに入れる（`npm install <名前> -w <パッケージ>`）（検査: ESLint。import したライブラリが、そのファイルのパッケージの `package.json` にあるかだけを見る）
- `devDependencies` を読んでよいファイル（テストと設定のファイル。server では種データ・評価・スクリプトと、PGlite を読み込む `src/db/` の 2 ファイルも。範囲は `docs/decisions/0002-package-manager.md` の「npm で気を付けること（幻の依存）」）だけで使うものは、`devDependencies` に入れてよい（`npm install -D <名前> -w <パッケージ>`）（検査: ESLint。範囲の外のファイルが `devDependencies` のものを import していないかだけを見る）
- ただし、import せずに読み込まれるもの（Vitest がテストの環境として読み込む jsdom など）と、リポジトリ全体で使う道具（husky など）は、ルートの `package.json` に入れる（`docs/decisions/0002-package-manager.md` の「テストの画面の環境（jsdom）はルートで宣言する」）
- ほかのパッケージにだけ入っているライブラリを使うときは、そのパッケージと同じ版を入れる
- ライセンスが許可リスト（`scripts/check-licenses.mjs` の `ALLOWED_LICENSES`）にあるものだけを入れる（検査: CI。`node_modules` の各パッケージの `license` が許可リストにあるかだけを見る）
- 直近 1 年以内に新しい版が出ているものだけを入れる
- 非推奨（`deprecated`）と示されているものを入れない
- 既に入っている依存と同じ役割のものを入れない（例: 日付のライブラリを 2 つ入れない）
- 候補が 2 つ以上あるときは、npm の週ごとのダウンロード数がいちばん多いものを選ぶ
- ただし、ルートの `CLAUDE.md` の「使わないもの」と、ほかの規約が入れないと決めているものは、ダウンロード数が多くても選ばない
- 条件を満たすライブラリは、誰にも聞かずに入れてよい
- ただし、費用が発生するもの（利用料が発生する外部サービスの SDK など）は、ルートの `CLAUDE.md` の「費用が発生するものは入れない」に従う
- ライブラリを入れた PR の本文の「変更点」には、「何を / なぜ / 代替案」を 1 行ずつ書く

## 使わないとき

- 汎用の処理を自前で書くときは、その関数かクラスの JSDoc に `ライブラリを使わない理由:` で始まる行を書く
- 理由の行には、探した候補の名前と、候補ごとの使わない理由を書く（`ライブラリを使わない理由: <名前>（<理由>）、<名前>（<理由>）`）
- 候補が見つからなかったときは、理由の行に、探した語と「見つからなかった」を書く
- 入力への守り（大きさや数の上限、制御文字の除去）が要ることだけを理由に、自前で書かない

## なぜ

探さずに自前で書いてよいものを、このアプリに固有の処理に限るのは、線引きを判断しやすくするためです。
固有の処理は、どのライブラリにもありません。

組み込みの機能を組み合わせて書いた処理を自前で書いたものとするのは、探す手順と理由の行を飛ばす抜け道を作らないためです。
CSV の分割も、`split` と正規表現だけで書けてしまいます。

汎用の処理をライブラリで済ませる理由は 2 つあります。
1 つ目は、細かい場合の扱いを誤らないためです。
汎用の処理には、見落としやすい場合が多くあります（CSV の引用符の中の改行、日付の月末とうるう年など）。
広く使われているライブラリは、多くのアプリでそうした場合に当たり、直されてきています。
2 つ目は、自分たちで直すコードを減らすためです。
自前のコードの不具合と脆弱性は、自分たちで見つけて直すほかありません。
ライブラリの脆弱性は、Dependabot と `npm audit` が知らせます。

標準の機能と既に入っている依存を先に使うのは、依存を増やさないためです。
依存が増えるほど、更新と脆弱性の確かめの手間が増えます。

ライブラリを import するパッケージに入れるのは、パッケージを単体で配布したときに落ちないようにするためです。
ワークスペースでは、ほかのパッケージのライブラリも同じ `node_modules` に並びます。
そのため、`package.json` に書き忘れても、手元では動いてしまいます。
`devDependencies` を読んでよいファイルだけで使うものを `devDependencies` に入れてよいのは、本番で使わないものを、本番の環境に入れないためです。
リポジトリ全体で使う道具をルートに入れるのは、どのパッケージにも属さないからです。
ほかのパッケージと同じ版を入れるのは、同じ書き方が片方のパッケージでだけ通る状態を避けるためです。

入れる条件を決めておくのは、誰にも聞かずに入れても困らないようにするためです。
利用者はエンジニアではないので、ライブラリの良し悪しを判断できません。
ライセンスを許可リストに限るのは、費用や義務が生じるライセンスを、聞かずに入れないためです。
許可リストに無いライセンスは、シン株式会社が判断します。
1 年以内に新しい版が出ているものに限るのは、更新が止まって直せなくなったライブラリを避けるためです。
非推奨のものを入れないのも、同じ理由です。
同じ役割のものを 2 つ入れないのは、同じことをするコードの書き方を 1 つにそろえるためです。
PR の本文に「何を / なぜ / 代替案」を書くのは、選んだ理由と比べた候補を、レビューする人が確かめられるようにするためです。

候補からダウンロード数のいちばん多いものを選ぶのは、広く使われているもの（デファクトスタンダード）を使うためです。
使われている数が多いライブラリほど、不具合と脆弱性が早く見つかって直ります。
使い方の情報も多いので、Claude が書き方を誤りにくくなります。
ダウンロード数を基準にするのは、選び方を、誰が確かめても同じ答えになる数にするためです。

「使わないもの」と、ほかの規約が入れないと決めているものをダウンロード数で選ばないのは、理由があって外したものだからです。
NestJS と NgRx を外した理由は、`docs/decisions/0001-template-stack.md` の「採らなかったもの」にあります。
ほかの規約が入れないと決めているものの理由は、その規約の「なぜ」にあります。

使わない理由を JSDoc に書くのは、そのコードを後で直す人が、理由を読んで判断できるようにするためです。
理由が無くなったら（ライブラリが、要る機能を備えたときなど）、ライブラリに置き換えられます。
PR の本文に書いた理由は、コードを直すときには読まれません。
行の書き出しを `ライブラリを使わない理由:` にそろえるのは、自前で書いた汎用の処理を `git grep` で一覧にするためです。

守りが要ることだけを理由にしないのは、守りはライブラリを使っても書けるからです。
上限は、ライブラリの設定（1 つのセルの長さの上限など）か、ライブラリが返す行やファイルを数えながら確かめられます。
守りのために処理の全体を自前で書くと、守りと関係ない部分（引用符や改行の扱い）の誤りまで、自分たちで負うことになります。

API 定義のヘルパーを汎用の処理に含めないのは、自前で書く理由が [api-contract.md](api-contract.md) の「なぜ」にあるからです。
