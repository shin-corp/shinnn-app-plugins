# 振り返りを残す

作業した Issue に短い振り返りを残し、引き継ぎに効くことを 1 か所に集める。
**長く書かない。** 読まれない記録は無いのと同じ。

## 1. 対象の Issue を決める

今のブランチ名（`feature/<番号>-<slug>`）から Issue 番号を取る。分からなければ聞く。

## 2. Issue に 3 行コメントする

```
gh issue comment <番号> --body-file <本文のパス>
```

**この 3 行だけ**を書く。各 1〜2 文。

| 見出し | 書くこと | 書かないこと |
|:--|:--|:--|
| 詰まり | 想定と違って時間を取られたこと | 詰まらなかった作業の説明 |
| 学び | 次に同じことをする人が知っておくと早いこと | コードを読めば分かること |
| 次に試す | 次にやること、または試したい改善 | 感想 |

該当が無い項目は「無し」と書く。**無理に埋めない。**

## 3. 引き継ぎメモに追記する

pin されている「引き継ぎメモ」Issue（番号は `.shinnn/setup.json` の `handoverIssue`）に、
**引き継ぐ人が知らないと困ることだけ**を追記する。

- 仮置きで進めた決定と、その理由
- 仕様書に書ききれていない前提（外部システムの癖、手で入れたデータ など）
- 既知の未整合。直っていない不具合
- 環境の起こし方で、README に書いていないこと

日々の作業ログは書かない（それは Issue と git 履歴が持っている）。

## 4. 進捗スナップショットを更新する

```
node scripts/progress-snapshot.mjs
```

`docs/progress.md` を Issues から生成し直す。**このファイルを手で書かない**（`.claude/settings.json` の deny が止める）。
`gh` が使えない環境では、このスクリプトは動かない。その場合はスキップし、その旨を報告する。

## 5. 報告

コメントした Issue の番号と、引き継ぎメモに足した項目を一覧で示す。

**コミットとプッシュは人の指示があるときだけ行う。**

## このスキルの対象外

開発の進め方そのものについての気づき（手順を SKILL に落とす、規約を直す など）は、
`session-retro` の担当。標準そのものを直すべきだと思ったら、そちらを使う。
