# 画面を 1 つ追加する

このスキルは順番だけを示す。守る決まりは `client/CLAUDE.md` と `.claude/rules/` の client の規約
（`client-architecture.md`・`client-coding-conventions.md`・`client-styling.md`）にある。**層を新しく作らない。**

最初に手本のサンプル `client/src/app/features/items/` を読む（サンプルの `items` を消した後は、既存の機能を手本にする）。
読むと、`client/CLAUDE.md` と client の規約も読み込まれる。

**画面のコードを書く前に、手順 0 で見た目の方針を確かめる。方針が空なら、Skill ツールで `frontend-design:frontend-design` を
呼んで、デザインの指導を受ける。指導の案で方針を決める。手順 3 で、方針と既にある画面に沿って画面の案を決める。
書き終えたら、手順 9 で作った画面を撮って見直す。どれも飛ばさない。**
ただし、手順 9 を飛ばしてよいときと、いつ指導を受けるかの決まりは、`.claude/rules/client-styling.md` の「デザインの指導」にある。
元のアプリの作り直しで、指導を受けずに進めるときの手順は「作り直しのとき」にある。

## デザインの指導を受ける

手順 0 で見た目の方針を決めるときと変えるときに、次のとおり受ける。

1. 材料を集める。

   | 材料 | 取る場所 |
   |:--|:--|
   | アプリの目的とやること | `docs/仕様書.md` の「目的」「スコープ」 |
   | 使う人と場面（どんな人か、業務と IT の慣れ、どこで・どの機器で・どのくらいの頻度で使うか） | `docs/仕様書.md` の「見た目の方針」の「使う人と場面」。空か分からないところがあれば、依頼の言葉と今ある文書から推測して書く（書き方は規約の「デザインの指導」） |
   | 見た目の方針（配色・書体・骨組み・大事にすること） | `docs/仕様書.md` の「見た目の方針」。空なら「空」と書く |
   | 今回の対象 | 利用者の依頼の言葉と、これから作る画面とその受入条件（方針を変えるだけなら、画面と受入条件は省く） |
   | 今の画面 | 既にある画面を、手順 9 の 1 のとおりに撮った画像の場所。画面がまだ無ければ省く |

2. Skill ツールで `frontend-design:frontend-design` を呼び、`args` に材料と次の条件を渡す。
   - 業務の画面なので、目新しさより、使う人が迷わず・間違えずに速く進められることを優先する
   - 部品は Angular Material、見た目は Tailwind のユーティリティで作る。守る決まりは `.claude/rules/client-styling.md`
     （「テーマと書体」を含む）。案が規約とぶつかるときは規約に従う
   - `mergePolicy` が `auto-merge` なら、作る前の案を利用者に確かめない。案を 1 つに決めて進める

## `frontend-design` が無いとき

手順 0 で指導を受けるときに、スキルの一覧に `frontend-design` が無ければ、`claude plugin install frontend-design@claude-plugins-official --scope local`
を実行する。配布元に無いと出て失敗したら、`claude plugin marketplace add anthropics/claude-plugins-official` を実行してから
入れ直す。入れたものは、次に起動したときから使える。

- 「見た目の方針」が空なら、ここで止めて、利用者に起動し直してもらう。起動し直した後に手順 0 から始める
- ただし、`mergePolicy` が `auto-merge` なら止まらない。使わずに進め、同梱のテーマのままにする。起動し直すと指導を受けられることを、最後の報告に書く
- 方針を変える依頼で、方針が埋まっていれば、今回は使わずに進める。新しい方針の案は、依頼の言葉と規約に沿って立てる
- 入れられなかったときは、そのことを利用者に伝えて使わずに進める。方針が空なら、決めずに空のまま残し、同梱のテーマのままにする

## 作り直しのとき

`docs/仕様書.md` の「見た目の方針」の「再現の度合い」が「元に寄せる」のとき（`/shinnn-app:feature` の作り直しで書く）は、
`frontend-design` を呼ばない（規約 `client-styling.md` の「デザインの指導」）。手順 0・3・9 を次のように進める。ほかの手順は同じ。

| 手順 | 進め方 |
|:--|:--|
| 0. 見た目の方針 | 1〜3 と 5 を行わない（方針は、`feature` が元のアプリから取り出して仕様書に書いてある）。4 のテーマの生成と書体の入れ方は、`client/src/theme.css` がまだ無いときと、仕様書の色・書体を変えたときだけ行う。そのときは、仕様書の「見た目の方針」に書いた元の主な色を `--primary-color` に、ほかの系統の色を `--secondary-color`・`--tertiary-color` に、背景と文字の灰色を `--neutral-color` に渡す。書体は、元の書体の名前を書体の並びに入れる（規約の「テーマと書体」）。ただし、`[デザイン]` の Issue（`/shinnn-app:design-review` で利用者が入れると決めた改善案）が見た目の方針（配色・書体）を変えるときは、「0. 見た目の方針を確かめる」の 3 と 4 を、Issue の「変えること」のとおりに行う（元の色・書体に戻さない） |
| 3. 画面の案 | 元の画面の画像（`screenshots/original/`）と元のアプリのコード（HTML・テンプレート・CSS）を読み、配置・項目の順・文言・ボタンの位置を元に合わせる。元の画像が無い画面は、元のコードから配置・項目・文言・ボタンや操作の並びを読み取り、見た目はほかの画面（元から取り出した色・書体のテーマ）に合わせる。元に無い状態（読み込み中・0 件・失敗）は、`client/CLAUDE.md` の「画面の決まり」に従って足す。`[デザイン]` の Issue（`/shinnn-app:design-review` で利用者が入れると決めた改善案）で変える点は、本文の「変えること」のとおりにし、元に合わせない（規約の「デザインの指導」） |
| 9. 作った画面の見直し | 2 と 3 の代わりに、1 で撮った画面と元の画面を並べた画像を、下の形で作る。並べた画像を Read で開き、配置・色・項目・文言の違いと崩れを挙げて直す。直したら撮り直して並べ直す。直すのは 2 巡までにする。直さない違い（規約に従うと変わる点など）は、`docs/移植対応表.md` のその画面の行の「違い」に書く。9 の 4 で PR 本文の「確認した結果」に書くのは、元と並べて見直した画面と直した点。元の画像が無い画面は、並べずに、撮った画面と元のコードの読み取り（項目・文言・並び）を照らして直す。撮れないときは、9 の 5 と同じに飛ばす。`[デザイン]` の Issue で変えた点は、元と並べても戻さない。移植対応表のその画面の行を「違う」にし、「違い」に書く |

並べた画像は、次の形で作る。左に元、右に新を置く。元の画面を URL で撮れるとき（`feature` の作り直しの (b)）は、`--left` に URL を渡してよい。

```
node ${CLAUDE_PLUGIN_ROOT}/scripts/capture-screens.mjs compare --left screenshots/original/<元の画面の画像> --right screenshots/<画面の名前>.png --out screenshots/compare/<画面の名前>.png
```

元の画面の画像が無い画面の扱いは、規約 `client-styling.md` の「デザインの指導」にある。その画面では、PR 本文の「確認した結果」に、元の画像が無かったことを書く。

## 0. 見た目の方針を確かめる

作り直し（「再現の度合い」が「元に寄せる」）では、「作り直しのとき」の 0 の行のとおりに進める。

`docs/仕様書.md` の「見た目の方針」を読む。埋まっていれば、その方針に沿って「1. 受入条件と API 定義を確かめる」へ進む。
空か節が無ければ、先に方針を決める。アプリ全体の見た目を変えたいと頼まれたときも、ここから始める。
すでに画面があるアプリで方針が空のときは、今の見た目のまま方針に書く案も示す（テーマを変えると、今ある画面の見た目も変わるため）。
変え方まで指定された依頼（色の値・書体の名前など。`/shinnn-app:design-review` で入れると決めた改善案を含む）では、
下の 1 と 2 を行わず、指定のとおりに下の 3 から進める（規約の「デザインの指導」のただし書き）。

1. 「デザインの指導を受ける」のとおり指導を受け、使う人と場面・配色（主色と、4〜6 色の役割）・書体・
   画面の骨組み・大事にすることの案を立てる。材料には、仕様書の「画面」も足す
2. 案を利用者に見せて確かめる（色の値と、画面のどこに使うか。書体の名前）。渡した色から Material が濃淡を作るので、
   出来上がる値は少し変わることも伝える。ただし、`mergePolicy` が `auto-merge` なら、確かめずに 3 に進む
3. 決めた内容を仕様書の「見た目の方針」に書く（節が無ければ「画面」の章の終わりに足す）。配色は、生成に渡した色を書く
4. テーマと書体を入れる（決まりは `client-styling.md` の「テーマと書体」）。案で主色のほかの色も決めたなら
   `--secondary-color` / `--tertiary-color` でも渡す。テーマを生成し直すときも同じコマンドで、`--force` が上書きする。
   どちらもリポジトリのルートで実行する（`-w client` が `client` を指す）

   ```
   npm exec -w client -- ng generate @angular/material:theme-color --primary-color=<主色> --is-scss=false --directory=src/ --interactive=false --force
   npm install <書体のパッケージ> -w client
   ```

   生成した `client/src/theme.css` を `styles.css` の同梱のテーマの代わりに読み込む。書体のパッケージも読み込み、
   書体の名前を `styles.css` の決まった場所に入れる。画面の骨組みのうちアプリ全体に関わるもの（ツールバーなど）は、
   `app.component.ts` のシェルに入れる

5. `npm run dev` で起動し、利用者に画面を開いて見た目を確かめてもらう（開発用の通行証の入れ方は `README.md` の
   「画面から API を呼ぶための通行証（開発中）」）。ただし、`mergePolicy` が `auto-merge` なら、手順 9 で Claude が見直す

## 1. 受入条件と API 定義を確かめる

Issue の受入条件を読み、作る画面と要るデータを確かめる。`shared/src/api/<機能>.ts` に API 定義が無ければ、
先に `/shinnn-app:add-api` で shared と server を用意する（同じ PR）。

## 2. 置き場所とルート

`features/<機能>/` を作り、`<機能>.routes.ts` を `app.routes.ts` から `loadChildren` で繋ぐ。
置き場所の決まりは `.claude/rules/client-architecture.md` の「新規ファイルの配置判断」。

## 3. 画面の案

作り直し（「再現の度合い」が「元に寄せる」）では、「作り直しのとき」の 3 の行のとおりに進める。

見た目の方針と既にある画面（手本）にそろえて、この画面の配置・情報の優先度・読み込み中と 0 件のときの案内を決める（そろえるものは規約 `client-styling.md` の「デザインの指導」）。
指導は受けない（規約 `client-styling.md` の「デザインの指導」）。
失敗のときの文言は `describeError()` が出すので、出し方だけを決める（`client/CLAUDE.md` の「画面の決まり」）。
色と書体は、方針の配色と書体を使う。
この画面だけで使う色や書体が要るときは、利用者に確かめてから（`auto-merge` なら確かめずに）、役割の名前で `styles.css` の `@theme` に足す。
その色や書体は「見た目の方針」の「画面だけの追加」にも書く（`client-styling.md` の「テーマと書体」）。

## 4. ページのコンポーネント

規約 `client-coding-conventions.md` の「コンポーネント」に従って作る。

## 5. 取得と表示

`client/CLAUDE.md` の「画面の決まり」（取得と 3 状態、一覧）と「API 呼び出し」に従う。

## 6. 入力

`client/CLAUDE.md` の「画面の決まり」（入力）に従う。

## 7. スタイル

手順 3 の案に沿って、`.claude/rules/client-styling.md` に従って作る。

## 8. テスト

`.claude/rules/testing.md` の「画面のテスト」に従う。画面に現れる受入条件（表示・操作）は、ここで `AC-n` のテストにする。

## 9. 作った画面を見直す

作り直し（「再現の度合い」が「元に寄せる」）では、1 で撮った後を「作り直しのとき」の 9 の行のとおりに進める。

1. 開発用のサーバーを起動し（`/shinnn-app:dev-stack-start`）、プラグインのスクリプトで画面を撮る。
   URL は、`dev-stack-start` が示す画面の開き方に、この画面のパスを足したもの

   ```
   node ${CLAUDE_PLUGIN_ROOT}/scripts/capture-screens.mjs shot --url <画面の URL> --out screenshots/<画面の名前>.png --token
   ```

   `--token` は、`npm run token -w server` で開発用の通行証を発行し、画面の読み込みの前に `localStorage` の `token` に入れる（通行証の値は出さない）。
   認証の要らない画面では付けない。
   ブラウザはスクリプトが探す。環境変数 `CHROME_PATH` に値があれば、スクリプトはそのブラウザを使う。
   `CHROME_PATH` の値は、Bash で出して確かめない（変数だけを出すコマンドは、許可があっても確認が出る）。
   撮った画像は `screenshots/` の下に置く。`screenshots/` は、本物のデータが写りうるので、`.gitignore` で git の対象から外してある。
   `.gitignore` に `/screenshots/` の行が無ければ、足してこの PR に入れる（スクリプトは、git の対象の場所には書かずに止まる）
2. 撮った画像を Read で開き、崩れ（何を崩れとするかは規約 `client-styling.md` の「デザインの指導」）を探す。
   手順 3 で決めた配置と、方針の配色と書体になっているかも見る。指導は受けない（規約 `client-styling.md` の「デザインの指導」）
3. 崩れがあれば直して、撮り直す。直すのは 1 巡にする。直しきれない崩れは、4 で PR 本文に書く
4. PR 本文の「確認した結果」に、見直した画面と直した点と、直しきれなかった崩れを 1 行で書く
5. 撮れないときは、飛ばして先に進む（規約の「デザインの指導」のただし書き）。PR 本文の「確認した結果」に、見直していない理由を書く

## 確認

```
npm run check -w client
```

画面のパッケージの型検査と lint だけを通す。まとめての `/shinnn-app:check` は、`/shinnn-app:pr` が PR を出す前に 1 回通すので、ここでは走らせない。
