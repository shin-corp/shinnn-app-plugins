# メッセージ規約

エラーや通知の文言は **`server/resources/messages.json` にだけ**書き、
そこから `server/src/util/message/message-keys.ts` を生成します。

## 編集の手順

1. `server/resources/messages.json` にエントリを追加する（`"<キー>": { "type": "INFO | WARN | ERROR | FATAL", "message": "文言" }`）
2. `npm run messages` を実行する（`server/scripts/gen-message-keys.mjs` が動く）
3. 生成された `server/src/util/message/message-keys.ts` を**そのままコミットする**

- **生成物を手で編集しない。** 次の生成で失われます
- 生成物もコミットします（クローン直後に `npm run messages` を実行しなくても型検査が通るように）
- メッセージを消すときは、使っている箇所を先に消す。生成物の型エラーで気づけます

## キーの付け方

- `APP_<領域>_<内容>` を大文字のスネークケースで書く（例: `APP_VALIDATION_FAILED`、`APP_ITEM_NOT_FOUND`）
- 先頭は必ず `APP_`。機能固有のものは領域に機能名を書く（item なら `APP_ITEM_`）
- **キーを文字列リテラルで書かない。** `MessageKeys.APP_ITEM_NOT_FOUND` の形で参照する
- 1 つの状況に 1 つのキー。似た文言のキーを増やさない。文言だけ違うなら JSON 側を直す

## 文言の書き方

- 日本語。読み手はアプリの利用者で、開発者ではない
- **「何が起きたか」と「どうすればよいか」を書く。**
  「エラーが発生しました」だけにしない
- 内部の情報（テーブル名・SQL・スタックトレース・ファイルパス）を文言に入れない。
  調査に必要な情報は `CommonException` の `details` かログに入れる
- 変数を埋め込む場合はプレースホルダ（`%1` / `%2` …）を使う。文字列連結で組み立てない

## なぜ

文言を 1 ファイルに集めるのは、同じ意味の言い回しが画面ごとにばらけるのを防ぐためと、
後から一括で見直せるようにするためです。ソースに散らばった文字列は、誰も全体を確認できません。

キーを生成物にするのは、存在しないキーを参照したときに**型エラーで止める**ためです。
文字列リテラルのままだと、綴りを間違えても実行するまで気づけません。

内部情報を文言に入れないのは、それが利用者の画面にそのまま出るからです。テーブル名や SQL が
見えると、攻撃の手がかりになります。
