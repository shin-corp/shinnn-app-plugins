# 作りたいことを形にする

作りたいことを受け取り、1 本ずつ Issue・仕様・実装・テストまで通す。
**1 Issue = 1 ブランチ = 1 PR** を崩さない。**要望を分けるのは Claude の仕事**で、利用者に分けさせない。

引数（`$ARGUMENTS`）に作りたいことが書かれていれば、それを出発点にする。
無いとき、または「続き」と言われたときは「続きから始める」に進む。続きも無ければ、作りたいことを最初に聞く。

## 準備. 道具とルールの版を確かめる

このスキルを読み込んだときに確かめた結果:

!`node "${CLAUDE_PLUGIN_ROOT}/scripts/check-plugin-version.mjs"`

上に結果が出ていなければ、同じコマンドを自分で実行する。結果に応じて、作業を始める前に次を行う。

| 結果 | すること |
|:--|:--|
| プラグイン: 古い | 「更新:」の 2 つのコマンドを順に実行する。終わったら利用者に「道具を新しくしました。`/reload-plugins` と入力してから、もう一度『続きをお願いします』と伝えてください」と頼み、**ここで止まる**（新しい手順は、読み込み直すまで使われない。`/reload-plugins` は利用者にしか打てない） |
| ルール: 古い | 利用者に「ルール（決まりごと）の新しい版が届いています。`/shinnn-app:update-rules` で取り込めます」と伝えてから、頼まれた作業を進める |
| 最新、または確かめられない | そのまま進める（オフラインなどで確かめられなくても止めない） |

## 0. 大きさを見る

PR 1 本の目安は、**使う人から見て 1 つできるようになること**。変更するファイルが 10 個くらいで、レビューする人が 15 分で読める量。

| 要望 | 進め方 |
|:--|:--|
| 1 本に収まる | 1 から順に進める |
| 収まらない（できるようになることが 2 つ以上ある、など） | 同じフォルダの `plan.md` で計画を作り、利用者の確認を取る。先頭の Issue を 2 から進める |

**文言 1 つの直しや不具合の修正も、同じ流れ（Issue → ブランチ → PR）で進める。** `main` で直接編集しない。違うのは次だけ。

- 不具合の Issue は `gh issue create --template bug.yml` で作り、ブランチは `fix/<Issue 番号>-<slug>` にする
- 受入条件の立て方（不具合の修正と、振る舞いが変わらない変更）は `.claude/rules/testing.md` の「何をテストするか」に従う。
  受入条件を足さないときは、Issue の受入条件の欄と PR 本文の「対応した受入条件」に「無し（文言だけの変更）」のように書く
- まれに落ちるテストなど、テストそのものの不具合は、直す前に `pr` の手順 1 の条件で落ちる回数を測っておく

**依存の脆弱性の勧告を直す依頼は、不具合の流れ（`bug.yml`・`fix/`）にしない。** CI の「依存の脆弱性」の失敗や注記を貼り付けた依頼も、
`npm audit` の勧告を直す依頼も、`/shinnn-app:check` の「`npm audit` で勧告が出たとき」で進める
（`main` の上で頼まれたときは、その節の「元の PR が無いとき」の順）。直しの Issue とブランチは、その節が決める。

**この道具を使わずに作ったアプリ（以下「元のアプリ」）を作り直すときも、計画から始める（`plan.md`）。** 違うのは次だけ。

- このフォルダに `.claude/rules/.standards-version` が無いときは、テンプレートから作ったフォルダではない。作り直しを始めず、
  `/shinnn-app:setup` の手順 0 の 1 の案内を伝えて止まる
- 依頼に元のアプリのフォルダの場所が無ければ聞く（「1. Issue を作る」の確認の質問の数には入れない）。
  そのフォルダはこのフォルダの外に置いたままにし、このフォルダにコピーしない。コピーすると、git・lint・CI の対象になる
- 元のアプリのフォルダを `--add-dir` で足さずに起動していると、読むときに確認が出る。そのときは `/exit` で終了し、
  `claude --add-dir <元のアプリのフォルダ>` で起動し直すよう頼む。起動し直した後は、計画を作る前なら同じ依頼を、
  作った後なら「続きをお願い」を入力してもらう
- 止まるときの報告（7）に、次も `claude --add-dir <元のアプリのフォルダ>` で起動することを添える
- 元のアプリは読むだけで、書き換えない。`--add-dir` で足したフォルダへの書き換えは、確認なしで通る（テンプレートの権限の設定は
  `acceptEdits`）。Edit・Write で開くのは、このフォルダの中のファイルだけにする
- 元のアプリのコードを写さない。書き方は規約と手本に従う。CLAUDE.md と規約の「既存の処理」「既存の機能」は、このフォルダの中だけを指す
- 元のアプリの `.env` で始まるファイルは、`.env.example` のほかは読まない。権限の設定が止めるのは `.env`・`.env.local`・
  `.env.production` などの決まった名前だけで、`.env.prod` のような名前は止まらない
- 元のアプリを検索するときは Grep ツールを使い、`glob` に `!**/.env*` を付けて `.env` で始まるファイルを外す。
  Bash の `grep -r` は使わない（`.env` の中身も結果に出る）
- 設定の項目の名前が要るときは、`.env.example` を Read ツールで読む（`cat` は権限の設定で止まる）。
  `.env.example` が無ければ、コードの `process.env.` の参照から拾う
- 計画は、元のアプリの画面・API・保存しているデータの形（テーブルと項目）を読んで、`plan.md` の「1. 分ける」の単位に分ける。
  データそのもの（DB のファイルや書き出したファイル）は読まない
- 受入条件は、元のアプリの今の振る舞いから立てる。規約に従うと振る舞いが変わる点（認可が無かった操作など）は、
  規約に従う側で仮置きし、元のアプリとの違いを Issue の「未決」に書く
- 本番のデータの移し替えと、新しいアプリへの切り替え（公開先・URL・利用者への周知）は、計画の「今回やらないこと」に書く。
  この 2 つは「あとで足せます」とは伝えず、シン株式会社の担当者に相談するよう、利用者に伝える

## 1. Issue を作る

- **確認の質問は 3 つまで。** 分からないことは仮置きし、Issue の「未決」に書く（質問を重ねて止めない）
- 聞くなら、この 3 つから選ぶ: 何のためか / 誰が使うか / 保存するデータは何か
- `gh issue create --template feature.yml` で作る。本文には次を必ず入れる

| 見出し | 内容 |
|:--|:--|
| 目的 | 何が嬉しいのかを 1〜2 行 |
| 画面 | 追加・変更する画面と、そこでできること |
| データ | 保存する項目と、その意味。**誰が見られて誰が変えられるか**（利用者ごと / 全員で共有 / 管理者だけが変える、など） |
| 受入条件 | `AC-n` の番号を振る。**1 行 = 1 つの確認できる事実**として書く。利用者ごとのデータなら「他の利用者のデータは見えず、変えられない」を 1 つ入れる |
| 未決 | 仮置きした点。人に確認してから決めること |

受入条件の番号は、`docs/仕様書.md` と open な Issue で**使われている最大の番号の続き**から振る（決まりは `.claude/rules/testing.md` の「何をテストするか」）。
受入条件ごとに「この AC に対応するテストがあるか」を、あとで CI が機械的に確かめる。
**測れない書き方（「使いやすいこと」など）をしない。**

計画から進めるときは、Issue は `plan.md` で作ってあるので 2 に進む。

## 2. 仕様書に反映する

Issue の `AC-n` が、仕様書やほかの open な Issue で使っている番号と重なることがある（人がフォームで立てた Issue は `AC-1` から振ってある）。そのときは、仕様書に追記する前に、使われている最大の番号の続きに振り直す。Issue の本文も同じ番号に直す。
`docs/仕様書.md` の該当章に、Issue と同じ内容を追記する。追記した後は、仕様書を正とする（ルートの `CLAUDE.md` の優先順位。CI の受入条件の検査も仕様書を見る）。Issue は作業の単位として扱う。
**着手する Issue の分だけ**入れる。計画にある他の Issue の受入条件を先に入れると、テストがまだ無いので CI（`check-ac-coverage`）が落ちる。
既存の記述と食い違う場合は、**書き換えずに人へ報告する**（仕様書の版は人が管理する）。

## 3. ブランチを作る

```
git fetch origin main
git switch -c feature/<Issue 番号>-<英小文字の短い slug> origin/main   # 不具合の修正は fix/<Issue 番号>-<slug>
gh issue edit <Issue 番号> --remove-label status:next --add-label status:doing
```

例: `feature/12-item-archive`

**ブランチは必ず `origin/main` から切る。** マージされていない別の PR のブランチから切らない。
前の PR が要る Issue は、そのマージを待つ。

## 4. 実装する（この順を守る）

| 順 | 場所 | やること |
|:--|:--|:--|
| 1 | `shared/src/api/` | API 定義。**データの形の唯一の正** |
| 2 | `server/src/db/schema/` | テーブルを足すなら先にスキーマ（`/shinnn-app:db-migrate`） |
| 3 | `server/src/service/` | 業務処理 |
| 4 | `server/src/api/<機能>/` | router と controller |
| 5 | `client/src/app/features/<機能>/` | 画面 |
| 6 | `server/tests/` と画面の `.test.ts` | 受入条件 `AC-n` ごとにテスト。API の振る舞いはサーバー、画面に現れることは画面のテスト（`.claude/rules/testing.md`） |

**参照される側を先に書く。** shared を変えずに server や client だけ直したくなったら、それは API 定義の考え漏れなので shared に戻る。

応答を終えるたびに、触ったファイルの lint と関連テストを hook が走らせる。各段階では、その結果を直してから次へ進む
（全部書いてからまとめて直さない）。段階ごとに `/shinnn-app:check` をまとめて走らせない（`pr` が出す前に 1 回通す）。
1〜4 とサーバーのテストは `/shinnn-app:add-api`、5 と画面のテストは `/shinnn-app:add-screen` の手順で進める。
アプリ全体の見た目（配色・書体・画面の骨組み）を変えるときは `add-screen` の「0. 見た目の方針を確かめる」から、
今ある画面の見た目だけを変えるときは `add-screen` の「3. 画面の案」と「7. スタイル」で進める。
守る決まりは、それぞれが名指しする規約にある。

## 5. コミットする

`.claude/rules/git-workflow.md` の「コミットメッセージ」「コミットの分け方」を読み直してから、それに従ってコミットする。

## 6. 仕上げ

```
/shinnn-app:pr
```

`pr` が手順 1 で `check` を通し、最後に `retro` で振り返りまで残す。どれも利用者に打たせず、ここで続けて行う。
計画の Issue なら、続けて 7 に進む。計画の無い 1 本なら、`/shinnn-app:session-retro` を 1 回行ってから、7 の形で報告して終える。
ただし、`check` の「`npm audit` で勧告が出たとき」で直しの Issue（題が `[依存] 依存の脆弱性の修正`）を作ったか見つけ、
それが `status:next` のときは、終える前にその Issue を、`check` の同じ節の 2 の 5 で進める（計画の Issue でも、7 で次の Issue より先に進める）。
進めてよいかを利用者に聞かない。直しは、頼まれた変更を出すための続きの作業で、依頼の範囲を広げることには当たらない。
利用者への報告は、直しの PR まで出してから 1 回にまとめる。

## 7. 次の Issue へ進む（計画があるとき）

PR を出したあとの動きは `.shinnn/setup.json` の `mergePolicy` で決まる（キーが無ければ `human`）。

| `mergePolicy` | PR を出したあと |
|:--|:--|
| `human`（既定） | PR はドラフトのまま人に渡す。**今の PR を待たずに作れる** `status:next` の Issue があれば、それを 2 から進める |
| `self-review` | `pr` がマージまで済ませたら、`git switch main && git pull --ff-only` のあと `plan.md` の「依存が解けた Issue を進める」を行い、`status:next` の先頭を 2 から進める。`pr` がマージせずに人に渡したときは `human` と同じ |

どちらでも、次の Issue を選ぶ前に「続きから始める」の 1 の後半（待っている PR への `main` の取り込み）を行う。
次の Issue は「続きから始める」の 4 の順で選ぶ（題が `[依存] 依存の脆弱性の修正` の Issue を先に取る）。

次のときは止まる。

- 進められる `status:next` の Issue が無い（計画が終わった、または残りが PR のマージ待ち）
- 実装の途中で仕様の穴が見つかり、人に返した
- `pr` のレビューが収束しない（`pr` の手順 2 で直しきれず、PR を作って人に渡した）、または CI が直らない

1 つ目の理由（進められる Issue が無い）で止まるときは、報告の前に `/shinnn-app:session-retro` を 1 回行い、
このセッションで出した PR の振り返りを、次から役立つ形に置き直す（PR ごとには行わない）。

止まるときは、次の 3 つを**利用者の言葉で**報告する。

- できたこと（PR の番号と、使う人から見て何ができるようになるか）
- 待っていること（誰が何をすれば続きを作れるか。例: 「PR #14 を取り込んでもらえれば、在庫の一覧を作れます」）
- 次に「続きをお願い」と言われたら着手する Issue

## 途中で要望が増えたとき

作業中に別の要望を言われたら、**今のブランチに混ぜない。** `plan.md` の「計画に足す」で Issue にし、今の Issue を最後まで進める。
今の Issue の受入条件を変える話なら、勝手に変えず利用者に確認し、決まったら Issue と仕様書を直す。

## 続きから始める

0. **Issue に紐づかない変更**が手元にあれば、先にそれを流れに乗せる。`main` の上に未コミットの変更か `origin/main` より先のコミットがある、
   または今のブランチの名前が `feature/<番号>-`・`fix/<番号>-` で始まらないときがこれに当たる
   1. その変更の Issue を手順 1 で作る。振る舞いが変わる変更なら、手順 2 で受入条件を仕様書に足す
   2. `git switch -c feature/<Issue 番号>-<slug>`（不具合の修正は `fix/`）で作業ブランチを作る（未コミットの変更もコミットも、そのまま移る）。
      未コミットの変更があれば、ここで手順 5 の決まりでコミットする（3 の切り替えで衝突しないように）
   3. `main` にコミットがあったときは、`git switch -C main origin/main` で手元の `main` を `origin/main` に戻し、
      作業ブランチに `git switch` で戻る。コミットは作業ブランチに残るので、`git reset --hard` と違って何も失わない
   4. 手順 4 以降（残りの実装とテスト、コミット、`pr`）を進める
1. 作業途中のブランチ（`git status` に変更がある、または PR の無い `feature/`・`fix/` ブランチ）があれば、その Issue を先に仕上げる。
   open な PR の本文に `依存の脆弱性: NG（… #<番号> で直す）` の行があり、#<番号> の Issue が閉じていれば、その PR に `main` を取り込む
   （`check` の「`npm audit` で勧告が出たとき」の 2 の 4）
2. `git switch main && git pull --ff-only`
3. `plan.md` の「依存が解けた Issue を進める」を行う
4. 題が `[依存] 依存の脆弱性の修正` の `status:next` の Issue があれば、計画や番号の順より先に取る（`check` の「`npm audit` で勧告が出たとき」の 2 の 5 で進める）。
   無ければ、open な計画（タイトルが `[計画]` の Issue）の「作る順番」で `status:next` の先頭を取る。計画が無ければ `status:next` の Issue を番号の小さい順に取る
5. 取った Issue を 2 から進める（直しの Issue は 4 のとおり）。取れる Issue が無ければ、7 と同じ形で報告して止まる

## 迷ったとき

- 規約の理由が分からない: `/shinnn-app:why <話題>`
- 実装の途中で大きすぎると分かった: 残りを Issue に切り出して計画に足す（`plan.md`）
- 片方だけでは動かず分けられない変更: 実装の前に、決めたことと理由を Issue に書き、PR 本文にも載せる。あとの判断に役立つものは `docs/decisions/` に残す
- 実装の途中で仕様の穴が見つかった: **勝手に決めず**、Issue にコメントして人に返す
