# レビューの観点と書き方

当社のレビュアーと、プラグインのレビューエージェントが共通で使う観点。
**このファイルは公開されます。** 顧客名・案件名・具体的な業務内容を書かないでください。

## 指摘の書き方

指摘 1 件につき、次の 4 つをこの順で書きます。どれかが欠けると、直し方が伝わらないか、同じ指摘が繰り返されます。

| 要素 | 書くこと | 悪い例 |
|:--|:--|:--|
| **現象** | 何が起きるか。ファイルと行を添える | 「ここが変です」 |
| **理由** | なぜそれが問題か。何が壊れるか | 「規約なので」 |
| **直し方** | 具体的にどう書き換えるか。コードで示す | 「適切に修正してください」 |
| **規約参照** | 根拠にした規約のファイルと節 | （省略） |

規約に根拠が無い指摘は、**Info 止まり**にします。好みを規約として押しつけないためです。

## 分量の決まり

- **良かった点を 1 つ必ず書く。** 何が正しい書き方なのかが伝わらないと、次も同じ書き方になります
- **Info（好みの範囲）は 5 件まで。** 多いほど読まれず、重要な指摘が埋もれます
- Critical / Warning に件数の上限はありません

## 重要度

| 重要度 | 基準 | 例 |
|:--|:--|:--|
| **Critical** | データを壊す・受入条件を満たさなくなる・秘密が漏れる | 層をまたいだ参照、`await` 漏れ、トランザクション境界の誤りで中間状態が残る、認証情報のハードコード、他人のデータが読める経路 |
| **Warning** | 仕様と食い違う・誤った値を残す・テストが実際には検証していない | 仕様書との食い違い、競合で壊れる、実装と食い違うコメント、失敗しても通るテスト、規約違反、N+1 |
| **Info** | 情報・好みの範囲 | 命名の提案、代替の書き方 |

**迷ったら 1 段階重く見る。** 「動くが誤った値を残す」は Warning ではなく Critical です。

**ファイルの行数は指摘しない。** 行数の上限は規約にありません。

## 見る順番

上から見て、上で見つかったものを優先します。下の指摘は、上が片付いてから出します。

1. **API 定義との整合**: `shared` の定義が正か。手書きの型が無いか。定義を変えたなら server と client が同じ PR に入っているか
2. **配置と依存**: 層をまたいだ参照が無いか。層を新しく作っていないか
3. **正確性**: `await` 漏れ、`null` の扱い、境界値、競合、中間状態
4. **セキュリティ**: 入力の検証、認可、秘密の扱い、上限
5. **テスト**: 受入条件ごとにテストがあるか。**そのテストが本当に落ちる条件を持っているか**
6. **一貫性**: 同じことをする既存の処理と書き方が揃っているか
7. **可読性とコメント**: 実装と食い違うコメントが無いか

## 指摘しないこと

- **好み**（規約に根拠が無いもの）。どうしても言いたければ Info に 1 件だけ
- **この PR の範囲外の既存コード**。気づいたら Issue にする
- **ファイルの行数**
- 同じ理由の指摘を箇所ごとに繰り返すこと。**1 件にまとめて「他 N 箇所」**と書く

## レビュアーがやらないこと

- **勝手に直さない。** 指摘して、直すかどうかは書いた人が決める
- **ready にしない。マージしない。** どちらも人が行う
- 動作に影響が大きい指摘は、レビュアーの判断で結論を出さず**人に相談する**

## 指摘を受けた側の作法

- **1 コメント = 1 コミット**。返信にコミットの SHA を添える
- 見送る場合は**理由を返信と PR 本文に残す**。次に同じ指摘が来たとき再検証しないで済みます
- 指摘が規約と食い違うと感じたら、鵜呑みにせず `/shinnn-app:why` で規約の意図を確認してから答える
