# 画面のデザインを見直す

すべての画面をまとめて見せて、改善案を受ける。入れる改善案は、利用者に選んでもらう。
このスキルは順番だけを示す。いつ見直すかと、作るものの決まりは、規約 `.claude/rules/client-styling.md` の「デザインの指導」にある。
`auto-merge` でも利用者に聞く決まりは、規約 `git-workflow.md` の「`auto-merge` のとき」にある。

このスキルはブランチを切らず、コミットもしない。作るのは Issue だけで、改善は `/shinnn-app:feature` が Issue ごとに作る。
リポジトリのファイルは、`.gitignore` に `/screenshots/` を足すときのほかは変えない（足した行の扱いは 1 の 4）。

`args` に `計画: #<親の番号>` があれば、`/shinnn-app:feature` の「8. デザインを見直す」から呼ばれている。
そのときは、このスキルを終えたら（途中で終えたときを含む）、feature の 8 に戻る。

## 0. 始める前に確かめる

1. 題が `[調整] デザインの見直し` の open な Issue があれば、前の見直しで聞き終えていない改善案がある。
   撮り直さずに、「4. 1 件ずつ聞く」から続ける。聞くのは、題が `[デザイン]` で始まり、`status:*` のラベルが無い open な Issue。
   ただし、4 の 3 のコメント（`入れると決まった（ラベルは最後に付ける）`）がある Issue は聞かずに、入れる側に数える。
   聞き終えたら、4 の 6 までを行う。そのうえで、`args` に `計画: #<親の番号>` があり、その記録の Issue の本文の先頭の `計画:` の行と違う
   （行が無いときを含む）ときは、`args` の計画の見直しを、この節の 2 から始める。ほかのときは、5 に進む
2. 画面のルート（`client/src/app/app.routes.ts`）に画面が 1 つも無ければ、見直さずに、そのことを伝えて終える
3. `docs/仕様書.md` の「見た目の方針」の「再現の度合い」が「元に寄せる」なら、始める前に利用者に確かめる。
   見直しは、元の画面に寄せる案ではなく、新しいデザインの案を出すことを伝え、それでよいかを聞く。
   よいと言われたら進める。よいと言われなければ、見直さずに終える（規約の「デザインの指導」）
4. スキルの一覧に `frontend-design` が無ければ、`/shinnn-app:add-screen` の「`frontend-design` が無いとき」の最初の段落のとおりに入れる。
   入れたものは次の起動から使える。そのため、今回は見直さない。
   入れたことと、起動し直してから `/shinnn-app:design-review` を呼べば見直せることを伝えて終える。
   入れられなかったときは、そのことを伝えて終える

## 1. 材料をそろえる

1. `docs/仕様書.md` の「目的」と「見た目の方針」（「使う人と場面」を含む）を読む。
   「使う人と場面」が空か分からないところは、規約の「デザインの指導」のとおり推測で埋める。
   推測で埋めたところは、3 の記録の Issue の本文に書く（仕様書は変えない）
2. `/shinnn-app:dev-stack-start` で起動する
3. 画面の一覧を作る。`client/src/app/app.routes.ts` と、そこから読み込む `features/<機能>/<機能>.routes.ts` のルートを読み、
   画面ごとに名前と URL を決める。ルートを読むと、client の規約も読み込まれる
   - URL は、`dev-stack-start` が示す画面の開き方に、画面のパスを足したもの
   - name は、画面のパスから取った英小文字と `-` の名前にする（例: `items`）。撮った画像のファイルの名前になる
   - 別のパスへ移すだけのルート（`redirectTo`）は入れない
   - パスに `:id` のような値を含む画面は、一覧の画面に出ている 1 件の値を入れる。データが無くて開けない画面は、撮れなかった画面に入れる
   - ダイアログ（`MatDialog`）のように URL の無い画面は撮れない。その部品のテンプレート（`.html`）の場所を、2 の材料に書く
4. `.gitignore` に `/screenshots/` の行が無ければ、撮る前に足す（スクリプトは、git の対象の場所には書かずに止まる）。
   撮った画像には本物のデータが写りうるので、git に入れない。足した行は、このスキルではコミットせずに残す
   - 入れる改善案があれば、足した行は、最初に作る `[デザイン]` の Issue のブランチに持ち越し、その PR に入れる
     （`/shinnn-app:feature` の手順 3 の `git switch -c` で、コミットしていない変更が移る）
   - 入れる改善案が無ければ、足した行を残したことを最後に伝える（feature から呼ばれたときは、feature の最後の報告に入れる）。
     この変更は、次に feature を始めたときの「続きから始める」の 0 に任せ、このスキルでは 0 を行わない
5. 一覧を JSON で、Write ツールで scratchpad に書き、まとめて撮る。
   `--token` とブラウザの扱いは、`/shinnn-app:add-screen` の「9. 作った画面を見直す」の 1 と同じ

   ```
   node ${CLAUDE_PLUGIN_ROOT}/scripts/capture-screens.mjs batch --list <一覧のファイル> --out-dir screenshots/review --token
   ```

   一覧の形: `[{ "name": "items", "url": "<画面の URL>" }]`。撮った画像は `screenshots/review/<name>.png` に書かれる。
   撮れなかった画面は「撮れませんでした: <name>（理由）」と出る。撮れた画面だけで進め、撮れなかった画面は 3 の記録の Issue に書く
6. 1 枚も撮れない（ブラウザが無い、サーバーを起動できない）ときは、見直さずに、そのことを伝えて終える（規約の「デザインの指導」のただし書き）

## 2. 指導を受ける

1. 撮った画像を、すべて Read ツールで開く
2. Skill ツールで `frontend-design:frontend-design` を 1 回呼ぶ。`args` に次を渡す

   | 渡すもの | 中身 |
   |:--|:--|
   | 目的 | `docs/仕様書.md` の「目的」 |
   | 使う人と場面 | 「見た目の方針」の「使う人と場面」。1 の 1 で推測で埋めたところには「（仮）」を付ける |
   | 見た目の方針 | 「見た目の方針」の配色・書体・画面の骨組み・大事にすること。空なら「空」と書く |
   | 画面 | 画面ごとの名前・パス・画像の置き場所（`screenshots/review/<name>.png`）。撮れなかった画面と URL の無い画面は、テンプレートの場所 |
   | 条件 | 業務の画面なので、目新しさより、使う人が迷わず・間違えずに速く進められることを優先する。守る決まりは `.claude/rules/client-styling.md`（「テーマと書体」を含む）で、案が規約とぶつかるときは規約に従う |
   | 頼むこと | 画面をまたいだ改善案を、効き目の大きい順に、多くても 10 件挙げること。用語・配置・操作の順番・情報の優先度が画面の間でそろっているかも見ること。1 件ごとに、対象の画面・変えること・理由（何が良くなるか）・見た目だけか振る舞い（操作の順番など）も変わるかを書くこと。1 件は、PR 1 本で作れる大きさにすること |

3. 結果を、1 件ずつの改善案に分ける。規約とぶつかる案は、規約に合う形に直すか、落とす。
   見た目の方針（配色・書体・画面の骨組み）を変える案は 1 件にまとめ、「変えること」に `docs/仕様書.md` の「見た目の方針」を直すことも書く
4. 改善案が 1 件も無ければ、3 の 1 の記録の Issue だけを作る。結果をコメントして閉じ、5 に進む

## 3. 改善案を Issue にする

本文は、Write ツールで scratchpad に書き、`--body-file` に渡す。
画像の場所は、リポジトリからの相対パスで書く（絶対パスには利用者の名前が入りうる）。

1. 記録の Issue を先に作る。題は `[調整] デザインの見直し`、ラベルは `type:feature` だけにする

   ```
   gh issue create --title "[調整] デザインの見直し" --label type:feature --body-file <本文のファイル>
   ```

   本文には次を書く。
   - `args` に `計画: #<親の番号>` があれば、その行を本文の先頭に書く（feature の 8 が、この行で計画ごとに 1 回かを見分ける）
   - 利用者が直接呼んだときも、`/shinnn-app:feature` の「8. デザインを見直す」でいう「この計画」があり、
     その計画の `[調整] デザインの見直し` も `[調整] すべての画面の見直し` も無ければ、`計画: #<その番号>` の行を本文の先頭に書く
     （feature の 8 が、利用者の頼んでいない 2 回目の見直しをしないため）
   - 撮った画面の一覧と画像の置き場所、撮れなかった画面とその理由
   - 「使う人と場面」を推測で埋めたところ（1 の 1）
2. 改善案ごとに Issue を作る。題は `[デザイン] <変えること>`、ラベルは `type:feature` だけにする

   ```
   gh issue create --title "[デザイン] <変えること>" --label type:feature --body-file <本文のファイル>
   ```

   | 見出し | 内容 |
   |:--|:--|
   | 目的 | 使う人から見て、何が良くなるか。利用者の言葉で書く（Material・Tailwind などの用語を使わない） |
   | 画面 | 対象の画面と、その画像の置き場所。「画像は、このパソコンのアプリのフォルダの `screenshots/review/` にあります（GitHub には送っていません）」と添える |
   | 変えること | この Issue で変えること。利用者の言葉で書く |
   | 作り方のメモ | 指導の案のうち、作り方の細かい点（使う部品・色や書体の役割の名前など） |
   | 受入条件 | 見た目だけの改善案は「無し（見た目の調整）」。振る舞いが変わる改善案（操作の順番を変えるなど）は、`/shinnn-app:feature` の「1. Issue を作る」のとおりに `AC-n` を立てる |
   | 記録 | `#<記録の Issue の番号>` |

`status:*` のラベルは、記録の Issue にも改善案の Issue にも付けない。
付けると、利用者が決める前に、`/shinnn-app:feature` が作る Issue として取る。

## 4. 1 件ずつ聞く

`auto-merge` でも聞く（規約 `git-workflow.md` の「`auto-merge` のとき」）。1 回の応答で聞くのは 1 件にする。

1. 改善案を 1 件ずつ、変えることと良くなることを、利用者の言葉で 2〜3 行に縮めて示す。入れるか入れないかを聞く。
   Issue の URL を添えて、「詳しくはこちら」と促す。
   最初の 1 件を聞くときは、改善案の全部の件数と、残りはまとめて答えてもよいことも添える
2. 入れないと言われたら、理由を書いて閉じる。理由は、利用者の言葉を短くしたものにする（言われなければ「入れないと決めた」）

   ```
   gh issue close <番号> --reason "not planned" --comment "<理由>"
   ```

3. 入れると言われたら、その Issue に次のコメントを残し、番号を控える。ラベルは、すべてを聞き終えてから付ける

   ```
   gh issue comment <番号> --body "入れると決まった（ラベルは最後に付ける）"
   ```

4. 「残りは全部入れる」のように残りをまとめて答えられたら、その答えを残りのすべてに当てる。
   入れるか入れないか分からない返事には、聞き直す
5. すべてを聞き終えたら、入れる Issue（3 のコメントを残した Issue）に `status:next` を付ける

   ```
   gh issue edit <番号> --add-label status:next
   ```

6. 記録の Issue に、入れた Issue と入れなかった Issue の番号をコメントして閉じる

   ```
   gh issue close <記録の Issue の番号> --comment "<結果>"
   ```

ラベルを最後に付けるのは、聞いている途中で作り始めないため。
`auto-merge` では、`status:next` の Issue が残っている間に応答を終えると、hook が作り続けるよう伝える。
3 でコメントを残すのは、聞いている途中で途切れても、入れると決まった改善案を 0 の 1 で見分けるため。

## 5. 次へ進む

- `/shinnn-app:feature` の「8. デザインを見直す」から呼ばれたときは、feature の 8 に戻る
- 利用者が直接呼んだときは、入れた Issue の番号と、「`/shinnn-app:feature` で作ります」を伝える（「続きをお願いします」でも始まる）
- ただし、`auto-merge` なら、伝えた後に Skill ツールで `shinnn-app:feature` を呼び、「続きから始める」の順で作る
- 入れた Issue が無ければ、そのことを伝えて終える
