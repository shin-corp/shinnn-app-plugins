# セッションの知見を開発資産に還元する

その場しのぎで解決したことを、次回は最初から効く形に置き直す。

**振り返りのうち、Issue に残すもの（詰まり・学び・次に試す）は `retro` の担当。**
このスキルは、**開発の進め方そのもの**を直す場合に使う。

## いつ使うか

`/shinnn-app:feature` が PR を出し終えて止まるときに 1 回呼ぶ（PR ごとには呼ばない）。人に頼まれたときも同じ手順で行う。
材料は次の 3 つ。

- このセッションで PR を出した Issue に `retro` が残したコメント（`gh issue view <番号> --comments`）
- 「引き継ぎメモ」Issue（番号は `.shinnn/setup.json` の `handoverIssue`）
- このセッションでのやり取り（人に指摘されたこと、繰り返したこと、詰まったこと）

## 1. 知見を棚卸しする

材料から、次に当たるものを列挙する。無ければ「無し」と報告して終わる（Issue もブランチも作らない）。**無理に作らない。**

- **詰まり**: 想定と違った挙動、失敗したコマンド、回避策
- **繰り返した手作業**: 同じ調べ物・同じ手順を 2 回以上やった
- **人からの指摘**: やり方・規約・書き方についての訂正
- **確定した正攻法**: 試行錯誤の末に決まった手順
- **既存のスキルや文書の誤り**: 書いてあることと実態が違った箇所

## 2. 反映先を決める

**1 つの事実は 1 か所に書く。** 重複させない。

| 知見の性質 | 反映先 |
|:--|:--|
| その案件でしか使わない手順（再現できる） | このリポジトリの `.claude/skills/<名前>/SKILL.md`。`/<名前>` で呼べる |
| どの案件でも要る手順（既存スキルの修正を含む） | スキル。**手順の正本はプラグイン側にある**ので、シン株式会社に上げる |
| コマンドやツールの落とし穴 | 該当スキルの当該節を実態に合わせて直す |
| ファイル種別ごとの規約（命名・記法・構造） | `.claude/rules/*.md`。**標準の rules は直接直せない**ので、直すべき内容としてシン株式会社に上げる |
| 構成・ビルド手順・技術スタック | 該当階層の `CLAUDE.md` |
| 「今後 X したら必ず Y」という自動実行 | hook。プラグイン側の変更になるためシン株式会社に上げる |
| 検証の結果・計測値 | `docs/results/` |
| このアプリの決定と理由 | `docs/decisions/` |

判断に迷ったときの原則:

- **コードを読めば分かること、git に残っていることは書かない。** 非自明だった点だけ残す
- 既存の記述に該当箇所があるなら、**新規作成より修正を優先**する
- 標準（`.claude/rules/` とプラグイン）に関わるものは、リポジトリ側で直さず**シン株式会社に上げる**。
  「引き継ぎメモ」Issue に書き、`/shinnn-app:update-rules` で降りてくるのを待つ
- **迷ったらシン株式会社に上げる。** 案件ごとに手順が枝分かれすると、テンプレートの更新を取り込みにくくなる

## 3. 反映する

**このリポジトリのファイル（`.claude/skills/`・`CLAUDE.md`・`docs/`）に書くものは、`main` に直接書かない。**
改善の Issue を `gh issue create` で作り（題は `[改善] 開発の進め方の反映`、ラベルは `status:doing`、本文に棚卸しの一覧）、
`origin/main` から `feature/<Issue 番号>-session-retro` を切って書き、`/shinnn-app:pr` で PR にする（本文の 1 行目は `Closes #<Issue 番号>`）。
`gh` が無い・ログインできないときは、Issue と PR を GitHub の画面で作ってもらう。
反映するものが標準に効くもの（引き継ぎメモに書くもの）だけなら、Issue もブランチも作らない。

- **案件固有の手順**は、このリポジトリの `.claude/skills/<名前>/SKILL.md` に置く
  - frontmatter に `name` と `description` を書く。`description` には何をするかと、呼び出すきっかけの言葉を入れる
  - 名前は標準のスキル（`shinnn-app:` が付くもの）と紛らわしくしない
- **標準に効くもの**（どの案件でも要る手順、規約、hook）はシン株式会社に上げる。内容を「引き継ぎメモ」Issue に書き、
  `/shinnn-app:update-rules` で降りてくるのを待つ
- `rules/*.md` には `paths` を必ず書く。書かないと常に読み込まれてコンテキストを圧迫する
  （リポジトリ全体に効かせる `git-workflow.md` だけは `paths` を持たない）

## 4. 報告

「知見 → 反映先 → 何を書いたか」の対応で簡潔に報告する。
**コミットは人の指示があるときだけ。**
