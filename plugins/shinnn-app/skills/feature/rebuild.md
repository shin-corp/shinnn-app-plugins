`/shinnn-app:feature` の SKILL.md の「0. 大きさを見る」と、「8. デザインを見直す」の「作り直しのとき」と、「作り直しの元の画面・見た目・移植対応表」から読む。

## 0. 大きさを見る

違うのは次だけ。

- このフォルダに `.claude/rules/.standards-version` が無いときは、テンプレートから作ったフォルダではない。作り直しを始めず、
  `/shinnn-app:setup` の手順 0 の 1 の案内を伝えて止まる
- 依頼に元のアプリのフォルダの場所が無ければ聞く（「1. Issue を作る」の確認の質問の数には入れない）。
  そのフォルダはこのフォルダの外に置いたままにし、このフォルダにコピーしない。コピーすると、git・lint・CI の対象になる
- 元のアプリのフォルダを `--add-dir` で足さずに起動していると、読むときに確認が出る。そのときは `/exit` で終了し、
  `claude --add-dir <元のアプリのフォルダ>` で起動し直すよう頼む。起動し直した後は、計画を作る前なら同じ依頼を、
  作った後なら「続きをお願い」を入力してもらう
- 止まるときの報告（7）に、次も `claude --add-dir <元のアプリのフォルダ>` で起動することを添える
- 計画を作る前に、元の画面の用意のしかたを利用者に聞き、答えを待つ（「作り直しの元の画面・見た目・移植対応表」の 1）。
  元のアプリのフォルダの場所と同じく、確認の質問の数には入れない。`auto-merge` でも聞く
- 元のアプリは読むだけで、書き換えない。`--add-dir` で足したフォルダへの書き換えは、確認なしで通る。
  Edit・Write で開くのは、このフォルダの中のファイルだけにする
- 元のアプリのコードを写さない。書き方は規約と手本に従う。CLAUDE.md と規約の「既存のコード」「既存の機能」は、このフォルダの中だけを指す
- 元のアプリの `.env` で始まるファイルは、`.env.example` のほかは読まない。権限の設定が止めるのは `.env`・`.env.local`・
  `.env.production` などの決まった名前だけで、`.env.prod` のような名前は止まらない
- 元のアプリを検索するときは Grep ツールを使い、`glob` に `!**/.env*` を付けて `.env` で始まるファイルを外す。
  Bash の `grep -r` は使わない（`.env` の中身も結果に出る）
- 設定の項目の名前が要るときは、`.env.example` を Read ツールで読む（`cat` は権限の設定で止まる）。
  `.env.example` が無ければ、コードの `process.env.` の参照から拾う
- 計画は、元のアプリの画面・API・保存しているデータの形（テーブルと項目）を読んで、`plan.md` の「1. 分ける」の単位に分ける。
  データそのもの（DB のファイルや書き出したファイル）は読まない
- 計画を作るときに、元のアプリから見た目の値を取り出し、仕様書に「再現の度合い」と一緒に書く（「作り直しの元の画面・見た目・移植対応表」の 2）
- 計画の Issue を作ったら、`docs/移植対応表.md` を作る（同じ節の 3）。作り直しの完成は、この表の「まだ」が 0 件になったとき
- 受入条件は、元のアプリの今の振る舞いから立てる。規約に従うと振る舞いが変わる点（認可が無かった操作など）は、
  規約に従う側で仮置きし、元のアプリとの違いを移植対応表のその行の「違い」に書く（Issue の「未決」には書かない）
- `docs/仕様書.md` の「目的」と「使う人と場面」は、計画を作るときに、元のアプリの画面・文言・文書から推測して書く
  （分からないところの書き方は規約 `client-styling.md` の「デザインの指導」）。この変更は、`plan.md` の 3 の 5 と同じく先頭の Issue の PR に入れる
- 本番のデータの移し替えと、新しいアプリへの切り替え（公開先・URL・利用者への周知）は、計画の「今回やらないこと」に書く。
  この 2 つは「あとで足せます」とは伝えず、シン株式会社の担当者に相談するよう、利用者に伝える

## 8. デザインを見直す

### 作り直しのとき

すべての画面を元と並べて撮る。撮った画像を見て直すことはしない（画面ごとの見直しは `add-screen` の「作り直しのとき」で済んでいる）。
並べた画像は、最後の調整（「9. 画面を見ながら調整する」）で利用者が見比べる。

1. この計画の親 Issue のコメントに `すべての画面を元と並べて撮った（screenshots/compare/）` があれば、この計画では撮ってある。撮らずに 5 に進む
2. `/shinnn-app:dev-stack-start` で起動する。移植対応表の画面の行から、画面の一覧を JSON で、Write ツールで scratchpad に書く。
   name は `add-screen` の 9 で使った画面の名前にする。元の画像がある画面は、`original` に `screenshots/original/<元の画面の画像>` を書く
3. まとめて撮る。`--token` とブラウザの扱いは、`add-screen` の「9. 作った画面を見直す」の 1 と同じ

   ```
   node ${CLAUDE_PLUGIN_ROOT}/scripts/capture-screens.mjs batch --list <一覧のファイル> --out-dir screenshots --token
   ```

   一覧の形: `[{ "name": "items", "url": "<画面の URL>", "original": "screenshots/original/<元の画面の画像>" }]`。
   撮った画像は `screenshots/<name>.png` に、元と並べた画像は `screenshots/compare/<name>.png` に書かれる（元の画像が無い画面は、並べた画像を作らない）
4. この計画の親 Issue に、計画ごとに 1 回の印としてコメントする

   ```
   gh issue comment <親の番号> --body "すべての画面を元と並べて撮った（screenshots/compare/）"
   ```

5. 7 の「止まるとき」の、報告の前に行う 2 に進む。報告には、並べた画像の置き場所を添える

撮れない（ブラウザが無い、サーバーを起動できない）ときは、4 の印を付けずに 5 に進む。報告には、撮れなかったことを書く。

## 作り直しの元の画面・見た目・移植対応表

元のアプリを作り直すとき（0 の作り直しの節）に行う。

### 1. 元の画面を用意する

計画を作る前に、次を順に行う。

1. 元のアプリのコード（ルート・画面の部品・テンプレートなど）を読み、画面の一覧を作る。この一覧は、「3. 移植対応表を作る」の画面の行の元にもなる
2. 画面の一覧と、画面ごとに付けてほしいファイルの名前（例: `商品一覧.png`）を示して、用意のしかたを聞き、答えを待つ。選んでもらうのは下の表の 2 つ。
   聞くときは、撮れない画面は飛ばしてよいことと、飛ばした画面は元のアプリのコードから作って最後に確かめてもらうことも伝える
3. (a) を選ばれたら、利用者に一覧の画面を撮って置いてもらい、置き終えたら伝えてもらう。撮れない画面（管理者だけの画面など）は飛ばしてよい。
   伝えられたら、置かれたファイルを一覧と照らす。名前が合わないファイルと、無い画面は、計画の知らせ（`plan.md` の 2）で示す（待たない）。そのうえで計画に進む
4. (b) を選ばれたら、下の形で撮る。撮った画像を Read で開いて確かめる（スクリプトは、ログインの画面に飛ばされても撮れたことにする）。
   ログインの画面か、頼んだのと別の画面が写っていれば、撮れなかった画面に入れる。
   撮れなかった画面は、同じ待ちの中で一覧にして示し、(a) で補うか、飛ばすかを選んでもらう。(a) で補うときは、3 と同じく置き終えるまで待つ

| 選択肢 | 用意のしかた |
|:--|:--|
| (a) 利用者が撮って置く | 利用者が元のアプリの画面を撮り、このフォルダの `screenshots/original/` に、示したファイルの名前で置く。PNG と JPEG を受け付ける |
| (b) Claude が URL から撮る | ログインの要らない画面か、テスト用のデータで動いている元のアプリの URL を受け取り、下の形で撮る |

- 聞くときは、撮った画面には本物のデータが写りうるので、`screenshots/` は git に入れないことを添える
- `.gitignore` に `/screenshots/` の行が無ければ、聞く前に足す（足した変更は、計画の先頭の Issue の PR に入れる）
- Claude はログインのパスワードを入れない。(b) でログインが要る画面は、4 のとおり (a) で補うか飛ばしてもらう
- 元のアプリを手元で起動して撮らない（元のアプリは読むだけにする）
- 元の画像が無い画面（飛ばした画面）も、止めずに作る（作り方は `add-screen` の「作り直しのとき」）。
  その画面は、移植対応表の「元の画像」を `無` にし、最後の報告（手順 7 の「止まるとき」）で確かめてもらう

(b) の撮り方: 一覧のファイル（JSON）を scratchpad に書き、まとめて撮る。`--token` は付けない（通行証はこのアプリのもの）。

```
node ${CLAUDE_PLUGIN_ROOT}/scripts/capture-screens.mjs batch --list <一覧のファイル> --out-dir screenshots/original
```

一覧の形: `[{ "name": "商品一覧", "url": "<元の画面の URL>" }]`。name には、2 で示したファイルの名前（拡張子を除く）を使う。撮れなかった画面は、4 のとおり示す。

### 2. 元のアプリから見た目を取り出す

計画を作るときに、元のアプリの CSS・テンプレート（HTML など）と元の画面の画像から、次を取り出す。
読み方は、0 の作り直しの節の決まり（Grep ツールで `.env` を外すなど）に従う。

- 主な色（見出しの帯・ボタン・リンク・背景・文字・強調）
- 書体（`font-family` の並び）
- 余白・角丸・文字の大きさ

取り出した値は、`docs/仕様書.md` の「見た目の方針」に書く。この変更は、計画の先頭の Issue の PR に入れる。

- 「再現の度合い」に「元に寄せる」と書く（振る舞いは元と同じにし、見た目は元に寄せる、という意味）。行が無ければ、「使う人と場面」の次に足す
- 「配色」に、テーマの生成に渡す色と、元のどこの色かを書く（例: 主色 `#1565c0`（元の見出しの帯））
- 「書体」に、元の書体の並びを書く
- 「画面の骨組み」に、元の余白・角丸・文字の大きさと、画面の並べ方（上の帯・左のメニューなど）を書く

この値でテーマを作るのは、最初の画面の `add-screen` の「作り直しのとき」の 0 の行。

### 3. 移植対応表を作る

`plan.md` の 3 で Issue を作ったら、`docs/移植対応表.md` を作る。この変更は、計画の先頭の Issue の PR に入れる。
仕様書とは別のファイルにする（受入条件の検査は仕様書の中の `AC-n` を数えるので、表を仕様書に入れない）。

```markdown
# 移植対応表

元のアプリの画面と機能を 1 行ずつ書き、作り直しの進み具合を数える表です。完成は、「状態」の「まだ」が 0 件になったときです。

| 元の画面・機能 | 元の場所 | 元の画像 | 状態 | Issue | 違い |
| :-- | :-- | :-- | :-- | :-- | :-- |
| 備品の一覧 | `public/index.html`（`/`） | 有 | まだ | #12 | |
| 備品の登録 | `public/new.html`（`/new`） | 無 | まだ | #13 | |
```

| 列 | 書くこと |
|:--|:--|
| 元の画面・機能 | 元のアプリの画面と、画面の中の機能（登録・検索・印刷・書き出しなど）。1 行に 1 つ |
| 元の場所 | 元のアプリのフォルダの中のファイルのパスと、画面のパス（URL のホストより後ろ）。元のアプリのフォルダそのものの場所（ドライブや利用者の名前を含むパス）は書かない |
| 元の画像 | `screenshots/original/` に元の画面の画像があれば `有`、無ければ `無`。画面の中の機能の行は、その画面と同じにする |
| 状態 | `済み`（元と同じに作った）・`違う`（違う形で作った）・`まだ`・`やらない` のどれか。表を作るときは、`plan.md` の 2 の確認で利用者が外したものを `やらない`、ほかを `まだ` にする |
| Issue | その行を作る Issue の番号。受入条件の番号（`AC-n`）は書かない（受入条件は仕様書の 6 にある） |
| 違い | `違う` と `やらない` の理由。`まだ` の行でも、違いになると分かった点は書いておく |

- 元のアプリの画面と機能は、すべて行にする。どの行も、計画のどれかの Issue に結ぶ（`やらない` の行を除く）
- 各 Issue の PR で、その Issue の行の状態を `済み` か `違う` に直す
- 規約に従うと振る舞いが変わる点（認可が無かった操作など）と、元の作りがこのテンプレートで作れない点は、`違う` にする
- `/shinnn-app:design-review` で利用者が入れると決めた改善案（`[デザイン]` の Issue）で変えた点も、`違う` にする
- `やらない` は、利用者が決めたときだけにする（`[確認]` への返事や、作業の途中で利用者が伝えたときを含む）。Claude は `やらない` を決めない
- 元のアプリとの違いは、この表にだけ書く。Issue の「未決」・PR 本文の「規約で迷った点」・引き継ぎメモには書かない
- 作り直しの完成は、「まだ」が 0 件になったとき。セッションの最初に、`session-start` が件数を出す
