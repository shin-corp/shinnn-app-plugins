# スタイリング規約（client）

**独自 CSS を書かない。Tailwind のユーティリティクラスと Angular Material のテーマ変数だけで作ります。**

## 基本

- **`.css` / `.scss` ファイルを新規に作らない。** コンポーネントの `styles` / `styleUrls` を増やさない
  （例外は生成したテーマ `client/src/theme.css` だけ。「テーマと書体」）
- `@apply` を使わない（クラスの実体がテンプレートから見えなくなる）
- グローバルスタイルは Tailwind のエントリ 1 ファイル（`client/src/styles.css`）だけ。
  機能ごとのクラスやセレクタをここに書き足さない（役割の名前の変数は「テーマと書体」）
- 色・余白・フォントは Tailwind の設定にある段階値を使う。
  任意値（`w-[137px]` / `text-[#1a2b3c]`）を書かない。必要なら Tailwind の `@theme` に段階値を足す

## Material と Tailwind の共存

- Material のスタイルは **Tailwind とは別の CSS レイヤ**に置く（`styles.css` の `@layer` 指定）。
  こうしないと Tailwind の preflight が Material の見た目を壊す
- 色をそろえたいときは Material のシステム変数（`--mat-sys-*`）を Tailwind の `@theme` に流し込む。
  同じ色を 2 か所に別々の値で書かない
- **Material の部品の要素（`mat-dialog-content`・`th mat-header-cell`・`td mat-cell` など）に、部品が自分で決めている性質
  （`display`・余白・文字の揃えなど）のユーティリティを付けない。** 効かないまま残る。並べ方・余白・揃えは、
  部品の中に置いた `div` に付ける。部品が決めていない性質（`gap`・幅など）は、部品の要素に付けても効く
- **Material のスタイルを `::ng-deep` で上書きしない。** コンポーネントが公式に提供する入力
  （`color` / `appearance` など）とテーマ変数だけで調整する。手段が無ければ見た目を諦め、
  `docs/仕様書.md` の未決事項に上げる

## テーマと書体

- **配色と書体は `styles.css` の 1 か所で決め、画面のテンプレートに直値を書かない。** 方針は `docs/仕様書.md` の
  「見た目の方針」に書き、変えるときはそこを先に直す
- 特定の画面だけで使う色や書体が要るときも、`styles.css` の `@theme` に役割の名前（例: `--color-highlight`、
  `--font-display`）で足し、どの画面のどこに使うかを「見た目の方針」に書く。名前に画面の名前を付けない。
  色の値はテーマの変数（`--mat-sys-*`）から取る。主色と別の系統の色が要るときは、`theme-color` の生成に
  第 3 の色（`--tertiary-color`）として加える
- 配色は Material のテーマで決める。同梱のテーマ（`styles.css` が読み込む `azure-blue.css`）か、主色から
  Material の `theme-color` で生成した `client/src/theme.css` のどちらか。`theme.css` は生成物なので手で書き換えず、
  色を変えるときは生成し直す。読み込むレイヤは同梱のテーマと同じ `material`。書体を変えるとき、主色と別の系統の色が
  要るときは、`theme.css` を生成して使う（同梱のテーマは下の書体の変数を読まない。配色を変えないなら今の主色で生成する）
- 書体は npm の `@fontsource` / `@fontsource-variable` のパッケージを入れて `styles.css` で読み込む。
  外部の配信（Google Fonts の `<link>` など）から読み込まない。書体の名前は `styles.css` の `html` の
  `--mat-sys-plain-font-family` / `--mat-sys-brand-font-family` と、`@theme` の `--font-sans` に入れる
- `frontend-design` スキルの案がこの規約とぶつかるときは、規約に従う（独自の CSS・任意値・外部の書体の配信は、
  案にあっても使わない）

## クラスの書き方

- 条件付きのクラスは `[class.xxx]` か `[ngClass]` で切り替える。
  **テンプレート内で文字列を連結してクラス名を組み立てない**（Tailwind のスキャンから漏れて消える）
- 同じクラスの組み合わせが 3 か所以上に出たら、コンポーネントに切り出す（クラス文字列の定数化ではなく）
- レスポンシブは Tailwind のブレークポイント接頭辞（`sm:` / `md:` / `lg:`）。
  メディアクエリを手書きしない

## なぜ

独自 CSS を禁じるのは、CSS が「離れた場所を壊す」唯一の言語だからです。ある画面のために書いた
セレクタが、別の画面の見た目を変えてしまっても、型検査もテストもそれを教えてくれません。
ユーティリティクラスなら、影響範囲がそのタグの中で閉じます。

Material を別レイヤに置くのは、Tailwind の preflight（ブラウザ既定のスタイルを打ち消す仕組み）が
Material のボタンや入力欄の見た目を消してしまうためです。レイヤを分けると、どちらが優先されるかが
記述順ではなく宣言で決まります。

部品の要素にユーティリティを付けないのは、Material の部品の CSS は Angular が画面を出すときにレイヤの外で差し込むためです。
レイヤの外の指定はレイヤの中のユーティリティより強いので、部品が決めている性質はユーティリティを付けても変わらず、
型検査にも lint にも出ません。部品の中の `div` には部品の CSS が当たらないので、書いたとおりに効きます。

`::ng-deep` を禁じるのは、Angular が非推奨にしており、Material の内部構造が変わると黙って
効かなくなるためです。バージョンを上げた日に、どの画面が崩れるか分からない状態になります。

見た目の方針をアプリで 1 つにするのは、画面ごとにばらばらだと、使う人が画面を移るたびに見方を覚え直すことになるためです。
画面だけで使う色や書体も同じ場所に役割の名前で足すのは、どの色と書体がどこで使われているかを 1 か所で見渡せるように
するためです。画面のテンプレートに直値が散らばると、方針を変えたときに直し漏れが出ます。
配色を生成に任せるのは、Material のテーマが主色 1 つから文字と背景の組み合わせを 150 を超える変数に展開しており、
手で書くと読みにくい組み合わせが混ざるためです。書体を npm で同梱するのは、外部の配信に頼ると、社内のネットワークで
読み込めなかったり、画面を開いたことが配信元に伝わったりするためです。`frontend-design` スキルは見た目の案を
立てるのに使いますが、独自の CSS を書く前提の案も出すので、上の理由から規約の方を優先します。
