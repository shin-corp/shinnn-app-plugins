# 大きな変更の進め方

API 定義・DB・サーバー・画面・テストが一度に動くような変更を、1 本の PR で通すための手順。

そもそも 1 本にまとめるべきかを先に考える。**Issue を分けられるなら分ける。**
分けられない（片方だけでは動かない）ときだけ、この手順に入る。

## 1. 設計メモを先に書く

実装を始める前に、次を書き出す。ここが弱いと後で必ず作り直しになる。

| 書くもの | なぜ |
|:--|:--|
| 決めたことと**その理由**（`D-1` のように番号を振る） | 後から「なぜこうしたか」を追える。PR 本文にそのまま使える |
| ファイルと役割の一覧（どこに何を置くか） | `.claude/rules/` の配置判断表を、この変更に落とす |
| **公開する関数の名前・引数・戻り値** | 使う側と作る側を同時に進められる |
| 後回しにする判断 | PR 本文の「人の判断を待つ項目」になる |

**API 定義（`shared` の zod）と、複数の場所から使う共通処理は最初に自分で書く。**
これを後回しにすると、それぞれが別々のものを作って食い違う。

決めたことと理由は、作業が終わったら `docs/decisions/` に残す。

## 2. フェーズに分ける

1 フェーズ = 「同時に進めても衝突しない仕事のまとまり」。フェーズごとに次を回してから先へ進む。

```
実装 → npm run check -w <対象> → テスト → 自分で差分を読む → 修正
```

- 依存があるものは**別のフェーズ**にする。同じフェーズで待たせない
- 並列で作業させる場合は、**触ってよいファイルを明示して重ねない**
- 複数の実装をまとめるファイル（束ねる側）は自分で持つ
- **差分は自分で読んでからコミットする**

## 3. まとめて同じ修正を当てるとき

同じ変更を多数のファイルに当てるときは、スクリプトを書いて実行する。次の 3 点で必ず失敗する。

- **冪等に書く**: 途中で失敗して再実行することが多い。「適用済みならスキップ」を入れる
- **改行コードを変えない**: テキストとして読み書きすると CRLF が LF になる。バイト単位で読み書きする。
  `sed -i` はファイル全体を LF に変換するので、既存ファイルの部分修正には使わない
- **絶対パスで書く**: Bash の作業ディレクトリはコマンドをまたいで残るため、一度 `cd` すると相対パスがずれる

当てたあとは必ず `git diff --shortstat` と `git diff --ignore-cr-at-eol --shortstat` を比べ、
改行だけの差分が出ていないことを確認する。

## 4. 検証と記録

- **テストが通ることと、人が手で通せることは別。** 実際に画面かコマンドで通してみる
- 通した結果は `docs/results/` に残す
- 開発用の DB を使った確認をしたら、**後始末して次の人が同じ状態から始められるようにする**
