# アプリの作り方ガイド

このリポジトリでアプリを作るときの進め方です。**2 ページで読み切れる分量**にしてあります。
細かい規約は Claude Code が自動で読むので、覚える必要はありません。

## 1. 使うコマンド

Claude Code の画面で、次のように入力します。**普段使うのは `feature` だけ**です。

### 最初の 1 回に使うもの

| コマンド            | 何が起きるか                                         |
| :------------------ | :--------------------------------------------------- |
| `/shinnn-app:setup` | 環境を調べ、必要な機能を一緒に決めて、設定を作ります |

### 普段使うもの

| 入力するもの                         | いつ使うか                       | 何が起きるか                                                                     |
| :----------------------------------- | :------------------------------- | :------------------------------------------------------------------------------- |
| `/shinnn-app:feature <作りたいこと>` | 何かを作りたいとき               | 作業票（Issue）に分けて完成の条件を決め、実装から提出（PR）まで 1 つずつ進めます |
| 「続きをお願いします」               | 次に開いたとき                   | 残りの作業から再開します                                                         |
| `/shinnn-app:why <知りたいこと>`     | 「なぜこう書くの？」と思ったとき | 規約の理由を、やさしい言葉と例で説明します                                       |

`feature` は、作ったあとに次のことを**続けて自分で行います。** 入力する必要はありません。

| 行うこと                                         | 中で使うコマンド    |
| :----------------------------------------------- | :------------------ |
| 型の検査・書き方の検査・テストをまとめて実行する | `/shinnn-app:check` |
| 変更をまとめて提出（PR）し、レビューを受ける     | `/shinnn-app:pr`    |
| 詰まったこと・学んだことを作業票に残す           | `/shinnn-app:retro` |

自分で手を入れたあとに確かめたいときなどは、これらを直接入力しても構いません。

作りたいことがいくつあっても、**まとめて `feature` に伝えてください。** 分け方と作る順番は Claude が決めて、一度だけ確認します。
提出（PR）の取り込みを待っているときは、Claude がそう伝えて止まります。

## 2. どこに何を書くか

作りたいものが決まったら、次の順に触ります。**この順番を守ると、途中で型のエラーが出ません。**

```
1. shared/     … 画面とサーバーがやり取りするデータの形を決める
        ↓
2. server/     … サーバー側の処理を書く（受け取る → 判断する → 保存する）
        ↓
3. client/     … 画面を作る
        ↓
4. テスト      … 「これができたら完成」の条件を確かめる
```

| 作ろうとしているもの                     | 置く場所                                                          |
| :--------------------------------------- | :---------------------------------------------------------------- |
| 新しい画面                               | `client/src/app/features/<機能の名前>/`                           |
| 画面からのサーバー呼び出し               | `client/src/app/api-client.ts` に追記（新しいファイルを作らない） |
| やり取りするデータの形                   | `shared/src/api/<機能の名前>.ts`                                  |
| サーバーの入口（URL）                    | `server/src/api/<機能の名前>/`                                    |
| 業務の判断（〇〇なら登録できない、など） | `server/src/service/<機能の名前>.service.ts`                      |
| 保存するデータの形                       | `server/src/db/schema/<名前>.ts`                                  |
| テスト                                   | `server/tests/<機能の名前>.test.ts`                               |

**新しいフォルダの種類を増やさないでください。** 迷ったら `/shinnn-app:why <ファイル名>` と聞くと、
どこに置くべきかを理由つきで教えてくれます。

**新しい画面は、同梱の `features/items/` をコピーして作ります。** ゼロから書かないでください
（サンプルの `items` を消した後は、既存の機能を手本にします）。

**サンプルの `items` は、自分の機能が 1 つ動くまで消さないでください。** 消したときは、
CLAUDE.md と `.claude/rules/` にある「手本は `items`」という記述を、自分の機能の名前に直します。

## 3. 良い提出（PR）の姿

| 良い例                                         | 良くない例                             |
| :--------------------------------------------- | :------------------------------------- |
| 1 つの作業票（Issue）に対して 1 つの提出       | 3 つの機能がひとつの提出に混ざっている |
| 本文に `Closes #12` と書いてある               | どの作業票に対応するか書いていない     |
| 「これができたら完成」の条件ごとにテストがある | テストが無い、または `skip` されている |
| 変更したファイルが 10 個くらい                 | 100 個のファイルが変わっている         |
| 「次に何をするか」が本文に書いてある           | 本文が空                               |
| 迷ったことが本文に書いてある                   | 迷ったまま黙って進めている             |

**提出は大きくしすぎないでください。** 目安は「レビューする人が 15 分で読める量」です。
`/shinnn-app:feature` は、依頼がこの量を超えるときは分けて作るので、自分で分ける必要はありません。

**赤い印（CI の失敗）が出たまま進めないでください。** 何が悪いかは日本語で表示されます。
そのまま Claude Code に貼り付ければ、直し方を教えてくれます。

## 4. シン株式会社に連絡するタイミング

次のときは、自分で解決しようとせず**連絡してください**。時間の無駄を防げます。

- **同じエラーで 2 回以上つまずいたとき**（1 回目は Claude Code に聞いてください）
- **規約を変えたくなったとき**。`.claude/` と `.github/` の中身は、こちらでレビューして変更します
- **有料のライブラリや、利用料のかかる外部サービスを使いたくなったとき**。無料のライブラリは Claude Code がそのまま入れるので、連絡は要りません
- **お金がかかる設定を入れるとき**（AI レビューなど）
- **個人情報や、実際の業務データを扱い始めるとき**
- **本番で使い始めるとき**、および**引き継ぐとき**
- **消してしまった・戻せなくなったとき**。手を止めて連絡してください。触るほど復旧が難しくなります

連絡の仕方は、リポジトリに Issue を立てるか、シン株式会社の担当者に直接ご連絡ください。
Issue に書いておくと、経緯が残るので次回の説明が要らなくなります。

## 5. 覚えておくと楽なこと

- **分からないことは `/shinnn-app:why` に聞く。** 規約は暗記するものではありません
- **「完成の条件」を先に決める。** 決めてから作ると、どこで終わってよいかが分かります
- **決まっていないことは実装しない。** `docs/仕様書.md` の「未決事項」に書いて、人に返します
- **作業票（Issue）のコメントを読む。** 提出のたびに Claude が詰まったこと・学んだことを残すので、次に開いたときの自分（と引き継ぐ人）が助かります
