# 外部の AI サービスとの連携（Claude Agent SDK など）

`server/src/provider/` に置く、外部システムの SDK を呼ぶコードと、その評価（`server/evals/`）の規約です。
層の位置づけは [server-architecture.md](server-architecture.md) を参照。ここでは Claude Agent SDK を例に書きますが、
他の AI サービスや外部 API でも同じ考え方で扱います。

「（検査: …）」には、その決まりを機械で確かめる仕組みを書いています。付いていない決まりは、レビューだけで確かめます。

## 置き場所と呼び出し

- 利用料が発生する外部サービスの SDK（AI の SDK など）は、入れる前に止まり、シン株式会社の判断を待つ（ルートの `CLAUDE.md` の「費用が発生するものは入れない」）
- 入れると決まった SDK がライセンスの検査（`scripts/check-licenses.mjs`）を通らない場合は、通し方もシン株式会社の指示に従う
- SDK を import するのは `server/src/provider/<システム>.provider.ts` だけにする（検査: ESLint。
  `server/eslint.config.js` に名前を書いた SDK だけを止める）
- 新しい SDK を入れたら、そのパッケージ名を `server/eslint.config.js` の禁止に足す
- `provider/` には通信だけを書く（渡された文字列を送って、結果を返す）
- プロンプトの組み立てとモデルの出力の解釈は `service/` に書く

## Claude Agent SDK を呼ぶときに指定すること

| 指定              | 値                                   | 理由                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| :---------------- | :----------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tools`           | `[]`                                 | 組み込みツール（ファイル・Bash・Web）を持たせない。文章を返すだけなら要らない。持たせると、利用者の入力を通じてサーバーのファイルに触れられる                                                                                                                                                                                                                                                                                                                                     |
| `strictMcpConfig` | `true`                               | 手元の Claude Code のログインに紐づく claude.ai のコネクタ（Gmail・Notion など）を読み込まない。このコネクタは `tools: []` では外れない                                                                                                                                                                                                                                                                                                                                           |
| `disallowedTools` | `['mcp__*']`                         | 上の保険。SDK の挙動が変わっても、MCP のツールをモデルに見せない                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `settingSources`  | `[]`                                 | 設定ファイル（CLAUDE.md や `.claude/`）を読ませない                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `maxTurns`        | `1`（文章を返すだけなら）            | ツールが無いので、1 往復で終わる。1 往復で終わらない実行（`error_max_turns`）は、失敗として扱う                                                                                                                                                                                                                                                                                                                                                                                   |
| `persistSession`  | `false`                              | 会話を SDK 側に残さない                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `env`             | `process.env` を土台に組み立てたもの | SDK の `env` は、子プロセスの環境を丸ごと置き換える。そのため、`process.env` を土台にして `PATH` などを引き継ぐ。**端末の `ANTHROPIC_API_KEY` は渡さない**。このアプリでキーを使うときは、専用の環境変数（`<アプリ名>_ANTHROPIC_API_KEY`。例 `MYAPP_ANTHROPIC_API_KEY`）を `config.ts` で読み、その値だけを `ANTHROPIC_API_KEY` として入れる。専用の環境変数が無いときは、手元の Claude Code のログインを使う（開発中の便宜。第三者に提供するサービスでは、専用のキーを設定する） |
| `abortController` | 上限時間で `abort()` する            | 上限時間（例 `GENERATION_TIMEOUT_MS`）は環境変数で決める。上限を超えたら中断し、502 を返す。生成は数分かかることがある                                                                                                                                                                                                                                                                                                                                                            |

## 運用の必須事項

- **同時実行数に上限を置く**（例 `MAX_CONCURRENT_GENERATIONS`）。上限を超えたリクエストは 429 で断る
- **利用者ごとの頻度制限**を掛ける（例 1 分 5 回）
- **利用者の入力（説明文・生成物）をログに出さない。** ログに残すのは、モデル名・所要時間・費用・失敗の種類だけにする
- **SDK が返した失敗の中身を、利用者へのレスポンスに載せない。** `details` には理由の種類だけを入れる。中身はログに残す
- SDK が返した出力は、`service/` で解析・検証してから使う（HTML なら形式の検査、JSON ならスキーマの検証）

## テスト

- **SDK に渡した `options` を検証する**テストを 1 本以上書く（`tools` / `strictMcpConfig` / `disallowedTools` /
  `settingSources` / `maxTurns` / `persistSession` と、`env` に端末の `ANTHROPIC_API_KEY` が無いこと）。
  このテストでは、SDK の `query()` を `vi.hoisted` + `vi.mock` で差し替えて、HTTP 経由で API を呼ぶ
- 専用のキーを設定した場合の `env` は、`config` を差し替える別ファイルのテストで確かめる
- 差し替えた SDK に形の崩れた出力を返させ、その出力を使わずに失敗（502）として扱うことを確かめるテストを置く
- 実際にモデルを呼ぶ経路は、自動テスト（CI）で確かめない。下の「評価」で確かめる

## 評価（実際にモデルを呼んで確かめる）

AI を呼ぶ機能ごとに、代表的な入力と正しい答えの条件を決めておく。実際のモデルで繰り返し流して判定する。

| 項目       | 決まり                                                                                                                                                                                                                                                                                                    |
| :--------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 置き場所   | 入力と条件は `server/evals/<機能>/cases.json`。`server/package.json` に `eval`（例 `tsx --env-file-if-exists=.env evals/run.ts`）を足し、`npm run eval -w server -- <機能>` で流す                                                                                                                        |
| ケース     | 代表的な入力を 3〜5 件。答えが入力に無いもの、または曖昧なものを 1 件は入れる（無い値を作らないかを見る）。利用者の実データは入れない                                                                                                                                                                     |
| 回数       | 各ケース 3 回（例: 5 件 × 3 回 = 15 回呼ぶ）                                                                                                                                                                                                                                                              |
| 呼び方     | プロンプトの組み立て・`provider/` の呼び出し・応答の検証をまとめた `service/` の関数を直接呼ぶ。HTTP・認証・DB への保存は通さない                                                                                                                                                                         |
| 判定       | コードで確かめられる条件を使う（値の一致、語を含む、応答の検証を通る、入力に無い値を作っていない）。読みやすさのように機械で決められない質だけ、別の呼び出しで 1〜5 の採点をさせ、合格とみなす点数の下限を決める。採点のプロンプトの組み立てと結果の解釈は `evals/` に置き、呼び出しは `provider/` を通す |
| 合格の基準 | 例: 不合格は全体で 1 回まで。「入力に無い値を作っていない」条件は全回で合格。案件で決めた基準は `docs/decisions/` に残す                                                                                                                                                                                  |
| 回すとき   | AI を呼ぶ機能を足したとき、プロンプト・モデル・応答の扱いを変えたとき。CI では回さない                                                                                                                                                                                                                    |
| 記録       | `docs/results/<機能>-eval.md` に、日付・コミット・モデル・ケースごとの合格数・基準と判定を書く。回し直したら同じファイルを書き換える。PR 本文の「確認した結果」に合否と記録のファイルを書く                                                                                                               |

`server/evals/` を初めて置くときは、次を確かめる。

- `server/tsconfig.check.json` の `include` に `evals/**/*.ts` があること。無ければ足す
- `server/eslint.config.js` の、SDK の import を止める設定の `files` に `evals/**/*.ts` があること。無ければ足す
- `server/eslint.config.js` の、開発用の依存を読んでよい範囲（`import-x/no-extraneous-dependencies` の `devDependencies`）に `evals/**` があること。無ければ足す
- 結果の表示は `process.stdout.write` で行う（検査: ESLint。`console` を止める）

## 記録

- SDK を採用した理由と、上の指定の根拠を `docs/decisions/` に残す
- 専用のキー・上限時間・同時実行数の環境変数を足す（書き足す場所は [server-coding-conventions.md](server-coding-conventions.md) の「環境変数」）

## なぜ

例に Claude Agent SDK を使うのは、API キーが無くても AI の機能を作って試せるためです。
開発者の手元の Claude Code のログインで動きます。第三者に提供するサービスでは、専用のキーを設定します
（「Claude Agent SDK を呼ぶときに指定すること」の `env` の行）。

AI の SDK を入れるかどうかをシン株式会社が判断する理由は 2 つあります。1 つ目は、AI の SDK には利用料がかかることです。
2 つ目は、Claude Agent SDK のライセンスが OSS のライセンスではないことです。ライセンスは `SEE LICENSE IN README.md` で、
ライセンスの検査はこの SDK を通しません。この規約は、入れると決まった後の書き方です。

`strictMcpConfig` を指定するのは、開発者のコネクタ（MCP）を、利用者の入力を処理するモデルに見せないためです。
`tools: []` が外すのは、組み込みのツールだけです。手元の Claude Code のログインに紐づく claude.ai のコネクタは、
`tools: []` では外れません。開発者の手元で動かすと、モデルから開発者の Gmail や Notion のツールが見えます。
モデルがそのツールを呼ぼうとすると、生成が失敗します。

`disallowedTools` も指定するのは、SDK の版が変わって `strictMcpConfig` が効かなくなったときの備えです。

`env` を明示するのは、別の案件向けの `ANTHROPIC_API_KEY` を誤って使わないためです。`env` を指定しないと、SDK は
端末の環境変数をそのまま子プロセスに渡します。端末に別の案件向けの `ANTHROPIC_API_KEY` があると、SDK はそのキーを
使います。その結果、別の案件のキーで課金されます。このアプリ専用の変数だけを渡す形にすれば、開発者の端末に何が
設定されていても、使うキーは変わりません。

`config` は、モジュールの読み込み時に決まります。そのため、専用のキーを設定した場合の `env` は、`config` を
差し替える別ファイルで確かめます。

上限時間と同時実行数を必須にするのは、サーバーの子プロセスと費用が際限なく増えるのを防ぐためです。生成は 1 回に
数分かかり、費用は数十円かかります。上限が無いと、利用者が操作するたびに、子プロセスと費用が積み上がります。

評価を置くのは、変更の前後を同じ物差しで比べるためです。AI の応答は、同じ入力でも毎回揺れます。
1 回動かして期待どおりでも、次も同じとは限りません。プロンプトを直したときに別の入力で崩れても、気づけません。

条件をコードで判定するのは、判定そのものを揺らさないためです。AI に採点させると、採点も揺れます。
件数と回数を小さく決めておくのは、時間と費用を抑えるためです。評価は 1 回ごとに時間と費用がかかります。
評価で `service/` の関数を直接呼ぶのは、モデルの応答だけを見るためです。HTTP・認証・DB への保存は、自動テストが確かめています。
CI で回さない理由は 2 つあります。1 つ目は、キーと費用が要ることです。2 つ目は、応答の揺れで CI が不安定になることです。

`server/evals/` を初めて置くときに `tsconfig.check.json` の `include` を確かめるのは、評価を型検査と型情報つきの lint の
対象にするためです。無いと、lint が解析の誤りで止まります。SDK の import を止める設定の `files` を確かめるのは、
評価からも SDK を直接呼ばずに `provider/` を通すためです。評価は配布物に入らないので、開発用の依存を読んでよい範囲に
`evals/**` を入れます。
