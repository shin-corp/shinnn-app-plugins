# DB のマイグレーション

**スキーマの正は `server/src/db/schema/*.ts`。** SQL を手で書かず、そこから生成する。
生成された `server/drizzle/` のファイルは手で編集しない（`.claude/settings.json` の deny が止める）。

## 1. スキーマを直す

`server/src/db/schema/` に、テーブル・カラム・制約を書く。

- 列は原則 `notNull()` にし、既定値を付ける。あとから必須にするのは既存行があると難しい
- 消す前に、その列を参照しているコードが無いことを確認する

## 2. マイグレーションを生成する

```
npm run db:generate -w server
```

`server/drizzle/` に SQL とメタデータが増える。

## 3. 生成された SQL を必ず読む

**ここを飛ばさない。** 次のどれかに当たったら、適用する前に人に確認する。

| 危ないパターン | なぜ | どうするか |
|:--|:--|:--|
| `DROP TABLE` / `DROP COLUMN` | 入っているデータが消える | 本当に消してよいか確認する。残すなら列名の変更として扱う |
| 列名の変更が `DROP` + `ADD` になっている | 値が引き継がれない | drizzle-kit の対話で「rename」を選び直す |
| `NOT NULL` を既存の列に付けている | 既存行が空なら失敗する | 先に既定値で埋める文を足すか、いったん nullable にする |
| 一意制約の追加 | 既存データが重複していると失敗する | 重複を確認してから当てる |

## 4. 適用する

```
npm run db:migrate -w server
```

`drizzle-kit push` は使わない（マイグレーションを残さず DB を直接変えるため、他の環境で同じ状態を再現できない）。

## 5. 確認する

```
npm run test -w server
```

テストは既定で PGlite に対してマイグレーションを当てるので、**生成物がおかしければここで落ちる。**

## 6. コミット

スキーマと生成物を**同じコミット**に入れる（片方だけだと、その時点でチェックアウトした人が動かせない）。
実装やテストとは分ける。
