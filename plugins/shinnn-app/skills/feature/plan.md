# 計画を作る

要望が PR 1 本に収まらないときに、Issue に分けて順番を決める手順。`SKILL.md` の 0 から使う。
計画は GitHub に残す（**親 Issue = 計画、子 Issue = PR 1 本分**）。会話が変わっても、親 Issue を読めば続きから進められる。

## 1. 分ける

| 決めること | 決め方 |
|:--|:--|
| 1 本の単位 | 使う人から見て 1 つできるようになること。1 本ごとに shared → server → client → テストを通し、**それだけで動く**状態にする。画面だけ・API だけの Issue にしない |
| 順番 | 他の機能が使うデータの登録・一覧を先に、記録・集計・出力・権限を後にする。最初の 1 本は、動くものの中でいちばん小さくする |
| 依存 | 前の Issue のコード（API 定義・テーブル）が `main` に無いと作れないときだけ「#n の後」を付ける。**付けすぎると、マージ待ちで止まる回数が増える** |
| やらないこと | 要望のうち今回の計画に入れないものを分けて書く。あとから計画に足せると伝える |

## 2. 確認する（1 回だけ）

- 確認の質問は**計画全体で 3 つまで**（何のためか / 誰が使うか / 保存するデータは何か から選ぶ）。分からないことは仮置きし、該当する Issue の「未決」に書く
- 一覧を**利用者の言葉で**見せて、この順で進めてよいかを 1 回だけ聞く。Issue・ブランチ・API などの言葉は使わない

```
ご要望を 5 つに分けて、この順に作ります。
1. 商品を登録・一覧できる
2. 入庫・出庫を記録できる（1 の後）
3. 在庫数を一覧で見られる（2 の後）
4. 月ごとの集計を見られる（2 の後）
5. CSV で書き出せる（3 の後）
今回はやらないこと: 担当者ごとの権限（あとで足せます）
仮に決めたこと: 在庫がマイナスになる出庫は受け付けない
この順で進めてよいですか？
```

- 直したいと言われたら、直した一覧をもう一度見せる

## 3. GitHub に残す

1. 親 Issue を作る。タイトルは `[計画] <要望の要約>`、ラベルは `type:feature` と `status:doing`
2. 子 Issue を「作る順番」のとおりに作る。本文は `SKILL.md` の 1 と同じ形にし、先頭に `計画: #<親の番号>` を書く。
   依存があれば `前提: #<番号>（マージされてから着手）` も書く
   - タイトルは `[機能] <できるようになること>`、ラベルは `type:feature` と、依存が無ければ `status:next`、あれば `status:blocked`
   - 受入条件の番号は、計画の Issue 同士でも重ならないように通しで振る
3. 親 Issue の本文を、下の形で書き直す。**この「作る順番」が計画の正**
4. 子 Issue を親 Issue の sub-issue として紐づける。GitHub の画面で進み具合が見えるようにするためで、失敗しても止めない

   ```
   id=$(gh api repos/{owner}/{repo}/issues/<子の番号> --jq .id)
   gh api repos/{owner}/{repo}/issues/<親の番号>/sub_issues -F sub_issue_id="$id"
   ```

5. `docs/仕様書.md` の「3. スコープ」の「やること」「やらないこと」を直す。この変更は先頭の Issue の PR に入れる（`main` に直接コミットしない）。
   受入条件は、各 Issue に着手したときに入れる（`SKILL.md` の 2）

親 Issue の本文:

```markdown
## 要望

（利用者が伝えた言葉をそのまま）

## 作る順番

1. #12 商品を登録・一覧できる
2. #13 入庫・出庫を記録できる（#12 の後）
3. #14 在庫数を一覧で見られる（#13 の後）

## 今回やらないこと

- 担当者ごとの権限

## 仮に決めたこと

- 在庫がマイナスになる出庫は受け付けない（#13 の未決）
```

## 4. 計画に足す（途中で要望が増えたとき）

- 今の計画に関係する要望なら、子 Issue を 3 の 2 と 4 の形で作り、親の「作る順番」に足す（依存があれば、その Issue より後ろ）
- 関係しない要望なら、PR 1 本に収まるものは Issue だけを作り（`status:next`）、収まらないものは別の計画にする
- 足したことを利用者に 1 行で伝える（例: 「バーコードの読み取りを 6 番目に足しました」）

## 5. 依存が解けた Issue を進める

- 「作る順番」で `#n の後` と書いた Issue は、前提の Issue がすべて閉じていれば `status:blocked` を `status:next` に変える
- 子 Issue がすべて閉じたら、親 Issue に「すべて完了」とコメントして閉じる
- 順番を変える・やめる Issue があるときは、先に親の「作る順番」を直す。やめる Issue は理由をコメントしてから閉じる
