# データベース規約

PostgreSQL 16 と Drizzle ORM です。層の位置づけは [server-architecture.md](server-architecture.md) を参照。

「（検査: …）」には、その決まりを機械で確かめる仕組みを書いています。付いていない決まりは、レビューだけで確かめます。

## 新規ファイルの配置判断

| 書こうとしているもの   | 置き場所                                                           |
| :--------------------- | :----------------------------------------------------------------- |
| テーブル定義           | `server/src/db/schema/<テーブル>.ts`（1 ファイル 1 テーブル）      |
| 接続                   | `server/src/db/client.ts`（新設しない）                            |
| マイグレーションの適用 | `server/src/db/migrate.ts`                                         |
| マイグレーション SQL   | `server/drizzle/`（`drizzle-kit generate` の生成物）               |
| クエリ                 | `server/src/service/<機能>.service.ts`（`db/` にクエリを置かない） |
| 初期データ             | `server/seed/`                                                     |

## スキーマ

- **テーブルは `db/schema/*.ts` でだけ定義する。** SQL の `CREATE TABLE` を手で書かない
- テーブル名・列名は snake_case、TypeScript 側の識別子は camelCase にする（`casing: 'snake_case'` が変換する）
- 主キーは `uuid` にする。作成日時 `created_at` と更新日時 `updated_at` を、すべてのテーブルに置く
- **一意性・参照整合・値域は、DB の制約（UNIQUE / FK / CHECK）で表す。** TypeScript の if 文だけで守らない
- **利用者ごとのデータのテーブルには、持ち主の列（DB では `owner_id`、TypeScript では `ownerId`）を `NOT NULL` で
  置く。**
- 持ち主の列の型は `varchar` にする
- 持ち主ごとの一意性は、`(owner_id, name)` のような複合の UNIQUE で表す
- 削除は物理削除にする。ただし、論理削除が要る場合は、仕様書に理由を書いたうえで論理削除にしてよい
- 列は `NOT NULL` にする。ただし、API 定義で省略できる項目（`.optional()`）の列は、NULL を許してよい
- `NOT NULL` の列のうち、作成のときに値を省略できる列（状態・日時など）には、既定値を付ける

## マイグレーション

手順は `/shinnn-app:db-migrate`（スキーマを直す → SQL を生成する → 生成された SQL を読む → 適用する）。

- **生成された SQL を読んでから適用する。** 意図しない `DROP` や型の変更が入っていないかを確かめる。
  列の削除と名前の変更では、生成された SQL がデータを消す形になっていないかも確かめる
- `drizzle-kit push` を使わない
- `server/drizzle/` の中を直したいときは、スキーマを直して生成し直す（生成物を手で編集しない決まりは、
  [git-workflow.md](git-workflow.md) の「やらないこと」）
- 生成済みのマイグレーションを書き換えない。変更を取り消したいときは、**打ち消す新しいマイグレーションを足す**

## クエリとトランザクション

- クエリは Drizzle のクエリビルダで書く。ただし、ビルダで表現できない場合は、理由をコメントに書いたうえで
  生 SQL（`sql` テンプレート）を使ってよい
- **1 つのリクエストで複数の書き込みをするときは、`db.transaction()` で囲む**
- **同じトランザクションの中のクエリは、1 つずつ `await` する。** `Promise.all` で並べない
  （同じ接続での並行クエリは非対応）
- 読んだ値を組み合わせて判断する複数のクエリは、読み取り専用のトランザクションにまとめる
- 一覧を返すクエリには `limit` を付ける。全件を取得するクエリを書かない
- 利用者の入力を、文字列の連結で SQL に埋め込まない。クエリビルダかプレースホルダを使う

## なぜ

制約を DB 側に置くのは、どの経路から書き込んでも制約を効かせるためです。管理画面・バッチ・手作業の SQL の
どれから書き込んでも、DB の制約は効きます。TypeScript の検査が効くのは、その検査を書いた経路を通ったときだけです。
並行して実行されたときも、if 文の検査はすり抜けます。DB の制約はすり抜けません。

持ち主の列を `varchar` にするのは、uuid 以外の識別子を使う認証の方式にも合わせるためです。持ち主ごとの複合の UNIQUE の
索引は、持ち主での絞り込みにも効きます。

列を最初から `NOT NULL` にするのは、あとから必須に変える作業を避けるためです。既存の行があると、あとから必須に
するのは難しくなります。

`drizzle-kit push` を使わないのは、どの環境でも同じ DB の状態を再現できるようにするためです。`drizzle-kit push` は、
マイグレーションを残さずに DB を直接変えます。そのため、他の環境で同じ状態を再現できません。

マイグレーションの生成物を手で編集しないのは、「スキーマ定義が正で、SQL は生成物」という関係を保つためです。
手で編集すると、次に `generate` を実行したときに、その編集が失われます。または、スキーマ定義との差分が二重に出ます。

トランザクションで囲むのは、書き込みが途中まで成功した状態を残さないためです。この状態が、いちばん直しにくい
状態です。どの行まで書けたかを人が調べる作業は、非エンジニアには手に負えません。
